# DeepSeek API + OpenRouter rules for driving DeepSeek models in a Claude Code-style tool loop

Research date: 2026-09-23. Scope: DeepSeek official API (OpenAI-compatible `https://api.deepseek.com` and Anthropic-compatible `https://api.deepseek.com/anthropic`) and OpenRouter IDs `deepseek/*`. Live JSON from `https://openrouter.ai/api/v1/models` and `https://openrouter.ai/api/v1/models/{id}/endpoints` was pulled on 2026-09-23 and is quoted below; everything else is cited by URL. Wayback Machine fetches were blocked from this environment, so V3.2-era official numbers that no longer appear on api-docs.deepseek.com are flagged as secondary or inferred.

Headline context that changes the assignment's premise: the official model names `deepseek-chat` and `deepseek-reasoner` (the V3.x names) were retired on 2026-07-24; the official API now serves `deepseek-flash` (V4.1-Flash) and `deepseek-v4-pro`. The V3.1 / V3.2 / R1 model IDs still exist on OpenRouter but are served only by third-party hosts (SiliconFlow, Novita, DeepInfra, GMICloud, Google Vertex, etc.), not by DeepSeek itself. The reasoning/tool rules below are therefore split into "official API today (V4.x)" and "V3.x-era rules that still govern the third-party endpoints".

## Key Question 1: Function calling — supported models/modes, `tools`/`tool_choice` shapes, strict mode, parallel calls, streaming, `finish_reason`, limits

### Takeaway
DeepSeek's Chat Completions API takes the standard OpenAI `tools`/`tool_choice` shape (`none|auto|required|{type:function,...}`), supports tool use inside thinking mode "from DeepSeek-V3.2" onward, and has a Beta strict mode that requires `base_url=https://api.deepseek.com/beta`, `strict: true`, every property in `required`, and `additionalProperties: false`. Nothing official documents parallel-call limits, streaming delta semantics, a maximum tool count or schema size; the observable failure modes are text-serialized tool calls (`finish_reason: "stop"`, `tool_calls: null`) and third-party DSML parser bugs.

### Inferences
- Because the official Chat Completions endpoint "does not support inserting tool calls mid-conversation", a harness must keep the strict `assistant(tool_calls)` → `tool` → `tool` ordering and never synthesize tool-call turns the model did not emit; the Anthropic-format endpoint is the documented path if you need to inject tool turns (e.g. compaction replay).
- The 11% text-serialized tool-call rate on V4-Pro (official API) and the `<think>`/DSML leakage on third-party hosts imply the harness needs a content-side fallback parser (detect `name{json}` / DSML markup in `content` when `finish_reason == "stop"` and `tool_calls` is null) plus a one-shot retry with `tool_choice: "required"` when a tool call was expected.
- Streaming aggregation should key tool calls by `delta.tool_calls[].index`, treat a missing index as "same call as last chunk", never overwrite a captured `id`/`name` with null, and ignore empty `tool_calls: []` arrays on reasoning-only chunks.

### Gaps
- No official statement on a maximum number of tools or a byte/token cap on tool schemas; searches only surfaced the 64-tools/287k-prompt failure report above.
- No official documentation of streaming tool-call delta semantics (whether `id` arrives once, whether arguments are chunked) — only third-party bug reports.
- `parallel_tool_calls` is not documented on api-docs.deepseek.com; whether the official API honours it is unverified.

## Key Question 2: Thinking / reasoning — `reasoning_content` return and pass-back rules, `thinking` / `reasoning_effort`, thinking + tools, visibility toggles

### Takeaway
On the current official API (V4.x), thinking is on by default at effort `high`; `reasoning_content` comes back as a top-level assistant-message field in both streaming and non-streaming responses. The load-bearing rule: if the request carries `tools`, every prior assistant message's `reasoning_content` must be sent back verbatim or the API returns HTTP 400 `The \`reasoning_content\` in the thinking mode must be passed back to the API.`; if the request has no `tools`, `reasoning_content` is ignored. Through OpenRouter, send it back as `reasoning` (string) or as the unmodified `reasoning_details` array; `reasoning_content` is accepted as an alias of `reasoning`.

### Cited Findings
- Enabling (OpenAI format): `extra_body={"thinking": {"type": "enabled"}}`; "Thinking mode is enabled by default, with the default effort being high"; supported efforts `low`, `high`, `max`; OpenAI-style effort names are mapped: "minimal → low; low → low; medium → high; high → high; xhigh → high; max → max; ultra → max". — [DeepSeek Thinking Mode guide](https://api-docs.deepseek.com/guides/thinking_mode)
- API reference: `thinking` object — `type`: `enabled` or `disabled` (default `enabled`); `reasoning_effort`: `none`, `low`, `high`, `max`; response `message.reasoning_content`: "For thinking mode only. The reasoning contents of the assistant message, before the final answer."; `usage.completion_tokens_details.reasoning_tokens` reported in thinking mode. — [DeepSeek Chat Completions API reference](https://api-docs.deepseek.com/api/create-chat-completion)
- Pass-back rule (verbatim): "If the request **carries the `tools` parameter**: the `reasoning_content` of all previous turns should be passed back to the API and will be concatenated into the context." / "If the request **does not carry the `tools` parameter**: `reasoning_content` does not need to be passed back; even if passed to the API, it will be ignored and will not be concatenated into the context." / "If your code does not correctly pass back `reasoning_content`, the API will return a 400 error." Recommended pattern: `messages.append(response.choices[0].message)` i.e. `{'role': 'assistant', 'content': ..., 'reasoning_content': ..., 'tool_calls': ...}`. — [DeepSeek Thinking Mode guide](https://api-docs.deepseek.com/guides/thinking_mode)
- Earlier wording of the same rule (quoted from the docs in a 2026 issue): "For turns that do perform tool calls, the reasoning_content must be fully passed back to the API in all subsequent requests." with the observed pattern "First turn with tool call: succeeds; Subsequent turns: fail with 400 error due to missing reasoning_content"; DeepSeek "tolerates this omission for non-tool-call turns but mandates it for tool-call turns". — [anomalyco/opencode issue #24722](https://github.com/anomalyco/opencode/issues/24722)
- Exact error strings: OpenAI endpoint `"The \`reasoning_content\` in the thinking mode must be passed back to the API."`; Anthropic endpoint `"The \`content[].thinking\` in the thinking mode must be passed back to the API."` (models deepseek-v4-pro / deepseek-v4-flash, issue 2026-05-05). — [musistudio/claude-code-router issue #1378](https://github.com/musistudio/claude-code-router/issues/1378)

### Inferences
- Implementable rule for the provider layer (official OpenAI-format endpoint): keep `reasoning_content` on every stored assistant message; when re-sending history with `tools`, emit `reasoning_content` on every assistant message (empty string when the turn had none, per the Continue/Kilo fixes); when the request has no `tools`, it is harmless to send it. Never re-order or edit it. Do not strip it at a new user turn — the API ignores what it does not need, but omission is what triggers the 400.
- The V3.2 open-weights template shows the model itself only conditions on reasoning inside an unfinished tool-call turn (`drop_thinking=True` removes it once the turn ended with a final answer); the official API's "pass all previous turns back" requirement is therefore a server-side validation/caching convenience, not a sign that the model reads old reasoning. This is why sending back reasoning is safe and cheap (it is cache-hit input).
- Through OpenRouter, store `reasoning`/`reasoning_details` from each assistant message and replay both unchanged; OpenRouter maps them to the provider's `reasoning_content`. Because OpenRouter relays DeepSeek's 400 verbatim, the same missing-field bug surfaces identically.
- For the V3.x IDs on OpenRouter, reasoning must be requested explicitly (`reasoning: {enabled: true}`) since `default_enabled` is false for `deepseek-v3.2`; for R1 it is mandatory; for V4.x Flash it is on by default and must be turned off with `reasoning: {enabled: false}` (or DeepSeek's `thinking: {type: "disabled"}` when calling DeepSeek directly).
- The Roo/rikkahub reports indicate that third-party endpoints have not always honoured the toggle or parsed `<think>` blocks; a harness should defensively strip a leading `<think>...</think>` (and stray `<｜end▁of▁sentence｜>`) from `content` when it appears.

### Gaps
- The R1-era statement that including `reasoning_content` in input causes a 400 (the pre-V3.2 inverse of today's rule) could not be re-verified from a primary page (Wayback blocked; the current docs no longer carry it). Treat it as historical only; the current rule (must pass back when `tools` present) is the one enforced.
- Whether DeepSeek's official API offers a way to hide `reasoning_content` while still thinking (an equivalent of OpenRouter's `reasoning.exclude`) is not documented.
- No official statement on whether `reasoning_content` from the Anthropic-format endpoint carries a `signature` or whether redacted blocks exist; only the error string `content[].thinking ... must be passed back` is documented via the issue above.

## Key Question 3: System prompt and message-shape handling — system message placement, multiple system messages, array content, images, ordering

### Takeaway
DeepSeek's API schema accepts `system` anywhere and multiple system messages (verified HTTP 200 on two-system payloads for both `deepseek/deepseek-v3.2` and DeepSeek-V4-Flash), accepts array content parts (`text`, `image_url`, `file`) with vision on `deepseek-flash`, and rejects the `developer` role. The practical hazard is behavioural, not schema-level: a request whose last message is `system` produced 1–3-token empty completions from DeepSeek via OpenRouter, so a harness should keep one leading system message and send any later instruction text as `user`.

### Cited Findings
- Roles: messages is a `oneOf System message | User message | Assistant message | Tool message`; system message has `content` (string) and optional `name`; user `content` is "Either a string, or an array of content parts (for image input). See the Vision guide"; content parts are `text`, `image_url` (http(s) URL max 8192 chars or base64 data URL; JPEG/PNG/GIF/WebP; `detail`: low/high/original/auto — "low downsamples the image to 512x512"), and `file`; tool message `content` is "Either a string, or an array of content parts (for image input)"; assistant messages accept `name`, `prefix` (Beta) and `reasoning_content` (Beta). — [DeepSeek Chat Completions API reference](https://api-docs.deepseek.com/api/create-chat-completion)
- `developer` role: "The official API does not accept messages assigned to `developer`." — [DeepSeek-V3.2 model card](https://huggingface.co/deepseek-ai/DeepSeek-V3.2/raw/main/README.md)
- Vision availability: `deepseek-flash` (V4.1-Flash) "includes vision capabilities; the pro version does not". — [DeepSeek Models & Pricing](https://api-docs.deepseek.com/quick_start/pricing); OpenRouter `architecture.input_modalities` is `['text','image']` for `deepseek/deepseek-v4.1-flash` and `deepseek-v4-flash-vision-exp`, and `['text']` for every V3.x/R1/V4-Pro ID. — [OpenRouter /api/v1/models](https://openrouter.ai/api/v1/models)
- Multiple/non-leading system messages: "DeepSeek models explicitly do NOT exhibit this constraint. Testing against `deepseek-ai/DeepSeek-V4-Flash` and `deepseek/deepseek-v3.2` shows both return HTTP 200 when given the identical two-system-message payload that fails on Qwen" (Qwen returns "System message must be at the beginning."). — [nearai/cloud-api PR #1026](https://github.com/nearai/cloud-api/pull/1026)
- Trailing system message failure: "DeepSeek models via OpenRouter returned an empty assistant message (1-3 tokens, `finish_reason: stop`) whenever the final message had role `system`", causing `max_empty_responses` after three turns; fix: `mapMessages` "now rewrites any system-role message that is not the first message to role `user` on the wire. Position and content remain unchanged"; verified 2026-09-06 with "three consecutive production runs using DeepSeek v4 Flash ... zero empty response retries". — [dennisonbertram/go-code PR #1396](https://github.com/dennisonbertram/go-code/pull/1396)
- Statelessness: the API "is stateless — the server does not record the context of the user's requests"; you must "concatenate all previous conversation history" each call. — [DeepSeek Multi-round Conversation guide](https://api-docs.deepseek.com/guides/multi_round_chat)
- R1-era: "Avoid adding a system prompt; all instructions should be contained within the user prompt." — [deepseek-ai/DeepSeek-R1 README](https://github.com/deepseek-ai/DeepSeek-R1)
- Claude Code via DeepSeek's Anthropic endpoint (official): `ANTHROPIC_BASE_URL="https://api.deepseek.com/anthropic"`, `ANTHROPIC_AUTH_TOKEN=<DeepSeek API key>`, `ANTHROPIC_MODEL="deepseek-flash[1m]"`, `ANTHROPIC_DEFAULT_OPUS_MODEL="deepseek-flash[1m]"`, `ANTHROPIC_DEFAULT_SONNET_MODEL="deepseek-flash[1m]"`, `ANTHROPIC_DEFAULT_HAIKU_MODEL="deepseek-flash"`, `CLAUDE_CODE_SUBAGENT_MODEL="deepseek-flash"`, `CLAUDE_CODE_EFFORT_LEVEL="max"`, `CLAUDE_CODE_AUTO_COMPACT_WINDOW="786432"`; "The DeepSeek API natively supports the Web Search feature in Claude Code"; claude-opus names map to `deepseek-v4-pro`, claude-haiku/sonnet to `deepseek-flash`. — [DeepSeek: Integrate with Claude Code](https://api-docs.deepseek.com/quick_start/agent_integrations/claude_code/)

### Inferences
- Recommended ordering for the bridge: exactly one leading `system`; convert any later system-role scaffold (reminders, "now respond" nudges) to `user` (or fold into the last user message); never end the array with `system`; keep `assistant(tool_calls)` immediately followed by its `tool` results; then the next `user`.
- Array content is safe for the official V4.1 endpoint; for V3.x IDs on OpenRouter third-party hosts, flatten to a plain string unless the endpoint's `input_modalities` includes image, since those endpoints are text-only.

### Gaps
- The exact scaffold-echo phrase "Now, respond to the last non-system message" was not found in any public source; the only related evidence is the trailing-system empty-response behaviour above. Its origin (likely a harness-injected trailing system message being echoed) is unverified.
- No official documentation on how the model treats a second system message semantically (accepted by schema, behaviour undocumented).

## Key Question 4: Context windows, output limits, overflow error wording, context caching, pricing

### Takeaway
Official API today: 1M context on both `deepseek-flash` and `deepseek-v4-pro`, max output 384K (393216), `max_tokens` defaults 8K/64K/128K by mode, and the overflow error is `This model's maximum context length is N tokens. However, you requested X tokens (Y in the messages, Z in the completion). Please reduce the length of the messages or completion.` — note that `max_tokens` counts toward the total. Prefix caching is automatic with `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens` in `usage`. V3.x on OpenRouter is 163,840 context with per-provider max output from 7,168 to 147,456.

### Inferences
- Budgeting rule: reserve `max_tokens` explicitly (e.g. 16K–64K for agent turns) and compute `prompt_budget = context_length - max_tokens`; the overflow error counts the requested completion, so a large default (Zed's 384,000) halves usable context.
- Cache economics favour a stable prefix (system prompt + tool schemas first, identical bytes each turn) and appending only; any edit to earlier turns (including dropping `reasoning_content`) invalidates the prefix from that point.
- On OpenRouter, do not rely on `top_provider.max_completion_tokens`; the endpoint you actually land on may cap output at 7,168 (SambaNova/Mara), 16,384 (DeepInfra fp4) or 32,768 (Venice) for `deepseek-v3.2`.

### Gaps
- The V3.2-era official `max_tokens` defaults (4K/8K chat, 32K/64K reasoner) are from secondary sources only; the primary page has been replaced by the V4.1 table.
- The V4.1-Flash news page hints at a V4-Pro pricing/routing change "starting September 14, 2026" but the fetched summaries conflicted with the changelog ("DeepSeek V4 Pro API services [will continue] after September 14, 2026"); the pricing page still lists `deepseek-v4-pro` as a live model. Verify before hardcoding.

## Key Question 5: OpenRouter provider variance for `deepseek/*` IDs, pinning, and `/api/v1/models` metadata

### Takeaway
As of 2026-09-23 DeepSeek itself is an OpenRouter provider only for the V4.x IDs (`deepseek-v4.1-flash`, `deepseek-v4-pro-0813`); `deepseek/deepseek-v3.2` has 16 third-party endpoints with wildly different caps (max output 7,168–147,456; context 32K–163,840), quantizations (fp4/fp8/unknown), and feature flags (Baidu, DigitalOcean, Mara, SambaNova do not list `tools`). Pin with `provider: {order: [...], allow_fallbacks: false, require_parameters: true}` and filter `quantizations`; OpenRouter itself documents that quality variance is "mainly because quantization differences across hosts".

- Provider routing fields: `order` ("List of provider slugs to try in order"), `allow_fallbacks` (default true), `require_parameters` (default false; "Only use providers that support all parameters in your request"), `data_collection`, `only`, `ignore`, `quantizations` (int4, int8, fp8, bf16, ...), `sort` ("price", "throughput", "latency"), `max_price`, `zdr`; "Tools and `response_format` are soft preferences even when [`require_parameters` is] false, deprioritizing unsupporting providers only if alternatives exist"; suffixes `:nitro` (throughput) and `:floor` (price); base slugs match variants (`deepinfra` vs `deepinfra/turbo`, `google-vertex/us-east5`). — [OpenRouter Provider Routing](https://openrouter.ai/docs/features/provider-routing)

### Inferences
- A safe pin for V3.2 tool loops: `provider: {order: ["siliconflow", "novita", "gmicloud"], allow_fallbacks: false, require_parameters: true, quantizations: ["fp8"]}` plus an explicit `max_tokens` ≤ 65536 (Novita's cap) — SiliconFlow/GMICloud accept up to 147456. Exclude `deepinfra` (fp4, 16384 output), `baidu`, `digitalocean`, `mara`, `sambanova` (no `tools`), and treat `atlas-cloud` as degraded (status -2).
- `require_parameters: true` is the only way to make `tools`/`reasoning` hard requirements; otherwise OpenRouter treats tools as a soft preference and may route to a non-tool endpoint when the preferred ones are down.
- For the V4.x IDs, prefer the first-party `deepseek` endpoint (lowest cache-read price, full 393216 output) via `provider.order: ["deepseek"]`; the `~deepseek/*-latest` aliases silently change models and should not be used in a harness that depends on stable tool behaviour.

### Gaps
- OpenRouter's public endpoints JSON no longer exposes boolean `supports_tool_parameters` / `supports_reasoning` fields (both returned null); tool support was inferred from `supported_parameters`.
- Provider-specific tool-quality benchmarks (e.g. which host most often serializes tool calls as text) are not published; only the anecdotal issues above exist.
- OpenRouter did not respond in issue #538, so the cause of the 1-token `length` stops (provider-side prompt cap vs. computed completion budget) is unconfirmed.

## Key Question 6: Prompting and harness guidance — temperature, avoiding text tool calls, forcing native calls, `</think>` leakage, language mixing, repeated identical calls, `max_tokens` defaults

### Takeaway
DeepSeek's own guidance is sparse: temperature 1.0 / top_p 0.95 for V3.2 (and temperature is ignored in thinking mode), 0.5–0.7 for R1 with no system prompt; JSON mode needs the word "json" in the prompt. Everything else — loop guards for identical tool calls, stripping `<think>`/special tokens, content-side tool-call recovery, explicit `max_tokens` — comes from harness authors' bug fixes, which converge on the same handful of defensive rules.

### Cited Findings
- V3.2 sampling: "For local deployment, we recommend setting the sampling parameters to `temperature = 1.0, top_p = 0.95`." — [DeepSeek-V3.2 model card](https://huggingface.co/deepseek-ai/DeepSeek-V3.2/raw/main/README.md); OpenRouter's `default_parameters` for `deepseek/deepseek-v3.2` are `temperature 1, top_p 0.95` and for `deepseek-v3.2-exp` `temperature 0.6, top_p 0.95`. — [OpenRouter /api/v1/models](https://openrouter.ai/api/v1/models)
- Thinking mode ignores `temperature`, `presence_penalty`, `frequency_penalty`; `top_p` clamped to 0.95–1.0. — [DeepSeek Thinking Mode guide](https://api-docs.deepseek.com/guides/thinking_mode); `frequency_penalty` and `presence_penalty` are marked deprecated in the current API reference. — [DeepSeek Chat Completions API reference](https://api-docs.deepseek.com/api/create-chat-completion)
- R1: temperature 0.5–0.7 (0.6 recommended) "to prevent endless repetitions or incoherent outputs"; no system prompt; force `<think>\n` prefix. — [deepseek-ai/DeepSeek-R1 README](https://github.com/deepseek-ai/DeepSeek-R1)
- Language mixing: V3.1-Terminus addressed "instances of mixed Chinese-English text and occasional abnormal characters" and optimized "the performance of the Code Agent and Search Agent". — [DeepSeek-V3.1-Terminus model card](https://huggingface.co/deepseek-ai/DeepSeek-V3.1-Terminus); OpenRouter describes Terminus as "addressing issues reported by users, including language consistency and agent capabilities" — [OpenRouter /api/v1/models](https://openrouter.ai/api/v1/models); V4-Pro's text-serialized tool calls were "often preceded by brief natural language commentary in Chinese". — [deepseek-ai/DeepSeek-V3 issue #1244](https://github.com/deepseek-ai/DeepSeek-V3/issues/1244)
- Repeated identical tool calls: "deepseek-v4-pro collapses into repeated identical tool_call inside its working context window, no client-side circuit breaker" — [QwenLM/qwen-code issue #4695](https://github.com/QwenLM/qwen-code/issues/4695); an OpenCode subagent issued "364 identical grep tool calls over ~50 minutes ... burning ~184k input tokens + ~40k output tokens + ~142M cache-read tokens" with "no repeated-action detection, no step limit, no heartbeat timeout" — [anomalyco/opencode issue #45442](https://github.com/anomalyco/opencode/issues/45442); mitigations: deny "the 2nd identical call (same tool name + canonically-equal arguments, property order ignored) before it executes" — [snailium/dsh-repeat-tool-breaker](https://github.com/snailium/dsh-repeat-tool-breaker); count repeats "cumulatively across a turn — not just consecutive runs" and either block the call or conclude the turn — [LIN-LAB-AI/dsh-loop-guard](https://github.com/LIN-LAB-AI/dsh-loop-guard); hash name+arguments and "inject a message to the agent asking it to change approach" after a threshold — [langchain-ai/deepagents issue #6441](https://github.com/langchain-ai/deepagents/issues/6441)
- `</think>` / special-token leakage: `deepseek-v3.2-exp` via OpenRouter answering inside the think block — [rikkahub/rikkahub issue #566](https://github.com/rikkahub/rikkahub/issues/566); `<｜end of sentence｜>` in reasoning strings and "Strip tokenizer artifacts before injecting reasoning into retry sequences" — [NousResearch/hermes-agent issue #86303](https://github.com/NousResearch/hermes-agent/issues/86303); a client fix titled "stop deepseek-flash tool-call markup from leaking into streamed output" — [linkerdog/rara PR #896](https://github.com/linkerdog/rara/pull/896)
- Text tool calls vs native: DeepSeek-V4-Pro returns tool calls as text with `finish_reason: "stop"` about 11% of the time in one session; the issue recommends "using content + tool_calls together per OpenAI spec rather than serializing tool calls into content". — [deepseek-ai/DeepSeek-V3 issue #1244](https://github.com/deepseek-ai/DeepSeek-V3/issues/1244); `tool_choice: "required"` exists to force a call. — [DeepSeek Chat Completions API reference](https://api-docs.deepseek.com/api/create-chat-completion)
- Reasoning round-trip fixes shipped by harnesses (all April–September 2026): OpenCode/Kilo inject empty `reasoning_content` on assistant messages lacking it — [Kilo-Org/kilocode issue #9501](https://github.com/Kilo-Org/kilocode/issues/9501); Continue documents `reasoning_content: ""` as the required element — [continuedev/continue issue #12246](https://github.com/continuedev/continue/issues/12246); loom sends `reasoning` to OpenRouter and `reasoning_content` to DeepSeek/Zhipu — [loomagent/loom PR #64](https://github.com/loomagent/loom/pull/64); LangChain.js `@langchain/deepseek` had the same drop bug — [langchain-ai/langchainjs issue #10883](https://github.com/langchain-ai/langchainjs/issues/10883); Codex CLI — [openai/codex issue #24500](https://github.com/openai/codex/issues/24500); n8n reported it as a "regression after DeepSeek V3.2" — [n8n-io/n8n issue #22579](https://github.com/n8n-io/n8n/issues/22579); JetBrains — [LLM-27762](https://youtrack.jetbrains.com/projects/LLM/issues/LLM-27762/DeepSeek-V4-models-fail-on-multi-turn-conversations-with-reasoningcontent-round-trip-error)

- Aider's DeepSeek page recommends only `aider --model deepseek/deepseek-chat` with `DEEPSEEK_API_KEY` (no other settings). — [Aider DeepSeek docs](https://aider.chat/docs/llms/deepseek.html); Roo Code: "Roo Code supports all models available through the DeepSeek API" with `deepseek-chat` / `deepseek-reasoner` examples — [Roo Code DeepSeek provider](https://roocodeinc.github.io/Roo-Code/providers/deepseek); Cline's page covers only key setup. — [Cline DeepSeek provider](https://docs.cline.bot/provider-config/deepseek)
- Keep-alive handling: non-streaming responses may contain leading empty lines and streaming responses `: keep-alive` SSE comments; inference must start within 10 minutes. — [DeepSeek Rate Limit](https://api-docs.deepseek.com/quick_start/rate_limit/)

### Inferences
- System-prompt rules for the bridge: one leading system message; state explicitly that tool calls must be emitted only through the native tool-call channel (never as text or DSML markup in the answer), that the assistant must not repeat a tool call whose result it already has, and that answers must be in English; keep the tool schemas byte-stable for cache hits.
- Provider-layer rules: do not send `temperature` when thinking is enabled (ignored anyway); send `temperature: 1.0, top_p: 0.95` for V3.2 non-thinking; always set `max_tokens` explicitly (≤ provider cap) and derive the prompt budget from it; strip a leading `<think>...</think>` and DeepSeek special tokens from `content`; fall back to parsing `name{json}` / DSML from `content` when a tool call was expected; retry once with `tool_choice: "required"`; implement an identical-call breaker (hash of name + canonical JSON arguments, cumulative per turn); on `finish_reason: "length"` with ≤ 1 completion token treat as provider failure and re-route rather than retry in place.
- For R1-family IDs, route the system prompt into the first user message and prefill `<think>\n`; R1 on OpenRouter has `reasoning.mandatory: true`, so budget for reasoning tokens inside `max_tokens`.

### Gaps
- DeepSeek publishes no cookbook-style prompting guidance for agent/tool use beyond the sampling recommendations and JSON-mode note; searches found no official statement on repeated calls, language mixing in tool loops, or `<think>` leakage.
- No harness (Cline, Roo, OpenCode, Aider, Kilo) documents DeepSeek-specific prompt text in its public docs; their behaviour is visible only through the bug fixes cited above.
