## Q1. What is "ori" exactly (name, repo, language, license, version, maintainers, cadence, install)?

### Takeaway
"Ori" is **Ori CLI / "Ori Harness"**, OpenRouter's official, **closed-source** CLI (single self-contained binary, ~100–127 MB per platform). Its headline job is to *configure and launch existing coding agents* (Claude Code, Codex, OpenCode, Hermes, Cline, Kilo, Muse, omp, Pi, Prime Agent, DeepSeek Harness, Grok Build) against OpenRouter with OAuth PKCE sign-in and per-harness/per-model "optimized settings"; since 0.8.0 it also ships **its own first-party agent loop** (`ori code` headless + chat TUI with built-in bash/read/write/edit/glob/grep tools, sessions, compaction, approvals, MCP), plus **Ori Eval**. It is NOT an SDK or an "OpenRouter Interface"; the SDKs are separate (`@openrouter/agent` etc.). Latest stable: **0.15.5+74c4cf2 (2026-09-24)**; curated changelog stops at 0.10.1 (2026-08-24).

## Q2. How is the agent loop built and which OpenRouter API features does it use?

### Takeaway
Two paths: (a) **wrapper mode** — Ori injects OpenRouter credentials/env/config and execs the third-party harness, which then talks to OpenRouter itself (Claude Code → Anthropic-compatible `https://openrouter.ai/api`, OpenAI-style harnesses → `https://openrouter.ai/api/v1`, Pi → OpenRouter Responses API); (b) **first-party loop** (default since 0.8.0) — a native turn loop with built-in tools, steering, subagents, approvals, sessions/compaction, threads, MCP, prompt caching, `--reasoning-effort`, `/fast` (throughput/fast-tier routing), `/zdr` (ZDR-only routing), presets, usage panel. Earlier versions drove harnesses over ACP (Claude Code, Pi, native Codex adapter).

### Cited Findings
- Wrapper contract: "You set the model with a single flag, and Ori sends anything after its own flags to the agent unchanged" ... "your agent starts with OpenRouter credentials, models, and settings in place." — [H](https://openrouter.ai/docs/guides/ori/harness)
- "we detect your `--model` flag and switch the settings to be most optimal for the model you're using." ... "For Anthropic models, enabling `ENABLE_TOOL_SEARCH` will save you almost half the system prompt in tokens." ... "when tool search is disabled, Claude uses more tokens, more turns to accomplish the same task, and uses the Todo tool more!" — [BH](https://openrouter.ai/blog/announcements/ori-harness/)
- Endpoint difference Ori handles: Claude Code uses `https://openrouter.ai/api` while OpenAI-compatible clients use `https://openrouter.ai/api/v1` — [aireiter](https://aireiter.com/blog/openrouter-cli-shell-workflows)
- Changelog architecture milestones (verbatim summaries): 0.2.2 "ACP wire foundation/connection runtime"; 0.2.3 "ACP agents (Claude Code, Pi), typed hooks, rollover/compaction, `/resume`/`/compact`"; 0.3.0 "Headless `ori code` with prompt-to-completion, structured JSONL output, session persistence across processes"; 0.4.0 "Provider-neutral agent connection seam, harness initialization/compaction, native Codex ACP adapter"; 0.5.0 "Claude credential isolation, non-Anthropic models"; 0.6.0 "One harness engine (removes switching), vault tunnel for secret egress"; 0.7.1 "`ori pi` via OpenRouter Responses API, `--reasoning-effort` flag, preset picker, turn speed reporting"; **0.8.0 "First-party loop default (unbundles Pi), native turn loop with steering/subagents/approval, built-in bash/read/write/edit/glob/grep tools, sessions/compaction, auto-approvals, threads (events/interception/structured output), MCP/harness inspection, faster cold start, usage panel/credit recovery, Pi prompt caching/token caps"**; 0.9.0 "`bypass` default approval, `auto` classifier mode, `manual` mode ... key validation"; 0.10.0 "Breaking: `self-drive` replaces `bypass`, `auto` removed; classifier removed" — [CL](https://openrouter.ai/docs/guides/ori/changelog)
- Prompt caching: 0.3.0 "Pi Anthropic `cache_control` breakpoints"; 0.8.0 "Pi prompt caching/token caps" — [CL](https://openrouter.ai/docs/guides/ori/changelog)
- Routing toggles in-session: "`/fast` enables fast routing (Claude fast mode, OpenAI Fast tier, throughput-sorted routing)"; "`/zdr` routes to zero-data-retention providers only"; Prime Agent uses `/speed`; `/model` "comes from your catalog" (organization-filtered); Grok Build/Muse Code get the catalog but no toggles; other harnesses get model validation at launch — [H](https://openrouter.ai/docs/guides/ori/harness)
- Org guardrails apply server-side: "Set guardrails, allowlists, and per-workspace permissions on your OpenRouter organization, and set workspace budgets there too. OpenRouter applies them to every request." — [H](https://openrouter.ai/docs/guides/ori/harness)
- Headless usage from OpenRouter's own skill: `ori code --model openai/gpt-5.6-terra --prompt-file <path>/task.txt`; never `--harness`; `ori auth` checks credentials; summary line format `summary  model=served/model  duration=200ms  input=100  output=25  context=90  $0.012346` — [spawn-ori-eval SKILL.md](https://github.com/OpenRouterTeam/skills/blob/main/skills/spawn-ori-eval/SKILL.md)
- `ori code` flags: `-p`, `--prompt-file`, `--model`, `--harness`, `--session`, `--json`, headless — [E](https://openrouter.ai/docs/guides/ori/eval)
- Hosted variant ("Interns", in the Ori docs group): `POST /api/v1/interns/{internId}/chat/completions`, `stream` must be `true`, `session_id` client-chosen, `approval_mode` `"self-drive"` (default) | `"manual"`; pauses with `finish_reason: "tool_calls"` on tool `openrouter.provide_input` with `kind: "permission"` (`allow_once|allow_always|reject_once|reject_always`) or `kind: "elicitation"`; continue by re-sending history plus a `tool` message; runtime model id `openrouter/intern`; 5-minute deadlines; `409 interaction_not_pending` — [intern-chat](https://openrouter.ai/docs/guides/ori/intern-chat)
- Vault (host-bound secrets for interns): `PUT /api/v1/vault/secrets/{name}` with `value` + `hosts[]`; "the intern runtime releases the value only to requests bound for one of those hostnames"; HMAC-SHA-256 fingerprints; names 1–255 lowercase; values ≤65,536 chars — [vault](https://openrouter.ai/docs/guides/ori/vault)
- The same primitives appear in OpenRouter's public Agent SDK loop: `callModel` "runs an inference loop that: 1. Sends the input to the model 2. If the model returns tool calls, executes them automatically 3. Appends tool results to the conversation 4. Repeats until a stop condition is met"; stop conditions `stepCountIs()`, `maxCost()`, `hasToolCall()`; MCP tools "drop straight into callModel" — [Agent SDK overview](https://openrouter.ai/docs/agent-sdk/overview); streams `getTextStream()`, `getToolCallsStream()`, `getReasoningStream()`, `getItemsStream()`, `getFullResponsesStream()` — [callModel](https://openrouter.ai/docs/agent-sdk/call-model/overview)

### Inferences
- "ACP" in the changelog is almost certainly Zed's Agent Client Protocol (Claude Code, Codex and Pi all have ACP adapters); Ori's chat TUI drove those harnesses over ACP before 0.8.0 made its own loop the default.
- `/fast` maps to OpenRouter `provider.sort: "throughput"` / `:nitro`-style priority tiers plus Claude's fast mode (Claude Code needs `CLAUDE_CODE_SKIP_FAST_MODE_ORG_CHECK=1`); `/zdr` maps to `provider.zdr: true`. Both are OpenRouter-only request fields.
- The intern API is the hosted form of Ori's first-party loop (same `self-drive`/`manual` approval vocabulary as `--approvals`, `openrouter/intern` model id).

### Gaps
- Whether the first-party loop uses Chat Completions or the Responses API, and whether it sends `reasoning_details` back, `usage`, `transforms`/`context-compression`, `plugins`, or `models` fallback arrays, is not documented.
- Structured JSONL output schema of `ori code --json` is not documented.

## Q3. What does its system prompt say; does it vary by model family?

### Takeaway
Ori's own system prompt is unpublished (closed source). What *is* documented: per-model switching of harness settings (tool search on Claude via `ENABLE_TOOL_SEARCH`, fallback to full tool descriptions otherwise), and OpenRouter's public harness template convention: static base prompt + appended `AGENTS.md`/`CLAUDE.md` sections.

### Cited Findings
- "we detect your `--model` flag and switch the settings to be most optimal for the model you're using" — [BH](https://openrouter.ai/blog/announcements/ori-harness/)
- Wiki (secondary): for Claude models Ori enables tool search by default "reducing system prompt token usage by nearly half" and "falls back to full tool descriptions for models lacking tool search support" — [Learn AI wiki](https://ai.miraheze.org/wiki/Ori_Harness)
- OpenRouter's harness template: "System Prompt Composition" combines a static base prompt with files found in the project such as "AGENTS.md" and "CLAUDE.md", appended as sections via `composeSystemPrompt({ base, files, projectDir })` — [create-agent-tui modules.md](https://github.com/OpenRouterTeam/skills/blob/main/skills/create-agent-tui/references/modules.md)
- The template "draws from production patterns: pi-mono/coding-agent — three-layer separation, JSONL sessions, pluggable tools; Claude Code — tool metadata (read-only, destructive, approval); Codex CLI — layered config, approval flow, structured logging" — [create-agent-tui SKILL.md](https://github.com/OpenRouterTeam/skills/tree/main/skills/create-agent-tui)
- `@openrouter/agent` passes the system prompt as `instructions` to `callModel` — [callModel](https://openrouter.ai/docs/agent-sdk/call-model/overview)

### Inferences
- In wrapper mode the system prompt is the wrapped harness's own (Claude Code's, Codex's...); Ori only changes environment (e.g. tool search) — so "prompt varies by model family" is realized as *harness settings* varying, not prompt text.

### Gaps
- No quotable Ori prompt text exists publicly.

## Q4. How does it handle weaker tool-calling models; per-model adapters / capability detection?

### Takeaway
Documented Ori behaviours are catalog-level: model-slug validation with near-miss correction, catalog filtering to text-in/text-out, per-model settings switching, `--reasoning-effort`, and "non-Anthropic models" support for Claude Code. There is no public documentation of text-embedded-tool-call parsing, JSON-arg repair or automatic `require_parameters`/provider pinning inside Ori. The OpenRouter platform pieces a replica should use are: `/api/v1/models` `supported_parameters`, per-provider "Tool Call Error Rate", `min_tool_success_rate` filter, `provider.require_parameters`, `provider.ignore/only/order`, and Response Healing (JSON only, non-streaming).

### Cited Findings
- "near-miss slugs are corrected (with a notice), and unknown IDs pass through untouched." — [H](https://openrouter.ai/docs/guides/ori/harness)
- Changelog: 0.2.0 "Model catalog filtering (text-in/text-out)"; 0.2.1 "OpenRouter provider prefix (`openrouter/`)", "Plain catalog ids in picker, harness-owned prefix"; 0.5.0 "non-Anthropic models"; 0.7.1 "`--reasoning-effort` flag"; 0.10.1 "variant model resolution, readable picker prices, no batch variants" — [CL](https://openrouter.ai/docs/guides/ori/changelog)
- Claude Code caveat from OpenRouter: "Non-Anthropic providers may lack compatibility with thinking blocks and native tool use" — [Claude Code integration](https://openrouter.ai/docs/cookbook/coding-agents/claude-code-integration)
- Agent SDK: "Invalid tool arguments are caught before execution" and "Errors in execute functions are caught and sent back to the model" (Zod validation error returned as the tool result; no automatic retry documented) — [Agent SDK tools](https://openrouter.ai/docs/agent-sdk/call-model/tools)
- Models API fields for capability detection: `supported_parameters` enum = `temperature, top_p, top_k, min_p, top_a, frequency_penalty, presence_penalty, repetition_penalty, max_tokens, max_completion_tokens, logit_bias, logprobs, top_logprobs, prediction, seed, response_format, structured_outputs, stop, tools, tool_choice, parallel_tool_calls, include_reasoning, reasoning, reasoning_effort, web_search_options, verbosity`; `architecture.input_modalities` (text, image, file, audio, video), `architecture.tokenizer`, `architecture.instruct_type`; `top_provider.{context_length,max_completion_tokens,is_moderated}`; `pricing.{prompt,completion,request,image,web_search,internal_reasoning,input_cache_read,input_cache_write,input_cache_write_1h,audio,audio_output,discount,overrides}`; `per_request_limits`; `default_parameters`; query params include `supported_parameters=`, `min_tool_success_rate`/`max_tool_success_rate` [0–1], `zdr`, `region` (`eu`|`us`), `q`, `context`, `sort=agentic-high-to-low|coding-high-to-low|...`; per-endpoint data via `links.details` → `/api/v1/models/:slug/endpoints` — [Models API](https://openrouter.ai/docs/api/api-reference/models/list-all-models-and-their-properties)
- Tool calling page: "the `tools` parameter must be included in every request" (also when sending results back); `parallel_tool_calls: false` → one tool at a time (default true); arguments arrive as JSON strings; "The `Tool Call Error Rate` metric on model pages tracks provider reliability"; filter `openrouter.ai/models?supported_parameters=tools` — [Tool calling](https://openrouter.ai/docs/guides/features/tool-calling)
- `provider.require_parameters: true` = "Only route to providers supporting all request parameters"; `ignore`, `only`, `order`, `allow_fallbacks` — [Provider routing](https://openrouter.ai/docs/guides/routing/provider-selection)
- Structured outputs advice: "Set `require_parameters: true` in your provider preferences" to guarantee `response_format: json_schema` support — [Structured outputs](https://openrouter.ai/docs/guides/features/structured-outputs)
- Response Healing (`{"id": "response-healing"}`) fixes missing brackets/commas/quotes, markdown-wrapped JSON, trailing commas, unquoted keys — but only for `response_format` `json_schema`/`json_object`, **non-streaming only**, and "The documentation does not indicate support for tool calls" — [Response healing](https://openrouter.ai/docs/guides/features/plugins/response-healing)
- Community workaround for Kimi K2 tool calls via OpenRouter: ignore providers Baseten and DeepInfra "which get confused calling tools" — [zed discussion #37032](https://github.com/zed-industries/zed/discussions/37032)

### Inferences
- A rolo-claude replica should: (1) fetch `/api/v1/models` once per session and gate tools on `supported_parameters` containing `tools` (and `reasoning`/`structured_outputs` as needed); (2) send `provider: { require_parameters: true }` whenever `tools` or `response_format` are present; (3) keep a per-model `provider.ignore` list (e.g. Baseten/DeepInfra for Kimi K2) sourced from the endpoint "Tool Call Error Rate"; (4) implement its own text-embedded tool-call parser and JSON-arg repair, since OpenRouter's Response Healing does not cover tool calls.

### Gaps
- No evidence that Ori itself does any of (1)–(4); it may rely on the wrapped harness or on OpenRouter server-side normalisation.

## Q5. Tool set and tool schema naming

### Takeaway
Ori's first-party loop ships "built-in bash/read/write/edit/glob/grep tools" (names as listed in the changelog) plus steering, subagents, approvals and MCP. OpenRouter's public template uses snake_case names (`file_read`, `file_write`, `file_edit`, `glob`, `grep`, `list_dir`, `shell`, optional `js_repl`, `sub_agent`, `plan`, `request_input`, `web_fetch`, `view_image`) with Zod schemas and read-only/mutating metadata; OpenRouter server tools use the `openrouter:` type prefix.

### Cited Findings
- Ori 0.8.0: "built-in bash/read/write/edit/glob/grep tools"; subagents; "MCP/harness inspection"; 0.7.1 "skill materialization"; 0.8.0 "skills (inspect-logs/selfdev)" — [CL](https://openrouter.ai/docs/guides/ori/changelog)
- `ori skills get create-eval` / `ori eval skill` expose skills from the CLI — [spawn-ori-eval SKILL.md](https://github.com/OpenRouterTeam/skills/blob/main/skills/spawn-ori-eval/SKILL.md)
- Template tool schemas (verbatim names/fields): `file_read` {`path`, `offset?`, `limit?`} read-only, 2000-line cap, 2000-char/line truncation; `file_write` {`path`, `content`}; `file_edit` {`path`, `edits[{old_text,new_text}]`} unified diff output; `glob` {`pattern`, `path?`} respects .gitignore, 1000 results; `grep` {`pattern`, `path?`, `glob?`, `ignoreCase?`} 100 results; `list_dir` {`path`} 500 entries; `shell` {`command`, `timeout?`} 120 s default, 256 KB cap; optional `js_repl` {`code`}, `sub_agent` {`task`, `message`, `model?`}, `plan` {`items[{step,status}]`} single in-progress item, `request_input` {`questions[]` 1–3, 2–4 options each}, `web_fetch` {`url`} SSRF-protected 50 KB, `view_image` {`path`} — [create-agent-tui tools.md](https://github.com/OpenRouterTeam/skills/blob/main/skills/create-agent-tui/references/tools.md)

## Q9. Known issues with DeepSeek, Kimi K2, Qwen3, GLM, Gemini through OpenRouter in agent loops

### Takeaway
The dominant failure class is **reasoning state not echoed back with tool calls**: Gemini 3 (`thought_signature`), DeepSeek thinking mode (`reasoning_content`), and Claude (signature-only reasoning chunks). Second class: **provider variance** in tool-call parsing (Kimi K2 on Baseten/DeepInfra emitting `<|tool_calls_section_begin|>` inside reasoning; Qwen3-Coder/Qwen 3.7 sending wrong argument types; GLM emitting Python-repr JSON). Third: providers that lack `tools` support returning "404 no tool use".

### Cited Findings
- Gemini: error "Gemini models require OpenRouter reasoning details to be preserved in each request." with upstream "Function call is missing a thought_signature in functionCall parts. This is required for tools to work correctly."; fix = echo `reasoning_details` from the tool-call turn in the assistant message of the follow-up request; opened 2025-12-18 for `google/gemini-3-flash-preview` — [gptel #1190](https://github.com/karthink/gptel/issues/1190); same failure in [cherry-studio #11418](https://github.com/CherryHQ/cherry-studio/issues/11418), [Roo-Code #10307](https://github.com/RooCodeInc/Roo-Code/issues/10307), [lobehub #10986](https://github.com/lobehub/lobehub/issues/10986), [claude-code-router #1024](https://github.com/musistudio/claude-code-router/issues/1024), [microsoft/agent-framework #2947](https://github.com/microsoft/agent-framework/issues/2947); Gemini "frequently returns a thought carried only as a signature with no text field" and rejects replayed camelCase `thoughtSignature` that isn't base64 — [openclaw #841](https://github.com/openclaw/openclaw/issues/841); [inspect_ai PR #4979](https://github.com/UKGovernmentBEIS/inspect_ai/pull/4979)
- DeepSeek: OpenRouter returns 400 "The reasoning_content in the thinking mode must be passed back to the API." when an assistant message with both reasoning and `tool_calls` is replayed without its reasoning — [opencode #35689](https://github.com/anomalyco/opencode/issues/35689); same in [kilocode #9501](https://github.com/Kilo-Org/kilocode/issues/9501); "DeepSeek V3.1 Terminus forces reasoning; cannot disable" — [Roo-Code #8270](https://github.com/RooCodeInc/Roo-Code/issues/8270); reasoning traces lost when `reasoning_details` text isn't promoted (DeepSeek V4 Flash) — [OmniRoute #12665](https://github.com/diegosouzapw/OmniRoute/issues/12665)

## Q10. Pointing ori at Databricks / other OpenAI-compatible endpoints (added requirement)

### Takeaway
Ori exposes exactly one documented knob for a custom endpoint — `ORI_OPENROUTER_BASE_URL` ("API endpoint for inference requests") — plus `OPENROUTER_API_KEY` as a bearer credential, but nothing documents non-OpenRouter gateways, and most of Ori's value (OAuth PKCE, org-filtered catalog, `/fast`, `/zdr`, presets, key validation, usage/credit panel, Claude Code via the Anthropic-compatible `/api` endpoint) depends on OpenRouter-only endpoints and request fields. Databricks serves an OpenAI-compatible Chat Completions surface (`https://<workspace>/serving-endpoints`, `model` = endpoint name, `Authorization: Bearer <token>`) that "differs from the Anthropic API" and documents no `provider`/`reasoning`/`plugins`/`models` fields. Verdict: `ori claude`→Databricks is not viable without an Anthropic→OpenAI translating proxy (which is what claude-bridge's `bridge.py` already is); `ori code`→Databricks via `ORI_OPENROUTER_BASE_URL` is *untested and undocumented*.

### Cited Findings
- `ORI_OPENROUTER_BASE_URL` — type URL — "API endpoint for inference requests"; `OPENROUTER_API_KEY` env credential; `ORI_FORCE_OPENROUTER_API_KEY` "Prioritizes environment variable over stored credentials"; `ORI_DISABLE_ENV_KEY_LOGIN` "Rejects environment `OPENROUTER_API_KEY`"; `ORI_REQUIRE_LOGIN` refuses non-`ori login` credentials — [EV](https://openrouter.ai/docs/guides/ori/env-vars)
- Configuration page "does not address custom gateways, proxies, self-hosted endpoints, non-OpenRouter providers" (only `channel`, `autoUpdate`, `env{}`) — [C](https://openrouter.ai/docs/guides/ori/configuration); harness page has "No mention of `ORI_OPENROUTER_BASE_URL` or custom base URLs" — [H](https://openrouter.ai/docs/guides/ori/harness)
- Web search for the variable name returns only OpenRouter's own pages (no third-party reports of using it with LiteLLM/Databricks/etc.) — [search result set](https://openrouter.ai/blog/announcements/ori-harness/)
- Ori's OpenRouter-specific dependencies: OAuth PKCE sign-in; "The `/model` list comes from your catalog" (org-filtered); `/fast` = "Claude fast mode, OpenAI Fast tier, throughput-sorted routing"; `/zdr` = ZDR-only providers; org guardrails/budgets "OpenRouter applies them to every request" — [H](https://openrouter.ai/docs/guides/ori/harness); presets picker (0.7.1), key validation (0.9.0), usage panel/credit recovery (0.8.0), Pi via "OpenRouter Responses API" (0.7.1) — [CL](https://openrouter.ai/docs/guides/ori/changelog)
- Claude Code (wrapped by `ori claude`) talks Anthropic Messages format to `https://openrouter.ai/api` — [Claude Code integration](https://openrouter.ai/docs/cookbook/coding-agents/claude-code-integration)
- Model names: "unknown IDs pass through untouched" (so a Databricks endpoint name would not be rewritten), near-miss slugs corrected with a notice — [H](https://openrouter.ai/docs/guides/ori/harness)
- Databricks OpenAI client: `base_url` "`https://<workspace>/serving-endpoints`", `api_key` = Databricks token, `model` = endpoint name; REST `Authorization: Bearer <databricks-token>`; "The Databricks REST API is OpenAI-compatible and differs from the Anthropic API" — [Query foundation models](https://docs.databricks.com/aws/en/machine-learning/model-serving/score-foundation-models); example `OpenAI(api_key="dapi-...", base_url="https://example.staging.cloud.databricks.com/serving-endpoints")`, `model="databricks-claude-sonnet-4-5"` — [Query a chat model](https://docs.databricks.com/aws/en/machine-learning/model-serving/score-chat-models)
- Databricks REST invocations path: `POST /serving-endpoints/{name}/invocations` — [FMAPI reference](https://docs.databricks.com/aws/en/machine-learning/foundation-model-apis/api-reference)
- Databricks chat request fields documented: `messages`, `max_tokens`, `temperature`, `top_p`, `top_k`, `stop`, `n`, `stream`, `tools` ("`function` is the only supported `tool` type"), `tool_choice` (`auto|required|none|object`), `response_format` (`text|json_object|json_schema`), `reasoning_effort` (`minimal|low|medium|high|xhigh|max|none`), `service_tier`, `logprobs`, `top_logprobs`; "Code interpreter and web search tools are not supported by Databricks"; **unknown-field behaviour not specified** — [FMAPI reference](https://docs.databricks.com/aws/en/machine-learning/foundation-model-apis/api-reference)
- Databricks also documents an OpenAI Responses API surface (Azure docs title "Query with the OpenAI Responses API") — [Microsoft Learn](https://learn.microsoft.com/en-us/azure/databricks/machine-learning/model-serving/query-openai-responses); AI Gateway is configured *on* serving endpoints rather than as a separate URL — [Configure AI Gateway](https://docs.databricks.com/gcp/en/ai-gateway/configure-ai-gateway-endpoints)
- Ori is closed source (see Q1): no way to patch endpoint handling — [OpenRouterIncubator/ori 404](https://github.com/OpenRouterIncubator/ori)

### Inferences
- `ori claude --model <databricks-endpoint>` cannot work against Databricks directly: Claude Code speaks Anthropic Messages, Databricks speaks OpenAI Chat/Responses. The existing `bridge.py` (Anthropic→Databricks translator) remains the right path; Ori adds nothing there.
- `ORI_OPENROUTER_BASE_URL=https://<workspace>/serving-endpoints` + `OPENROUTER_API_KEY=<dapi token>` + `ORI_MODEL=<endpoint name>` *might* let `ori code` reach Databricks if (a) Ori appends OpenAI-compatible paths (`/chat/completions`) to that base, (b) Databricks ignores unknown fields (`provider`, `reasoning`, `plugins`, `usage`, `models`, `transforms`) rather than 400-ing, and (c) Ori tolerates failures of its OpenRouter-only calls (catalog `/models`, key validation, presets, usage). None of (a)–(c) is documented; the expected-path suffix (`/api/v1` vs bare) is also unknown.
- Safest experiment (not run): put a logging OpenAI-compatible proxy (e.g. the existing bridge or LiteLLM) at `http://127.0.0.1:<port>`, set `ORI_OPENROUTER_BASE_URL` to it, run `ORI_OUTPUT=json ori code -p "ping" --model <endpoint>`, and inspect which paths and JSON fields Ori actually sends — that answers (a)–(c) in one run.
- For rolo-claude the practical conclusion is: replicate Ori's *conventions* (catalog-gated capabilities, `reasoning_details` echo, provider preferences, cache breakpoints, `/model` `/zdr` `/fast` UX) behind a provider abstraction, and only emit OpenRouter-specific fields when the base URL is `openrouter.ai`.

### Gaps
- Whether Databricks rejects or ignores unknown top-level fields is not documented in the pages fetched; needs an empirical curl test.
- The `.../ai-gateway/mlflow/v1/chat/completions` URL form named in the brief was not found in any Databricks page fetched; unverified.
- No public report of anyone using `ORI_OPENROUTER_BASE_URL` with a non-OpenRouter backend.
