## Q1. What is the harness called, where is the source, what language/runtime, what license, current version and release cadence? Does DeepSeek even have an official harness?

### Takeaway
Yes — since 2026-08-13 DeepSeek ships an official, MIT-licensed, TypeScript/Node agent harness called **DeepSeek Harness** (CLI binary `dsh`, npm package `@deepseek-ai/dsh`, repo `github.com/deepseek-ai/deepseek-harness`), in "developer preview" with near-daily alpha/rc releases (current `0.1.7-rc.1`, 2026-09-23). It is primarily a local **Web UI** plus headless/SDK/ACP modes; a terminal TUI exists only as an add-on plugin. "DeepSeek Code" was the pre-launch working name of the same Harness-team effort, not a separate shipped product. Third-party "DeepSeek CLI" projects (Deep Code, DeepSeek-TUI, Reasonix, fenwii/deepseek-cli…) are community tools.

## Q2. How does the agent loop work end to end (request assembly, tool execution, result feeding, stop conditions, retries, max turns)?

### Takeaway
`dsh-agent-loop` is a classic "call model, run tools, repeat" ReAct driver, but every model-visible fact is first appended to an append-only session log and the request is re-derived from that log each step; tool calls run through a guarded pipeline with up to 10 parallel-safe calls per step, retries are provider-policy driven (default 5), and there is deliberately **no built-in turn budget**.

### Cited Findings
- Turn/step flow (verbatim from architecture doc): "A **step** is one model request plus the tools it calls. A **turn** is zero or more steps" and
  ```text
  turn/start
    claim next-step input plus one queued message
    assemble prompt sections + tool schemas; project runtime context
    -> agent/pre-step                   reject | enter(messages, startsRequestSeries?)
       step/start
       agent/request -> prepareCall (cancellation commits neither system nor users)
       reconcile system/message using the prepared call capability
       append entered messages as user/message; log request/header and request/context as needed
       derive and freeze model history from the log
       stream the bound prepared call -> llm/stream -> agent/assistant-stream start
         agent/assistant-stream chunk*
         assistant/message | assistant/attempt -> agent/assistant-stream end
       tool/call* -> tools/pre-execute -> tools/execute -> tools/post-execute -> tool/result*
       step/end
       tools owe another request, or next-step input arrived -> claim -> next step
    -> agent/turn-stopping
  turn/end
  ```
  — [docs/architecture.md](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.md).
- Request assembly: "Each step sends the session's derived history — with the latest non-empty `system/message` node as the effective prompt … and its visible tool schemas; the model's tool calls run through the guarded tool pipeline and every accepted fact is appended to the session log before the next step derives from it." "The request is `header.config`, `deriveMessages()`, and `header.tools`; it carries no `system` field" (the system prompt travels as a system-role node in history) — [packages/core/agent-loop/README.md](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/core/agent-loop/README.md).
- Parallelism: config `maxParallelToolCalls` default `10` ("`1` is serial"); "Parallel-safe calls may overlap up to `maxParallelToolCalls`; exclusive calls run alone as ordering barriers"; `DEFAULT_MAX_PARALLEL_TOOL_CALLS = 10` — [agent-loop README](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/core/agent-loop/README.md), [src/constants.ts](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/core/agent-loop/src/constants.ts).
- Declarative agent config fields: `agents[].id`, `provider`, `model`, `reasoningEffort`, `maxTokens`, `cwd`, `sessionId`, `resumeSessionId` (mutually exclusive) — [agent-loop README](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/core/agent-loop/README.md); catalog entry in [docs/config-catalog.md](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/config-catalog.md).
- Retries and failures: "Final adapter selection, dispatch, and iteration failures arrive as terminal finishes and enter `agent/request-error`; a handling listener returns `{ kind: 'retry' }` … while an unhandled failure is terminal." "Retries reuse the same rendered assembly without repeating assembly, `agent/pre-step`, or user admission." — [agent-loop README](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/core/agent-loop/README.md). Provider adapters own `retryPolicy` ("omission uses normal mode with five retries") executed by `dsh-llm-retry` — [llm-deepseek README](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/llm/llm-deepseek/README.md), [config catalog `dsh-llm-retry`](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/config-catalog.md).
- Stop conditions / limits: "**No built-in turn budget** — tool calls or steering continue the current turn; a policy that bounds runaway turns must cancel from an existing lifecycle extension point such as `agent/turn-stopping`." — [agent-loop README](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/core/agent-loop/README.md). Loop-guard plugin `dsh-repeat-tool-reminder`: "Consecutive-repeat counts that trigger a reminder (default `[3, 5, 8]`)", `argumentsPreviewChars` default 500, `include`/`exclude` wildcard patterns — [config catalog](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/config-catalog.md); enabled in the base bundle with `thresholds: [3, 5, 8]` — [base cordis.patch.yml](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/bundle/base/cordis.patch.yml).
- Cancellation: "a cancelled stream appends an `interrupted: true` anchor with the delivered prefix so the next request contains what the user saw"; undispatched calls after cancellation get synthetic results with code `ABORTED_BEFORE_DISPATCH` and text `Error: tool call aborted before dispatch` — [agent-loop README](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/core/agent-loop/README.md).
- Tool pipeline and tool definition shape: tools are registered with `defineTool({ name, description, parameters: { field: { type, required, description } }, output: { schema, render, presentationMeta }, execute(args, exec) })` — e.g. [packages/fs/tool-fs/src/edit.ts](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/fs/tool-fs/src/edit.ts). Tool results are "first-class `ToolResultMessage` values with `toolCallId`, result `content`, and optional `isError`" — [docs/subsystems/llm-streaming.md](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/llm-streaming.md).
- Background jobs: bash `run_in_background`, subagents and PTY sends register with `ctx.jobs`; "A foreground command that reaches its timeout is not killed: it moves to the background the same way, returning its job id" — [docs/tool-catalog.md](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/tool-catalog.md). Job completion is injected as a user-role notice into the next step ("You are notified in-session when a job finishes — do not busy-poll") — [packages/jobs/tool-jobs/src/index.ts](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/jobs/tool-jobs/src/index.ts).
- Headless one-shot semantics: `dsh --profile headless "run the tests"` "creates one fresh persisted Agent…, submits the task, waits for quiescence, and flushes the Session… It streams non-empty provider reasoning deltas to stderr under a `dsh: reasoning:` heading, prints only the final text on stdout, and exits 0 for `completed`, else 1" — [apps/cli/reference/README.md](https://github.com/deepseek-ai/deepseek-harness/blob/master/apps/cli/reference/README.md). Headless app flags: `--json` ("write newline-delimited run events to stdout instead of the final message"), `--session-id <id>` — [packages/bundle/headless/src/startup.ts](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/bundle/headless/src/startup.ts); catalog config `task`, `sessionId`, `json` — [config catalog](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/config-catalog.md).

### Inferences
- For rolo-claude: the transferable pattern is "log first, derive request from log" (crash-safe resume, deterministic replay) plus exclusive-vs-parallel-safe classification of tools; DeepSeek Harness relies on the *model* (via reminders/notices) rather than a hard max-turns cap.

### Gaps
- I did not read `agent.ts` itself; step/turn wording above is from the package README and architecture doc, which the repo marks as authoritative contracts.

## Q3. What exactly is in the system prompt, and how does it avoid the model echoing scaffolding or producing malformed tool calls?

### Takeaway
The prompt is assembled from ordered, named sections: a fixed one-line identity, a one-line persona ("You are a coding agent powered by the {{model}} model."), one short guidance sentence per tool, optional plan-mode policy, MCP server instructions, and a suffix ("Your working directory is {{cwd}}."); dynamic state (sandbox/approval policy, AGENTS.md/CLAUDE.md, skill catalog, job notices) is injected as **user-role context snapshots**, not into the system prompt, to keep the prefix cache stable. Malformed-call defence is mostly structural (strict schemas with `required`, unresolved-variable/prompt failures fail loudly, read-before-edit policy, repeat-tool reminders) rather than prompt prose.

### Inferences
- The prompt is remarkably short compared with Claude Code's; DeepSeek's team pushes behaviour into (a) tool descriptions/schemas, (b) user-role snapshots that change without invalidating the cached prefix, and (c) structural guards. ## Q4. Which DeepSeek API features does it rely on (function calling, strict mode, `reasoning_content` round-trip, `thinking`, context caching, `max_tokens`, `stop`, streaming)?

### Takeaway
Surprisingly, the native adapter talks to DeepSeek through the **Anthropic Messages format** (`https://api.deepseek.com/anthropic` + `/v1/messages`, header `x-api-key`), not Chat Completions: it streams SSE with `stream: true`, sends tools as `{name, description, input_schema}`, thinking via `thinking: {type: enabled|disabled}` plus `output_config.effort: low|high|max`, `max_tokens` (default 256,000), `stop_sequences`, and replays `thinking` blocks with their `signature` so the "reasoning must be passed back" rule is satisfied natively; caching is DeepSeek's automatic prefix cache, read back from `cache_read_input_tokens`/`cache_creation_input_tokens`. OpenAI-format `reasoning_content` handling exists only in the pi-ai route via compat switches.

### Cited Findings
- Endpoint and format: "Stream DeepSeek models through `deepseek-official` using the Messages API"; "The official root is `https://api.deepseek.com/anthropic`. An explicit `baseURL` or `$DEEPSEEK_BASE_URL` supplies a Messages-compatible root. Model and Files requests append `/v1/messages` and `/v1/files`"; "Messages sends text, thinking, tool calls, and tool results as content blocks, reasoning effort as `output_config.effort`, and images as Files references or inline base64"; "API keys use `x-api-key`"; account tokens use `x-dsh-auth-token`; "Neither credential mode follows redirects" — [packages/llm/llm-deepseek/README.md](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/llm/llm-deepseek/README.md). `PUBLIC_BASE_URL = 'https://api.deepseek.com/anthropic'` — [src/config.ts:115](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/llm/llm-deepseek/src/config.ts).
- Request body (source): `model: options.model, stream: true, messages, max_tokens: options.maxTokens ?? model?.maxTokens ?? connection.maxTokens, thinking: { type: effort === 'off' ? - DeepSeek API rules the harness must satisfy (API docs): thinking is "enabled by default, with the default effort being `high`"; OpenAI format `{"thinking": {"type": "enabled/disabled"}}` + `reasoning_effort: low/high/max`; "for requests carrying the `tools` parameter, the `reasoning_content` must be fully passed back… even for turns where the model did not perform a tool call", else "the API will return a 400 error"; `temperature`/`presence_penalty`/`frequency_penalty` "will not trigger an error but will also have no effect"; `top_p` below 0.95 is treated as 0.95 in thinking mode — [Thinking Mode](https://api-docs.deepseek.com/guides/thinking_mode/). Exact 400 texts observed by clients: "The 'reasoning_content' in the thinking mode must be passed back to the API." (Chat Completions) and "The 'content[].thinking' in the thinking mode must be passed back to the API." (Anthropic endpoint) — [claude-code-router #1378](https://github.com/musistudio/claude-code-router/issues/1378); "Missing `reasoning_content` field in the assistant message at message index 2" — [vercel/ai #10778](https://github.com/vercel/ai/issues/10778).
- Function calling / strict mode (API docs): tools use the OpenAI `{"type":"function","function":{name,description,parameters}}` shape; strict mode is beta: `base_url="https://api.deepseek.com/beta"` with `"strict": true` per function, "All properties of every `object` must be set as `required`, and the `additionalProperties` attribute of the `object` must be set to `false`", supported types object/string/number/integer/boolean/array/enum/anyOf, `$ref`/`$def` supported, no minLength/maxLength/minItems/maxItems; "From DeepSeek-V3.2, the API supports tool use in the thinking mode"; "The Anthropic API and Responses API support inserting tool calls mid-conversation, while Chat Completion API does not" — [Tool Calls](https://api-docs.deepseek.com/guides/tool_calls).
- Context caching (API docs): "enabled by default for all users"; usage fields `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens`; cache units form at "the end position of the user input" and "the end position of the model output" and at fixed intervals; "best-effort"; cleared "within a few hours to a few days" — [Context Caching](https://api-docs.deepseek.com/guides/kv_cache).
- Anthropic-format models/endpoint: base URL `https://api.deepseek.com/anthropic`, models `deepseek-flash`, `deepseek-v4-pro` — [Anthropic API](https://api-docs.deepseek.com/guides/anthropic_api/).

### Inferences
- Because the native adapter uses the Messages format, the harness never touches `reasoning_content`; it simply replays `thinking` content blocks with signatures. A Chat-Completions-based rolo-claude must instead persist and resend `reasoning_content` on every assistant message once tools are in the request (empty string is accepted by the API per pi-ai's `requiresReasoningContentOnAssistantMessages` semantics, but loses the CoT).
- `max_tokens` is treated as a per-request output cap (default 256k), not an accounting concept; compaction uses `contextWindow − maxTokens − headroomTokens` as the pressure ceiling (see Q9).
- The harness does not use strict mode; its tool schemas (Q5) leave `additionalProperties` unset on top-level objects, which strict mode would reject.

### Gaps
- The DeepSeek docs page for "thinking with tools" (`/guides/thinking_with_tools`) redirected to the quick-start page at fetch time; the rule text above comes from `/guides/thinking_mode/` and from client issues. The Anthropic-format thinking parameter shown by the docs summary (`{"reasoning": {"effort": ...}}`) conflicts with what the adapter actually sends (`thinking.type` + `output_config.effort`); trust the adapter source.

## Q6. How does it handle config: user vs project config files, model selection, API keys, environment variables?

### Takeaway
Everything lives under `$DSH_HOME` (default `~/.dsh`): per-profile `profiles/<name>/cordis.patch.yml` + `package.json`, a machine-wide `cordis.patch.yml`, write-only `.credentials.yaml`, `sessions/`, `storages/`, `logs/`, and a user-global `AGENTS.md`; project-level config is limited to `AGENTS.md`/`CLAUDE.md` (+ `.local.md` overlays) and a `.env`. Model selection is a `provider`+`model` pair (default `deepseek-official`/`deepseek-flash`) stored as the session's recorded route; API keys resolve per request from env → `.credentials.yaml` → cwd `.env` → `$DSH_HOME/.env`.

### Cited Findings
- Layering: "The effective tree is composed over an empty root by applying, in order: each bundle patch named in the profile manifest's `dsh.profile.bundles` list, the profile's own `cordis.patch.yml`, the home-level `$DSH_HOME/cordis.patch.yml` (machine-local preferences shared by every profile, so it outranks the per-profile layer), and each `--patch <path>` overlay in argv order. Later layers win per row; a patch replaces the targeted row's complete `config` value rather than deep-merging keys" — [apps/cli/reference/README.md](https://github.com/deepseek-ai/deepseek-harness/blob/master/apps/cli/reference/README.md). - Launcher flags (verbatim help): `-V, --version`; `--profile <name>`; `--from-default-profile <name>`; `--patch <path>` (repeatable); `--dump-config`; `--dump-config-schema`; `--dump-default-config`; examples `dsh web`, `dsh headless "run the tests"`, `dsh tui --resume <session>`, `dsh plugin --profile tui add <package>` — [apps/cli/tests/expected/launcher-help.txt](https://github.com/deepseek-ai/deepseek-harness/blob/master/apps/cli/tests/expected/launcher-help.txt). ## Q8. Known issues/quirks reported by users relevant to tool calling and long agentic sessions with DeepSeek

### Takeaway
The dominant failure class is **session poisoning**: any crash or provider rejection that leaves an assistant `tool_calls` without matching tool results (or a truncated/invalid tool call) makes DeepSeek return HTTP 400 on every later request, and the harness's repair only handled unclosed turns at the log tail. Related: image conversions rejected by non-DeepSeek providers, plugin dependency hoisting breaking the tool pipeline, and (for any Chat-Completions client) the mandatory `reasoning_content` round-trip.

### Cited Findings
- Discussion #2900 (2026-08-17, dsh 0.1.0-rc.6, macOS, `deepseek-v4-flash`): tool execution crashed with `Cannot read properties of undefined (reading 'prepare')`, the turn closed "without a corresponding `tool/result`", and every later request failed with "An assistant message with 'tool_calls' must be followed by tool messages responding to each 'tool_call_id'" (HTTP 400 `INVALID_REQUEST`); root cause "The harness error path (`packages/core/agent-loop/src/agent.ts`) closes the turn on tool execution failure without synthesizing a `tool/result`… The existing repair mechanism (`interruptedTurnClosers`) only triggers when logs end with an unclosed turn"; the crash itself came from pnpm hoisting duplicate `@deepseek-ai/dsh-tools` copies; maintainer-side commenter mapped it as "mechanism #9 in the session-corruption family" and recommended a serialize-time pairing check — [discussion #2900](https://github.com/deepseek-ai/deepseek-harness/discussions/2900).
- Discussion #4843 (2026-08-28): "Incomplete or Orphaned tool_calls Records Cause DeepSeek API to Return 400" — errors "insufficient tool messages following tool_calls message", `tool_call_id` reference errors, and "Failed to parse the request body as JSON: messages[N].content: unexpected end of hex escape" (UTF-16 surrogate pair split by truncation); three gaps identified in `agent.ts`, `llm-deepseek/translate.ts` (empty-string fallback tool-call id) and compaction `tool-pairing.ts` (balances by count not callId); maintainer @liyangbing "acknowledged the core issue"; community workaround plugin `dsh-messages-sanitizer` "auto-repairs invalid tool_calls/tool message pairing… to stop 400 INVALID_REQUEST session crashes" — [discussion #4843](https://github.com/deepseek-ai/deepseek-harness/discussions/4843), [Leeminjing/dsh-messages-sanitizer](https://github.com/Leeminjing/dsh-messages-sanitizer).
- Discussion #4048 (2026-08-22, v0.1.1-rc.2, Windows): `read_image` converted PNG→WebP, LM Studio rejected it (`400 "'url' field must be a base64 encoded image."`), DSH "escalates this to a hard turn abort (`turn/end reason: "error"`) instead of returning a failed tool result", and the poisoned result replays on every resume; maintainer "Verified as genuine bug… member of 'sticky turn-end family' with related issues #3685, #2821, and #3552" — [discussion #4048](https://github.com/deepseek-ai/deepseek-harness/discussions/4048).
- Discussion #1697: "installing any plugin that depends on @deepseek-ai/dsh-tools breaks every tool call (Cannot read properties of undefined (reading 'prepare'))" — [discussion #1697](https://github.com/deepseek-ai/deepseek-harness/discussions/1697).
- Third-party troubleshooting sites claim that with `reasoningEffort` high/max "any turn that calls a tool can fail with a 400 INVALID_REQUEST error, and the session becomes permanently poisoned… a session captures it at creation and never re-reads it" and recommend `reasoningEffort: off` for tool-heavy work — [dshdocs.com/troubleshooting](https://dshdocs.com/troubleshooting/) (aggregator; not confirmed in a primary discussion I read).
- DeepSeek API-level quirks hitting other clients: claude-code-router #1378 — with V4 Pro/Flash "Multi-turn requests combining thinking mode with tool calls… subsequent assistant messages lack required reasoning fields, causing 400 errors on all follow-up turns"; all four user-space workarounds failed because "Tool-use code paths bypass transformer hooks" — [claude-code-router #1378](https://github.com/musistudio/claude-code-router/issues/1378). vercel/ai #10778 (Dec 2025, V3.2): "Missing `reasoning_content` field in the assistant message at message index 2", fixed by PR #10785 — [vercel/ai #10778](https://github.com/vercel/ai/issues/10778). Similar reports: [SillyTavern #4857](https://github.com/SillyTavern/SillyTavern/issues/4857), [n8n #22579](https://github.com/n8n-io/n8n/issues/22579) (from search results; not fetched).
- Loop/duplication guard exists because repeated identical tool calls happen: `repeat-tool-reminder` thresholds `[3, 5, 8]` (Q2).
- Windows: the base bundle swaps `tool-bash`/`bash-sandbox` for `tool-pwsh`/`pwsh-sandbox` when `process.platform === 'win32'`; the pwsh tool "runs in a fresh process (no persistent PTY session)"; CI has `check:ci:windows-*` gates and a `sandbox-windows-acl` backend — [base cordis.patch.yml](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/bundle/base/cordis.patch.yml), [tool-catalog.md](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/tool-catalog.md), [package.json](https://github.com/deepseek-ai/deepseek-harness/blob/master/package.json).

### Inferences
- Observation from this research (not a cited source): `git clone --depth 1` on Windows initially failed to check out part of `packages/` until `core.longpaths` was enabled — the repo has deep, long paths; expect the same when installing from source on Windows.
- For rolo-claude the actionable lessons are: (1) never let an assistant message with tool calls reach the log without a paired tool result — synthesize an error result on any crash/cancel (the harness now emits `ABORTED_BEFORE_DISPATCH` results on cancel); (2) validate `tool_calls` ↔ `tool` pairing and non-empty ids/names/valid JSON at serialize time; (3) make provider rejections of a tool *result* into `isError` tool results, not turn-level errors; (4) use `String.prototype.toWellFormed()` before JSON-serialising truncated tool output.

- Issue tracker is disabled, so there is no authoritative list of open bugs; discussions are user-triaged. I did not confirm whether the #2900/#4843 patches have landed in 0.1.7-rc.1.

## Q9. Context management, compaction and prompt-caching strategy

### Takeaway
Compaction is automatic at step boundaries when estimated tokens exceed 80% of (context window − reserved output − 65,536 headroom), retains the most recent ~16% of context, and produces a structured Markdown checkpoint through a one-shot call that **replays the conversation's own system prompt, tools and messages verbatim** (so the provider prefix cache is reused) followed by a final user message containing the compaction instruction; the checkpoint replaces the shadowed range as a `user/message`. Tool results are additionally pruned deterministically (head 4096/tail 1024 above 8192 chars), oversized tool output is spilled to files (12,500 inline-token cap), and images are offloaded.

### Cited Findings
- Policy defaults: `thresholdRatio` 0.8 "capped at context window minus reserved output and `headroomTokens`"; `headroomTokens` 65,536; `retainRatio` 0.16 (or `retainTokens`); `summarizationProvider`/`summarizationModel` (default: the conversation's route); `maxTokens` (defaults to headroom); `compactionRetries` 1; `maxOverflowRetries` 1; `auto` true; per-model overrides via `modelPolicies[{provider, model, …}]` — [config catalog `dsh-compaction-basic`](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/config-catalog.md).
- Mechanism: compaction "summary itself rides on a separate `user/message` with `surfaceOp: { op: 'replace', startSeq, endSeq }` — the only surface mutation performed by summary compaction"; log-only events `compaction/start`, `compaction/summary`, `compaction/end` bracket the operation — [docs/subsystems/compaction.md](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/compaction.md). "Summarize the replayed conversation region through a direct one-shot `ctx.llm.stream()` call whose prefix reuses the conversation's own system prompt, tools, and messages so the provider's KV cache is not invalidated" — [compaction-basic/src/index.ts](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/compaction/compaction-basic/src/index.ts). The request carries `purpose: 'compaction'` (which the DeepSeek adapter turns into header `x-deepseek-harness-compact: 1`) — [summarizer.ts](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/compaction/compaction-basic/src/summarizer.ts), [wire-extensions doc](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/deepseek-llm-api-wire-extensions.md).
- Compaction instruction (verbatim, appended as the final user message): "You are now acting as a compaction engine for this AI coding assistant. Condense the conversation ABOVE into a structured checkpoint that lets another model resume the work with no loss of essential context. / Output EXACTLY the Markdown structure below: keep every section, in order. Use terse bullets, not prose paragraphs. Write \"(none)\" for an empty section — never drop a section. / ## Primary Request and Intent / ## Key Technical Concepts / ## Files and Code / ## Errors and Fixes / ## Pending Jobs / ## Current Work / ## Next Step / ## Critical Context / Rules: - Write concise English engineering prose. Preserve exact file paths, commands, error strings, identifiers, numeric values, function signatures, and syntax fragments. - Capture user feedback and explicit instructions faithfully, especially corrections. - Do NOT mention this summarization request or that the context was compacted. - Output only the checkpoint text: do not call any tool or take any other action. - If the conversation already contains a <compacted-summary> block, it is a PRIOR checkpoint. Do not copy it forward verbatim: preserve still-true facts, drop stale ones, and merge newer information into a single consolidated summary under the same structure." The replacement message is framed as `CHECKPOINT_PREAMBLE` = "This is an automatically generated checkpoint condensing an earlier span of the conversation to free up context. Treat the captured context as established background and build on it without restating it. Continue the task directly from the messages that follow, without acknowledging this checkpoint." followed by `<compacted-summary>…</compacted-summary>` — [summarizer.ts](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/compaction/compaction-basic/src/summarizer.ts). A `max-tokens` finish is treated as failure ("summarization truncated at the token cap (incomplete checkpoint)") — same file.
- Tool-result pruner: `thresholdChars` 8192, `headChars` 4096, `tailChars` 1024 (Unicode code points) — [config catalog](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/config-catalog.md); spill policy `maxInlineTokens: 12500` — [base cordis.patch.yml](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/bundle/base/cordis.patch.yml); image offload via `compaction-image-offload` and provider `IMAGE_OFFLOAD_REQUIRED` — [docs/subsystems/llm-streaming.md](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/llm-streaming.md).
- KV-cache discipline (documented per package under "KV Cache effect"): system prompt is "Prefix-stable while identity, persona, variables, section text, and order render identically"; with `systemPromptUpdate: 'in-history'` "the agent loop appends a non-empty changed prompt after the cached history inside a continuing request series, so the prefix through that history stays reusable"; "Registration, restriction, or reordering [of tools] may invalidate reuse from the first changed schema token"; plan mode keeps "The tool catalog… the same across modes for request-cache stability" — [system-prompt README](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/core/system-prompt/README.md), [agent-loop README](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/core/agent-loop/README.md), [base cordis.patch.yml](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/bundle/base/cordis.patch.yml).
- Manual compaction: `/compact` command; token accounting via `dsh-token-meter` — [command-compact](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/compaction/command-compact/src/index.ts).

### Inferences
- The "replay the exact prefix, then ask for a checkpoint" design is the cheapest possible compaction on DeepSeek's automatic prefix cache (only the instruction is a cache miss). rolo-claude can adopt the same section template and preamble.

### Gaps
- The exact token estimator (`dsh-token-meter`) algorithm was not examined.

## Q10. Streaming, UI surfaces and session persistence details

### Takeaway

## Q11. Pointing this harness at Databricks / other OpenAI-compatible endpoints

### Takeaway
Yes: the `dsh-llm-pi-ai` adapter's "Custom model API" route takes a lowercase provider id, `baseURL`, `api` protocol (`openai-completions` | `openai-responses` | `anthropic-messages`), an `apiKeyEnv` credential reference (sent as a bearer token by pi-ai's OpenAI-compatible client), optional `headers`, and a hand-declared `models` list — which maps directly onto Databricks' OpenAI-compatible `https://<workspace>/serving-endpoints` base (model = endpoint name) or the AI Gateway `https://<workspace>/ai-gateway/mlflow/v1` base. The native `deepseek-official` adapter cannot be used for Databricks because it speaks the Anthropic Messages format. Expect to set `compat` switches (`supportsDeveloperRole: false`, `maxTokensField: max_tokens`, `thinkingFormat: deepseek`, possibly `requiresReasoningContentOnAssistantMessages: true`, `supportsUsageInStreaming`, `supportsStore: false`) and to enter model ids by hand; reasoning passthrough through Databricks' gateway is only partially characterised.

- Repo confirmation: `https://github.com/deepseek-ai/deepseek-harness` — 234,451 stars, 28,178 forks, last push 2026-09-23T13:30:24Z, HEAD `46a7f68` (PR #5073), prereleases every 1–3 days (see Q1) — [GitHub API](https://api.github.com/repos/deepseek-ai/deepseek-harness), [releases](https://github.com/deepseek-ai/deepseek-harness/releases).

### Inferences
- Concrete Databricks recipe for dsh (derived from the cited config surface; untested): in `$DSH_HOME/profiles/web/cordis.patch.yml` add
  ```yaml
  - id: llm-pi-ai
    config:
      providers:
        databricks:
          displayName: Databricks
          apiKeyEnv: DATABRICKS_TOKEN
          api: openai-completions
          baseURL: https://<workspace>/serving-endpoints      # or https://<workspace>/ai-gateway/mlflow/v1
          compat:
            supportsDeveloperRole: false
            maxTokensField: max_tokens
            supportsStore: false
          models:
            - id: <endpoint-name>            # Databricks: model == serving endpoint name
              contextWindow: 131072
              maxTokens: 32768
              compat:
                thinkingFormat: deepseek
                requiresReasoningContentOnAssistantMessages: true
              reasoningEfforts:
                off:
                high: high
                max: max
  ```
  then export `DATABRICKS_TOKEN` (PAT or OAuth token; pi-ai's OpenAI-compatible client sends it as `Authorization: Bearer …`), select `databricks / <endpoint-name>` in Settings → Models, and disable telemetry (`DSH_TELEMETRY_DISABLED=1`). If the pay-per-token endpoint does not implement `GET /models`, skip "Fetch available models" and type the id.
- Risks specific to DeepSeek-on-Databricks: (a) Databricks strips or reshapes `reasoning_content` on the way back (litellm needed a fix just to *read* it) — if the gateway does not forward `reasoning_content` on *replayed* assistant messages to DeepSeek, thinking-mode tool calls will 400 exactly as in claude-code-router #1378; mitigation is `reasoningEfforts.off` / `thinkingFormat: deepseek` with `off` for tool-heavy work, or `requiresThinkingAsText`; (b) `stream_options.include_usage` and `finish_reason` behaviour of the gateway are unknown — set `supportsUsageInStreaming`/`supportsFinishReason` if streams end without usage or finish reason; (c) DeepSeek's automatic prefix cache is only observable through DeepSeek's own usage fields; behind Databricks the harness will show no cache hits.
- For rolo-claude (which speaks Chat Completions): the pi-ai compat matrix above is the checklist of "gateway knobs" a DeepSeek-through-gateway client must expose: system-vs-developer role, `max_tokens` vs `max_completion_tokens`, `reasoning_effort` acceptance, `thinking` object format, `reasoning_content` replay (real text vs empty string vs `<thinking>` text), `stream_options`, `store`, `strict`, tool-result `name`.
