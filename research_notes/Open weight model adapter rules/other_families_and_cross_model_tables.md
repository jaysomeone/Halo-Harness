## KQ1a. Adapter facts: Llama 4 (Maverick/Scout), Llama 3.x, Gemma 3 / Gemma 4

### Takeaway
Llama 4 and Llama 3.3 emit tool calls as either a Python list `[f(a=1)]` or a JSON list; Meta says 3.3/4 support parallel calls natively but vLLM's `llama3_json` parser still documents "parallel tool calls not supported in Llama 3", and Databricks says its Llama 4 endpoint is single-turn-optimised. Gemma 3 has *no* system role and *no* tool tokens (prompt-emulated ```tool_code```), while Gemma 4 adds a real `system` role, `<|tool_call>` / `<|tool_response>` tokens and a `<|channel>thought` thinking channel with a strip-prior-thoughts rule that has a tool-calling exception; both Gemma generations sample at temperature 1.0 / top_k 64 / top_p 0.95.

### Inferences
- Llama 3.3 / 4 tool-call *strings* are plain-text JSON or Python lists; a harness receiving raw text (an OpenAI-compatible server without `--enable-auto-tool-choice`) must parse leaked `[{"name":..,"parameters":..}]` / `[f(a=1)]` forms; on OpenRouter/Databricks this is server-side, but the "arrays as strings" argument quirk is provider-independent.
- For Gemma 3, "tools supported" on OpenRouter/LiteLLM must be provider-side prompt emulation (the model has no tool tokens or tool role); expect lower reliability than Gemma 4 and treat `tool_choice: required` as best-effort.
- `system_placement`: Gemma 3 = fold into first user turn (Aider `use_system_prompt: false` and LiteLLM `supports_system_messages: false` encode this); Gemma 4 = real system turn.
- Databricks' "single turn optimised" / "no parallel calls" notes mean a Claude-Code-style loop on `databricks-llama-4-maverick` should tell the model one call per turn and never send `parallel_tool_calls`.

### Gaps
- Meta's `generation_config.json` for Llama 3.3 / Llama 4 is gated (HTTP 401), so the commonly quoted temperature 0.6 / top_p 0.9 default could not be verified from the primary file.
- No Meta, vLLM or Databricks page gives an exact context-overflow error string for Llama on Databricks.
- The Gemma 3 `generation_config.json` is gated; sampling values come from HF discussions attributed to the Gemma team.

## KQ1b. Adapter facts: Mistral (Devstral 2, Mistral Medium 3.5 / Large 3, Codestral, Magistral) and OpenAI gpt-oss-120b/20b

### Takeaway
Mistral's hard, non-negotiable rule is the tool-call id: exactly nine `[a-zA-Z0-9]` characters, enforced by the API (and through OpenRouter), so every harness normalises ids before replay; its reasoning models now expose `reasoning_effort` (`none`/`high`) and return a `ThinkChunk` (`type: "thinking"`) that must be replayed verbatim, while the open Magistral weights use literal `[THINK]…[/THINK]` tokens. gpt-oss is a harmony-format model: `analysis`/`commentary`/`final` channels, `Reasoning: low|medium|high` set in the *system* message, reasoning effort exposed as `reasoning_effort` on every host, prior-turn analysis dropped unless the last assistant turn was a tool call, and OpenAI recommends temperature 1.0 / top_p 1.0.

### Cited Findings — Mistral API rules (all Mistral models)
- `tool_choice`: `"auto"` ("default mode. Model decides if it uses the tool or not"), `"any"` ("forces tool use"), `"none"` ("prevents tool use"); `parallel_tool_calls: true` is "default mode. The model decides if it uses parallel tool calls or not", `false` "forces the model to use single tool calling"; the docs' example tool-call id is `"D681PevKs"` (9 chars); function calling is listed for Mistral Large 3, Mistral Medium 3.5, Mistral Small 3.2, Devstral 2.0, Codestral, Magistral, Ministral 3 (14B/8B/3B) — [Mistral function calling](https://docs.mistral.ai/capabilities/function_calling)
- Tool-call id validation error, verbatim from the API: `Tool call id was 2968-LWy3uasib but must be a-z, A-Z, 0-9, with a length of 9`; the same failure is reported for `call_0fypS1hVX`-style OpenAI ids and for Anthropic-style ids, and it also surfaces when Mistral models are routed via OpenRouter ("invalid_function_call code 3280") — [eca issue #233](https://github.com/editor-code-assistant/eca/issues/233); [gptel issue #1203](https://github.com/karthink/gptel/issues/1203); [zed issue #53034](https://github.com/zed-industries/zed/issues/53034); [openclaw issue #52548](https://github.com/openclaw/openclaw/issues/52548); [vercel/ai issue #11802](https://github.com/vercel/ai/issues/11802)
- vLLM states the same constraint for local serving: "Mistral's tokenizer requires tool call IDs that are exactly 9 digits"; parser `mistral`, templates `examples/tool_chat_template_mistral.jinja` or `tool_chat_template_mistral_parallel.jinja` ("adds a tool-use system prompt when tools are provided, that results in much better reliability when working with parallel tool calling"); "Mistral 7B struggles to generate parallel tool calls correctly"; HF-format flags `--tokenizer_mode hf --config_format hf --load_format hf --tool-call-parser mistral --chat-template examples/tool_chat_template_mistral_parallel.jinja` — [vLLM tool calling docs](https://docs.vllm.ai/en/latest/features/tool_calling.html)

- Roo's OpenRouter handler passes `normalizeToolCallId: normalizeMistralToolCallId` whenever `modelId.toLowerCase().includes("mistral")` ("Mistral compatibility (requires 9-char alphanumeric IDs)") — [Roo openrouter.ts](https://github.com/RooCodeInc/Roo-Code/blob/main/src/api/providers/openrouter.ts)

### Inferences
- Mistral's 9-char id rule cannot be data-driven by a boolean alone: a harness needs a deterministic id-rewrite that is applied symmetrically to `tool_calls[].id` and `tool` message `tool_call_id` (OpenCode's scrub+pad and Roo's `normalizeMistralToolCallId` are two working shapes). A `tool_id_format: "alnum9"` field plus one code branch is enough.
- Mistral "prepend system to last user turn" is a *template* behaviour of open weights; the hosted API accepts a leading `system` message normally, so `system_placement: "first"` is correct for OpenRouter/Databricks-hosted Mistral and only self-hosted mistral-common templates reorder it.
- gpt-oss `reasoning_effort` is the only reasoning control; there is no on/off toggle (OpenRouter marks it `mandatory:true`), so `thinking_toggle: "effort-only"`; the analysis channel must not be replayed as `reasoning_content` to Groq-backed endpoints — replay rule "drop unless last assistant turn was a tool call" comes from the harmony spec itself.
- Because OpenRouter has dropped the `devstral`/`magistral` ids (and models.dev marks Devstral `deprecated`), a 2026 harness should pin Devstral 2 to Mistral's own API (`devstral-medium-latest` / `devstral-2512`) or self-host; `mistralai/mistral-medium-3-5` is the OpenRouter-visible reasoning-capable Mistral.

### Gaps
- Mistral's public docs do not state the 9-char id rule; the constraint is verified only via the API's error string (multiple independent issue reports) and vLLM's note.
- Whether Mistral's API accepts `tool_choice: "required"` as an alias of `"any"` is not stated on the function-calling page (only `auto`/`any`/`none` are documented).
- No Mistral page gives the verbatim context-overflow message; only "400 Bad Request" is documented.
- OpenAI publishes no `max_output` for gpt-oss; host caps differ (OpenRouter 65536 / 32768, Databricks-LiteLLM 131072, models.dev-Databricks 32768, Cerebras 40960).

## KQ1c. Adapter facts: xAI Grok 4.x, NVIDIA Nemotron 3, Google Gemini 3.x (thought signatures), plus the serving-stack parser inventory

### Takeaway
Grok 4.5+ reasoning "cannot be disabled" and defaults to `reasoning_effort: "high"`; grok-4.7 additionally returns `reasoning.encrypted_content` on every response which must be passed back unchanged — so Grok needs opaque-reasoning replay just like Gemini. ### Inferences
- `reasoning_replay` for Grok: on the Responses API pass `reasoning.encrypted_content` items back verbatim; through OpenRouter chat-completions, pass `reasoning_details` back unmodified (same mechanism as Gemini). Grok 4.7's "encrypted on every response" makes it structurally identical to Gemini 3 for the harness: opaque blob per assistant turn, must round-trip.
- For Nemotron 3 the adapter can reuse the Qwen3 tool parser and the Qwen-style `enable_thinking` chat-template kwarg; the per-model difference is the reasoning parser name (`nemotron_v3` vs Nano's documented `nano_v3`) and the two sampling profiles keyed on thinking state.
- Gemini 3's rule "signature only on first parallel call" means a harness that reorders or splits parallel tool calls will break validation; keep assistant turns atomic and keep `extra_content` attached to `tool_calls[0]`.
- Because OpenRouter exposes Gemini signatures as `reasoning.encrypted` blocks keyed by the first tool-call id, the Roo sentinel-injection trick is the only known way to *switch* into Gemini mid-conversation; a harness should record which turns carry real vs sentinel signatures.

### Gaps
- xAI docs give no default temperature and no exact context-overflow string for Grok 4.x; the only verbatim overflow text found is from the Grok 3 era.
- The Nemotron 3 Super/Ultra model cards are gated, so their recommended sampling comes from vLLM blog examples rather than NVIDIA's `generation_config.json`.
- Google's thought-signature page does not state how signatures interact with OpenRouter's `reasoning_details`; that mapping is documented only by OpenRouter and Roo's code comments.
- Databricks' Gemini endpoints: no page states whether thought signatures are surfaced or required through the Databricks OpenAI-compatible layer.

## KQ2. The cross-model tables: schemas and representative rows (Aider, models.dev, LiteLLM, Cline, Roo, Kilo, Continue, OpenCode)

### Takeaway
Six mature tables exist and they only agree on a small core — a tool-calling boolean, a reasoning boolean, a vision/attachment boolean, context and max-output limits, and prices. Everything that actually drives an agent loop (reasoning replay, temperature policy, tool-id shape, effort vocabularies, system-role placement) is either a per-table extension (models.dev `reasoning_options`/`interleaved`, OpenRouter `reasoning`/`default_parameters`, Roo `preserveReasoning`/`defaultTemperature`, Aider `use_temperature`/`reasoning_tag`) or lives in code.

## KQ3. How the harnesses SELECT behaviour per model at runtime (capability flags → prompt variant, tool protocol, temperature, reasoning replay)

### Takeaway
All four code bases resolve behaviour in the same order — (1) exact-id table row, (2) substring/regex rules on the model id, (3) provider-wide defaults — and every one of them still keeps hand-written id-substring branches for the things the tables cannot express (Gemini signatures, Mistral ids, DeepSeek/Kimi replay, Qwen `/no_think`, Gemma thinking toggles).

### Cited Findings
- Aider: `Model.__init__` applies `configure_model_settings()`, which first calls `apply_generic_model_settings(model)` — a chain of substring tests on the id (`"/o3-mini" in model`, `"deepseek" in model and "v3" in model`, `"deepseek" in model and ("r1" in model or "reasoning" in model)` → `use_temperature=False; reasoning_tag="think"`, `("llama3" in model or "llama-3" in model) and "70b" in model`, `"qwq" in model and "32b"` → `use_temperature=0.6; extra_params=dict(top_p=0.95)`, `"qwen3" in model and "235b"` → `system_prompt_prefix="/no_think"; use_temperature=0.7; extra_params={"top_p":0.8,"top_k":20,"min_p":0.0}`) — then explicit YAML rows override; `set_thinking_tokens()` forces `use_temperature=False`; `send_completion()` sends `temperature=0` when `use_temperature` is `True`, `float(use_temperature)` when numeric, and omits it when `False`; `is_deepseek_r1()` = `"r1" in name or "reasoner" in name`; reasoning text is stripped via `remove_reasoning_content(res, self.reasoning_tag)` — [aider/models.py](https://github.com/Aider-AI/aider/blob/main/aider/models.py)
- Roo: `getModelParams({format, modelId, model, settings, defaultTemperature})` computes `temperature = customTemperature ?? model.defaultTemperature ?? defaultTemperature`; if `shouldUseReasoningBudget` (`!!model.requiredReasoningBudget || (!!model.supportsReasoningBudget && !!settings?.enableReasoningEffort)`) it sets a budget clamped to ≤ 80 % of `maxTokens` and ≥ 1024 (128 for `gemini-2.5-pro`) and **forces `temperature = 1.0`** ("Let's assume that 'Hybrid' reasoning models require a temperature of 1.0 since Anthropic does"); else if `shouldUseReasoningEffort` it propagates `settings.reasoningEffort ?? model.reasoningEffort` unless `"disable"`; hard-coded exceptions: ids starting `o1`/`o3-mini` and `openai/o1-pro` get `temperature = undefined`; the result is then shaped per wire `format: "anthropic"|"openai"|"gemini"|"openrouter"` by `getAnthropicReasoning`/`getOpenAiReasoning`/`getGeminiReasoning`/`getOpenRouterReasoning` — [Roo model-params.ts](https://github.com/RooCodeInc/Roo-Code/blob/main/src/api/transform/model-params.ts); [Roo shared/api.ts](https://github.com/RooCodeInc/Roo-Code/blob/main/src/shared/api.ts)
- Roo OpenRouter handler: `defaultTemperature: isDeepSeekR1 ? DEEP_SEEK_DEFAULT_TEMPERATURE : 0` (i.e. 0.3 for R1, **0** otherwise); `deepseek/deepseek-r1*` and `perplexity/sonar-reasoning` are converted with `convertToR1Format([{ role: "user", content: systemPrompt }, ...messages])` ("DeepSeek highly recommends using user instead of system role"); Gemini ids get `sanitizeGeminiMessages` + sentinel `reasoning.encrypted` injection; Mistral ids get tool-id normalisation; `reasoning_details` from the stream are accumulated and stored back on the assistant message "to prevent malformed responses" — [Roo openrouter.ts](https://github.com/RooCodeInc/Roo-Code/blob/main/src/api/providers/openrouter.ts)
- OpenCode: capabilities come from models.dev (`toolcall: model.tool_call ?? true`, `interleaved.field`), sampling from id regexes — `temperature()`: `claude` → undefined; Gemini matching `gemini-2.5`, `gemini-3-(flash|pro)`, `gemini-3.1`, `gemini-3.5-flash` (not lite) → 1.0 else undefined; `glm-4.6`/`glm-4.7` → 1.0; `minimax-m2` → 1.0; `kimi-k2` → 1.0 when id contains `thinking|k2.|k2p|k2-5` else 0.6; `north-mini-code` → 1.0; `topP()`: Gemini → 0.95, `minimax-m2|kimi-k2.5` → 0.95, `deepseek-v4-flash` on DeepSeek/opencode providers → 0.95; `topK()`: `minimax-m2` → 40 (m2.x) / 20, Gemini → 64; reasoning "variants" are built per SDK package (`@openrouter/ai-sdk-provider` → `reasoning: { effort }`, `@ai-sdk/openai-compatible` → `reasoningEffort`, Google → `thinkingConfig.thinkingLevel` or `thinkingBudget` (2.5), Anthropic → `thinking`), with special cases for `glm-5.2` (`high|xhigh` via OpenRouter, `high|max` via openai-compatible), Kimi Anthropic-compatible `thinking: {type:"adaptive", display:"summarized"}`, and a `chat_template_kwargs: { thinking_mode: "enabled"|"disabled" }` variant; message transforms: DeepSeek — "requires all assistant messages to have reasoning on them" (empty reasoning part injected), `interleaved.field` → the reasoning text is re-emitted as `reasoning_content` or `reasoning_details` on every assistant message ("Always set the field even when empty"); Mistral family → id scrub + `"Done."` bridging; Anthropic → signature checks — [opencode transform.ts](https://github.com/anomalyco/opencode/blob/dev/packages/opencode/src/provider/transform.ts); [opencode provider.ts](https://github.com/anomalyco/opencode/blob/dev/packages/opencode/src/provider/provider.ts)
- Cline: routing keys are `apiFormat` (`default | openai-responses | r1`), `apiProtocol` metadata (`openai-chat | openai-responses | anthropic | gemini`), `systemRole` (`developer | system`) and the SDK `capabilities` list, with the explicit rule that a missing list "fail[s] open" — [Cline api.ts](https://github.com/cline/cline/blob/main/apps/vscode/src/shared/api.ts); [Cline model-info.ts](https://github.com/cline/cline/blob/main/sdk/packages/shared/src/llms/model-info.ts)
- Continue: "Continue automatically detects these capabilities for most models" (by model name) and lets `capabilities: [tool_use, image_input]` override — [Continue reference](https://docs.continue.dev/reference)
- vLLM/SGLang side: behaviour is selected by server flags, not by the client — `--tool-call-parser <name>`, `--reasoning-parser <name>`, `--chat-template`, `--enable-auto-tool-choice`; the client only sees OpenAI-shaped `tool_calls` / `reasoning_content` if the operator chose the right parser — [vLLM tool calling docs](https://docs.vllm.ai/en/latest/features/tool_calling.html)

### Inferences
- The selection pipeline every harness converges on is: `row = table[id] ⊕ regexRules(id) ⊕ providerDefaults(provider)`; then `wire = protocol(provider)`; then `preSend(messages)` branches keyed on family for id-rewrite / reasoning replay / system folding; then `postReceive` branches for leaked tags and reasoning fields. A `model_table.json` can carry the first two stages fully and *name* the branches for the last two (`quirks[]` / `pre_send_hooks[]`), but the hook bodies stay in code.
- Roo's "hybrid reasoning ⇒ temperature 1.0" and OpenCode's per-family 1.0/0.95/64 defaults show that the *thinking state* changes the sampling profile; the table needs sampling defaults per `thinking_on` and `thinking_off` (Nemotron's 1.0/1.0 vs 0.6/0.95 is the clearest published case).

### Gaps
- Cline's actual per-provider handlers (e.g. how `r1` apiFormat rewrites messages) live under `apps/vscode/src/core/api/` and were not read; only the schema was.
- OpenCode's `session/llm.ts` shows `temperature/topP/topK` and `providerOptions` being passed, but the code that decides whether to send `tools` when `toolcall` is false was not located in the grep.

## KQ4. Where the mature tables agree, what needs code branches, shipped defaults, and disagreements

### Takeaway

### Inferences
- The "0.3 vs omit" style disputes are really disputes about *who owns the default*: Aider assumes the harness owns it (0), OpenCode assumes the provider owns it (omit unless a family is whitelisted), Roo assumes the model row owns it (`defaultTemperature`, else 0 / 1.0 for budget-thinking). A superset schema should carry `temperature: {mode: "omit"|"fixed"|"provider_default", value}` per thinking state rather than a bare number.

### Runtime selection this schema implies (mirrors Aider/Roo/OpenCode)
1. Resolve `row = table[id] ⊕ family_regex_defaults(id) ⊕ provider_defaults(provider)` (Aider `apply_generic_model_settings` → YAML; Roo `model.defaultTemperature ?? defaultTemperature`; OpenCode models.dev → capabilities).
2. Choose wire: `api_protocol` (+ `api_format` for R1-style role rewriting) and the reasoning parameter shape by SDK/provider (OpenCode `variants()`), gating `effort_values` by `reasoning_mandatory`/`reasoning_default_on`.
3. Pick `sampling.thinking_on|off` from the resolved thinking state; `mode: omit` sends nothing (OpenCode default), `provider_default` sends OpenRouter `default_parameters`, `fixed` sends the row value (Roo/Aider style).
4. Run `hooks.pre_send` (id rewrite, signature/sentinel injection, reasoning echo/strip, system folding, message-sequence repair) and `hooks.post_receive` (leak parsing via `tool_leak_patterns`, `reasoning_tag` stripping, signature capture).
5. On error, match `overflow_error_regex[host]` and apply `overflow_recovery`.
