# Halo 2.0.8 brief: remote control of sessions from Signal (approved by rolo 2026-10-02)

(The 2.0.1 / 2.0.2 plan approved earlier today is recorded in the repo under
`plans/2.0.2-brief.md`, `plans/ROADMAP.md` and `plans/HANDOFF.md`; W4a is
executing. This plan adds 2.0.8 to that roadmap.)

## Context

rolo (2026-10-02, `/plan`): "for 2.0.8 add a remote-control feature that is
highly encrypted that allows a user to control their sessions from Signal."
Claude Code's own Remote Control drives a local session from the claude.ai
app through Anthropic's relay. Halo's version is self-hosted and reaches the
user where they already are, in Signal on their phone: read what a session
is doing, send it prompts and steers, answer its permission cards, switch
model or effort, interrupt it, and pick which session to drive, with nothing
leaving the user's own devices except Signal's end-to-end-encrypted traffic.

Facts verified during planning: a running session is already driven by a
command queue (`halo_harness/events.py` `Command` kinds `user_input`,
`interrupt`, `set_mode`, `set_model`, `slash`, `permission_reply`,
`question_reply`, `plan_reply`, `steer`, `run_compact`, `run_clear`) behind
`halo_harness/controller.py` (`submit`, `interrupt`, `set_permission_mode`,
`set_model`, `answer_permission`, `answer_question`, `answer_plan`,
`run_slash`, `list_models`, `list_sessions`, `resume`, `mcp_status`), so the
bridge needs no new session semantics, only a transport into that queue and
out of the event stream. Print mode already consumes a line-based command
stream (`headless.py`, `--input-format stream-json`). The `cc:` route
already runs a per-session local socket under `~/.halo/run/<id>.sock` for
its own bridge, the pattern a control socket reuses. The W3a pending-card
queue and the W2b phase events give the bridge the exact state to relay
(needs-you cards, phase line, status). No crypto or keyring dependency
exists in the tree today.

## Design

### 1. Transport: Signal through signal-cli, self-hosted

- `signal-cli` (the maintained Java/GraalVM client with a JSON-RPC daemon
  mode) is the only practical way to send and receive Signal messages from
  a program; Halo talks to it over its JSON-RPC socket, never over D-Bus.
  Halo ships no Signal keys itself; `halo remote signal setup` installs or
  locates `signal-cli` (native build on Linux x86_64, JRE path otherwise),
  stores nothing outside `~/.halo/remote/`, and `halo doctor` checks it.
- **Both identity models ship, dedicated number first** (rolo's choice).
  Default and recommended: a dedicated Signal number for Halo (a second
  SIM, eSIM or VoIP number registered through `signal-cli register` with
  the captcha flow), so the Halo device only ever sees messages sent to
  that number, and the user messages it from their own Signal. Documented
  alternative: linking Halo as a secondary device of the user's own account
  (`signal-cli link` with a QR), driven through "Note to Self"; because a
  linked device receives the account's entire message stream, this mode
  filters to self-messages only, never persists or relays anything else,
  and the setup text says so plainly. `halo remote signal setup` asks which
  model to use and walks through the matching flow.

### 2. Security layers ("highly encrypted", defense in depth)

1. Signal's own end-to-end encryption between the phone and the Halo
   number (Signal protocol, forward secrecy).
2. **Pairing and identity pinning**: the first message from a sender is
   answered with a one-time pairing code shown in the Halo TUI (`/remote`)
   and on the CLI; only after the user types that code back is the sender's
   Signal identity (ACI plus the current safety number) written to
   `~/.halo/remote/peers.json`; any later safety-number change is refused
   with a notice in both places until re-verified; one or several allowed
   peers, nobody else is ever answered.
3. **Command signing inside the message**: after pairing, Halo and the
   phone share a 256-bit secret shown once as a QR and a short phrase; each
   command carries `#<counter>:<hmac-sha256 prefix>` which the bridge checks
   (stdlib `hmac`, no new dependency), with a monotonic counter and a 5-minute
   timestamp window for replay protection. Users who want zero friction can
   turn signing off per peer (`signed: false`), keeping layers 1 and 2.
4. **At rest**: the shared secret and the signal-cli data directory live
   under `~/.halo/remote/` with 0600/0700 permissions; the OS keyring is
   used when available (optional `keyring` import, never required); no
   message content is logged, only a hashed audit line per command in
   `~/.halo/remote/audit.jsonl`; transcript relays are not stored by the
   bridge.
5. **Local control socket**: the session's control socket is a Unix socket
   or Windows named pipe owned by the user with a per-session token; the
   bridge is the only client; nothing listens on TCP.
6. Rate limiting per peer (commands per minute) and an explicit `/remote
   off` kill switch in the TUI. No safety or refusal logic anywhere: an
   authenticated owner can do everything they could do at the keyboard.

### 3. Session control surface (`halo_harness/remote/`)

- `remote/control_socket.py`: every TUI and print-mode session optionally
  (config `remote.enabled`) opens `~/.halo/run/<session>.ctl` and registers
  itself in `~/.halo/run/sessions.json`; the socket speaks newline JSON:
  `{"cmd": "status"|"submit"|"steer"|"interrupt"|"answer"|"model"|"effort"|
  "mode"|"slash"|"tail", ...}` mapped one-to-one onto `Controller` methods,
  and an event feed (`subscribe`) that forwards `phase`, `text_delta`
  summaries, `message_end`, `permission_request`, `question`, `plan_review`,
  `turn_done` from the existing event stream.
- `remote/signal_transport.py`: the signal-cli JSON-RPC client (receive
  loop, send, attachments optional), reconnect with backoff.
- `remote/bridge.py`: the daemon `halo remote signal run` that pairs peers,
  verifies signatures, routes commands to the attached session, and
  renders replies: Markdown flattened to plain text, long outputs chunked
  at Signal's limit, streaming coalesced into one message per few seconds,
  permission cards rendered as numbered choices (`1` allow once, `2`
  session, `3` always, `4` deny), questions as lettered options, plan
  reviews as approve / feedback.
- Chat commands from the phone: plain text = a prompt (or a steer while a
  turn runs); `/sessions`, `/attach <n>`, `/status`, `/stop`, `/mode
  <name>`, `/model <ref>`, `/effort <level>`, `/quiet` and `/loud` (relay
  verbosity), `/tail <n>`, `/remote pair`, `/remote unpair`, plus any Halo
  slash command passed through.
- TUI side: `/remote` shows the bridge state, peers, pairing code and the
  kill switch; a `⇄ remote` chip in the status bar while a peer is attached;
  commands arriving from Signal appear in the transcript tagged
  `(from Signal)`.
- CLI: `halo remote signal setup|link|register|run|pair|peers|unpair|
  status`, with `halo remote signal run --daemon` for a systemd/launchd
  unit the setup command can write.

### 4. Research round first

signal-cli's current JSON-RPC surface and daemon flags, registration and
captcha flow, linking flow, rate limits, native builds per OS, the Signal
message size limit, how safety numbers are exposed, and whether Windows
needs the JRE path only; documented in `docs/harness/SIGNAL-RESEARCH.md`
with URLs, then the design above is adjusted before implementation.

### 5. Rounds (one worker on the tree at a time)

1. Research (docs only).
2. Control socket + sessions registry + print-mode and TUI wiring, with a
   fake client test (every command kind round-trips; token required; the
   feed delivers a permission card and accepts its answer).
3. Signal transport + bridge + pairing + signing + rendering, tested
   against a fake signal-cli JSON-RPC server (receive, send, reconnect,
   pairing, safety-number change refusal, replay rejection, rate limit).
4. CLI, TUI `/remote`, status chip, doctor check, docs (`docs/REMOTE.md`:
   threat model, the two identity models, setup per OS, the chat command
   list), CHANGELOG, release.

## Verification

- Hermetic: the three suites on Windows, WSL and Kali plus the new fake
  signal-cli and fake control-socket tests; a test proves no message
  content reaches any log or file; a test proves an unknown sender is never
  answered and a changed safety number is refused.
- Live on the Kali VM with a dedicated test number: pair from rolo's
  phone, `/sessions`, attach, send a prompt, receive the streamed reply,
  answer a permission card from the phone, `/stop`, unpair; the same from
  a second phone must be ignored.
- Release: Opus review of the remote package with the threat model in
  hand, fix pass, tag.

## Research addendum (2026-10-02, docs/harness/SIGNAL-RESEARCH.md)

- signal-cli v0.14.8 (2026-09-10): JSON-RPC over `daemon --socket` (Unix
  socket), `--tcp` or `--http` (`/api/v1/rpc`, `/api/v1/events` SSE);
  GraalVM native build is Linux-only, Windows and macOS use the JVM build
  (JRE 25); the notification JSON shapes are taken from the source
  (`JsonMessageEnvelope`, `JsonDataMessage`, `JsonSyncDataMessage`).
- Run signal-cli with `--trust-new-identities=never` so the bridge owns the
  pin and refuse decision; exit code 4 is the "untrusted or changed key"
  signal; registration uses the captcha flow with rate-limit exit code 5
  and `submitRateLimitChallenge`; linking is `link`/`addDevice` with a
  5-device cap; Note to Self is a sync message addressed to self.
- Open questions for round 2: the message-length and attachment caps (only
  the long-text-as-attachment mechanism is documented), proxy support for
  a work VM (no documented `--proxy` flag), and the nine hands-on questions
  in the research doc's section 7.
