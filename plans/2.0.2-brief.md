## 2.0.2 design

### A. Roles v2 (`halo_harness/roles.py`, `config/agents_md.py`, `agent/loop.py`, `commands/builtins.py`, `tui/slash.py`, `tui/completion.py`, `roles_cli` or `cli.py`)

- `ROLE_NAMES` becomes `("orchestrator", "planner", "coder", "reviewer",
  "judge", "researcher", "tester", "compaction", "small", "subagent_default")`:
  the screenshot's three additions plus `judge` (adjudicates candidate
  outputs or verifies results against acceptance criteria and returns
  pass/fail with reasons; used by organization flows and `Agent(role="judge")`)
  and `tester` (runs suites and live checks and reports). Wiring per the
  screenshot: Plan agent → `planner`; `compaction` as the rung after
  `compactionModel`; `subagent_default` as the last rung before the
  session model. Built-in agent → role map in `config/agents_md.py` gains
  `Judge`, `Tester`.
- Per-role effort: `roles.<name>` accepts `{model, effort}` (a bare string
  stays a model); the effort is resolved through `providers/effort.py`
  (`effort_set(route)`, `sent_effort`) so each role shows the level its
  route actually accepts, as `requested (sent as X)`; `/roles` and
  `stats --roles` show model, effort sent, price.
- Custom role names: a template or team.json may define roles beyond the
  built-ins (any `[a-z][a-z0-9_]*`); `Agent(role=...)`, `--role NAME=MODEL`
  and frontmatter `role:` accept them; unknown names error with the list.
- Tab completion in the TUI: `/role <name> <model> [effort]` and
  `/roles set <name> <model> [effort]` complete role names, then model refs
  from the same enumerated catalog the picker uses
  (`controller.list_models()`, prefix and substring ranking from
  `tui/completion.py::filter_items`), then the effort levels valid for that
  model (`effort_set`). Shell completion: `halo completion bash|zsh|powershell`
  prints a script completing subcommands, role names and cached model refs.
- Templates: `~/.halo/roles/<name>.json` `{name, description, roles:
  {role: {model, effort}}}`; `/roles templates`, `/roles save <name>`,
  `/roles load <name>`, `/roles new <name>` and `/roles edit <name>` (a
  TUI form: one row per role with a model picker and an effort selector,
  or `$EDITOR` when configured); CLI `halo roles template list|save|load|
  new|edit|show`. Precedence: CLI `--role` > loaded template > team.json >
  session model (documented in `docs/ROLES.md`).

### B. Organizations (`halo_harness/orgs.py`, `tui/dialogs/org_editor.py`, `commands/builtins.py`, `agent/subagent.py`, `docs/ORGS.md`)

- An organization is a tree of positions, each a role assignment:
  `~/.halo/orgs/<name>.json` `{name, description, positions: [{title,
  role|model, effort, instructions, tools?, reports: [...]}]}`, for example
  CEO → VP Engineering / VP Marketing / VP Research → managers → workers.
  `/org list|show|new|edit|load|run`, CLI `halo org ...`; the editor is the
  same form family as the roles template editor (add/remove positions,
  pick model, effort, write the position's instruction paragraph).
- Running one: `/org run <name> "<goal>"` or `Agent(org="<name>", prompt=...)`:
  the root position gets the goal and the org's tree as context and
  delegates through the existing sub-agent machinery (each child = a
  position with its model and effort, instructions as its system prompt,
  `reports` as the sub-agents it may spawn); results flow back up; the
  dock and the tasks panel (C) show the tree live; depth and concurrency
  from the org (overriding the config caps).
- Built-in orgs shipped as templates the user can copy and edit: `solo`
  (orchestrator only), `release-flow` (the flow used to build Halo:
  orchestrator writes a brief → implementer works in ≤250-line writes →
  tester runs the suites → reviewer lists findings → fixer applies them →
  tester again → orchestrator commits; the hand-back format from
  `plans/WORKER-RULES.md`), and `company` (CEO, VPs, managers, workers with
  sensible defaults and empty instruction slots).

### C. Sub-agent visibility and scale (`tui/dialogs/tasks.py`, `tui/widgets/cards.py`, `agent/subagent.py`, `config`)

- `/tasks` and Ctrl+T open a tasks panel: every running, queued and
  finished sub-agent (and background job) with position/role, model,
  phase, elapsed, tool count and cost; Enter opens a live, scrolling
  transcript viewer of that agent's `subagents/agent-<id>.jsonl` (follow
  mode, PgUp/PgDn, `o` pager, Esc back); finished agents stay listed for
  the session; the TaskCreated/TaskCompleted hook events from W4a feed it.
- Scale: `agents.max_concurrent` (default 4, any number) and
  `agents.max_depth` (default 1, up to 3) in config, overridable per org;
  the Agent tool accepts `count` (identical prompts) and `batch` (a list of
  prompts) to spawn N in parallel in one call; the orchestrator prompt
  tells the model it may spawn several agents at once and that `/tasks`
  shows them; a shared task board (`TaskCreate`/`TaskUpdate`-style tool
  backed by the session) lets agents coordinate; a parent waits on all
  children with one combined result.

### D. MCP repair actions (`tui/dialogs/mcp_status.py`, `mcp_cli.py`, `mcp/manager.py`, `mcp/oauth.py`, `docs/COMMANDS.md`)

- The `/mcp` dialog shows its keys and gains the missing ones: `r`
  reconnect, `R` reconnect all, `a` approve, `l` login (the generic OAuth
  flow from 2.0.1 part 7, or the connector re-auth instructions), `L` the
  server's log tail (`~/.halo/mcp/<server>.log`), `e` edit the entry (opens
  the source file at that server in `$EDITOR`, or an inline form for
  command/args/env/url), `i` install hint for command-not-found
  (`npx`/`pipx`/`uv tool`/`pip` guess from the command), `d` disable or
  enable, `t` test (`tools/list` round trip with timing). Each failed row
  carries the reason and the one fix line, as doctor does.
- `halo mcp fix <name>` runs the same diagnosis from the CLI and offers the
  fix; `halo mcp login <name>` already exists. Servers that die mid-session
  reconnect on next use with backoff; the dialog shows the attempt.

### E. Qwen tool calling at work (`providers/profiles.py`, `providers/model_table.json`, `agent/repair.py`, `docs/MODELS.md`, `docs/harness/FAMILY-BASELINE-*.md`)

- Research first (one worker, docs only): the Qwen3 family's tool-call
  conventions (Hermes-style `<tool_call>{json}</tool_call>` in the chat
  template, parallel calls, `enable_thinking`, arguments sometimes a JSON
  string, `strict` schemas rejected, `tool_choice` support per gateway),
  how the Databricks Qwen endpoints and OpenRouter providers expose them,
  and the exact failing shape from rolo's work VM (`halo bugreport` with the
  endpoint name and the error text; the "openjev" name in the request needs
  that confirmation).
- Then the fix: a Qwen family profile row (replay rules, no `strict`,
  `tool_choice` auto only, reasoning handling), repair-layer coverage for
  `<tool_call>` tags, string-encoded arguments and id normalisation, a
  mock-server scenario per captured error shape, a FAMILY-BASELINE row with
  the measured rates, and a learned-rule entry so a new 400 shape is
  remembered per endpoint.

### F. Terminal tab title (`tui/app.py`, `agent/cc_process.py`, `providers/cc_models.py`, `headless.py`)

- Root cause to confirm on Windows Terminal/PowerShell: child `claude`
  processes (auth status, mcp list, the cc: bridge) set the console title
  to `claude` and leave it. Fix: re-assert `halo` (`App.title`/OSC 2) after
  every `claude` child exits and on each drain tick that follows a child,
  set it at TUI start and on resume, and in print mode restore the
  previous title at exit; one pilot test for the re-assert and a manual
  check on PowerShell, Windows Terminal, GNOME Terminal and tmux.

### G. 2.0.7 DOOM theme (queued after 2.0.6; `tui/theme.py`, `tui/styles.tcss`, `tui/widgets/statusbar.py`, `docs/`)

- `/theme doom` and `theme: doom`: a palette taken from the game's look
  (dark greys, blood reds, rust browns, muted greens, amber text), heavier
  borders, and a status-bar skin shaped like the game's bottom HUD:
  segmented panels in the same order the HUD uses, each carrying a Halo
  field (ammo → tokens remaining, health → context remaining percent,
  arms → tools loaded, armor → cost or balance, keys → providers, the face
  slot → an original ASCII "guy" whose expression follows the phase: idle,
  thinking, writing, error, needs-you). Everything Halo's status bar shows
  today stays visible in the skin; only original art and names, nothing
  copied from the game's assets; snapshot tests for every face state and
  the width cascade.

## E addendum (2026-10-02, from docs/harness/QWEN-RESEARCH.md)

- Leading hypothesis for the work-VM errors: the endpoint is
  `databricks-openjev-qwen35-4b`, which Databricks documents as "OpenJev
  (Qwen3.5 4B) evaluates yes or no, choice, and scoring questions": a
  constrained decision model, not a chat or tool-calling model, with no
  row in model_table.json. To confirm from the owner's bugreport. If so,
  the fix is classification, not tool repair: a capability flag
  (`decision_only`) on such endpoints, the picker labelling them
  "answers yes/no, choice and scoring questions; no tools", a plain
  one-line consequence when one is chosen as the main model (never a
  block), and routing them to the new `judge` role, where OpenJev's
  yes/no, choice and score questions are exactly the job (ties to the
  jev work planned for 2.0.3).
- Confirmed defects to fix in the same round: every Qwen row declares
  `tool_leak_patterns` `python_repr_args` and `missing_tool_call_opener`
  but `providers/hooks.py` implements neither (`_LEAK_PATTERNS` /
  `_LEAK_EXTRACTORS`); native Qwen tool calls carry `arguments` as a JSON
  string that must be replayed as real JSON; Qwen3-Coder uses the
  `<function=NAME><parameter=K>V</parameter></function>` XML shape and
  vLLM's parser is `qwen3_xml` (Halo's `qwen3_coder` spelling is stale);
  a bare `</think>` with no opener must be stripped (`think_tag_strip`
  handles paired tags only); Databricks schema stripping misses
  `prefixItems` and the 16-key cap (`_DATABRICKS_STRIP_KEYWORDS` in
  request.py); Databricks has no parallel function calling, so one call
  per turn on that route. Seven mock_databricks scenarios and six
  bugreport questions are listed in the research doc's section 4.
