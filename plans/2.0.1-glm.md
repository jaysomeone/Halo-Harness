# GLM brief: make GLM 5.x on Databricks work really well (Halo 2.0.1, part 2)

rolo (2026-10-01, two screenshots from the work VM on
`dbx:databricks-glm-5-3`): "Can we do more research to ensure glm works
really well? Sometimes it pauses with glm, and I'm not sure if it's the
harness or what. Work on this for the 2.0.1 update."

## What the screenshots show

- The session was at effort `xhigh`, then `medium` after rolo used the
  `/effort` card. Each of his follow-ups ("give me more info...", "you
  there?", "hello?") was queued as "↳ steering…" because a GLM turn was
  still running; the status bar spinner showed 59 s elapsed. The model
  eventually answered all of them at once.
- So the "pause" is the pre-first-token thinking phase: Databricks sends
  nothing during it, the harness shows only the status-bar spinner, and a
  steer typed during that phase waits for the first chunk before it can
  cut in.

## Vendor and gateway facts (2026-10-01)

Z.ai GLM API (docs.z.ai, chat completion reference): `reasoning_effort`
accepts `max, high, low, medium, minimal, none, xhigh`, default `max`;
`thinking: {type: enabled|disabled}`; reasoning streams as
`delta.reasoning_content`; `clear_thinking` (default true) drops prior
reasoning blocks, `false` requires replaying the full ordered
`reasoning_content`; `tool_stream` (default false) enables streaming for
function calls; `tool_choice` supports `auto` only; temperature range
[0, 1] default 1.0, top_p default 0.95; max output 128K, context 200K on
Z.ai; finish reasons include `sensitive` and
`model_context_window_exceeded`.

Databricks Foundation Model APIs (supported-models page): endpoints
`databricks-glm-5-3` (text, context 1,048,576, max output 65,536),
`databricks-glm-5-3-flash` (text+image), `databricks-glm-5-2`,
`databricks-glm-5`. Reasoning is ALWAYS enabled. `reasoning_effort`
accepts only `low`, `high`, `max`; `max` is the default AND the silent
fallback for unsupported values (`minimal`, `medium`, `xhigh`); `none` is
rejected. `thinking`, `tool_stream` and `clear_thinking` are not in the
Databricks parameter list, and unknown parameters are rejected with 400,
so they cannot be used on this route.

Databricks "query reasoning models" page: GLM-5.2/DeepSeek/Kimi are
hybrid reasoning models whose `reasoning_effort` defaults to `max` with
model-specific value restrictions; reasoning comes back as content blocks
`{"type": "reasoning", "summary": [{"type": "summary_text", "text":
...}]}` (or `reasoning_text` parts), which the harness already decodes
alongside the plain `reasoning_content` field; the page does not say
whether reasoning is streamed incrementally, so the thinking indicator in
change 2 must not depend on reasoning deltas arriving. Side fact for a
later pass: on Databricks the reasoning-only Claude models (Opus 5.5,
Fable 5.1) accept `output_config.effort` values `low, medium, high,
xhigh, max`, so the Anthropic-route clamp of `xhigh` to `max` could become
per-model there.

Consequence: the harness's current table row (`reasoning_default_effort:
"max"`, selector offering `low medium high xhigh max`) means every GLM
turn on Databricks runs at `max` thinking, and rolo's `/effort medium`
was silently treated as `max` by the gateway. That is the pause.

## Changes (each with a pinning test against the mock Databricks server)

1. Effort sets per route and family, table-driven: `databricks-glm-*`
   accepts exactly `low, high, max`, default `high`; clamping maps
   `medium` -> `high`, `minimal` -> `low`, `xhigh` -> `max`, `none` ->
   `low` (never sent); the `/effort` card for a GLM route shows only
   `low [high] max` with one line saying `medium`/`xhigh` are not
   distinct levels on this gateway; `/effort` and `--effort` confirm the
   value actually sent. Keep the Z.ai-direct set (seven values) on
   OpenRouter `z-ai/glm-*` routes where the provider forwards them.
2. (SUPERSEDED by Part A of HALO-2.0.1-liveness-tips-brief.md, which is the
   fuller spec; keep this as the minimum.) Visible thinking: from the moment a request is sent until the first
   streamed token (text, reasoning or tool call), the transcript shows a
   dim `✻ Thinking… (12 s, no tokens yet)` line updated once a second;
   when `reasoning_content` deltas do arrive it becomes the existing
   ThinkingBlock. After 120 s with no token, one dim note says the model
   is still thinking and Esc interrupts.
3. Steer during the pre-first-token wait: when a steer arrives and no
   chunk has been received for the in-flight call, abort that call and
   resend immediately with the steer appended (the harness already cuts
   at the next chunk; this covers the no-chunk case). The transcript shows
   `↳ steering (restarting the model call)` so the user knows nothing was
   lost. Config key `steer.restart_when_silent` (default true) to turn it
   off.
4. Finish reasons: `model_context_window_exceeded` feeds the existing
   overflow -> compaction -> retry path; `sensitive` becomes a clear error
   card with the provider's message; `length` with no output stays a
   provider failure (re-route, never retry in place).
5. GLM never receives `tool_choice: required` (the gateway supports `auto`
   only): the repair retry uses the text nudge instead; temperature is
   clamped to [0, 1] on GLM routes.
6. Telemetry: `stats --models` gains TTFT p50 and p95 and a count of
   turns that waited more than 20 s for the first token, per model; the
   FAMILY-BASELINE doc gets a GLM section filled from rolo's work-VM data
   once he runs `halo stats --models --since 7d` after upgrading.
7. Docs: `docs/MODELS.md` GLM section with the Databricks effort facts and
   the clamp table; `docs/TROUBLESHOOTING.md` entry "GLM seems to pause"
   explaining the thinking phase, the effort levels that actually apply on
   Databricks, and how to lower effort.
