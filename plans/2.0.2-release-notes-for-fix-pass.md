# Notes for the 2.0.2 release review / fix pass (collected per round)

- Round 2 (orgs): the built-in `release-flow` is modelled as a CHAIN
  (Orchestrator -> Implementer -> Tester -> Reviewer -> Fixer -> Tester), so the
  implementer decides when to test and the tester spawns the reviewer. That
  inverts control compared with how the project is actually run (the
  orchestrator owns the sequence and spawns each stage as a sibling, judging
  each hand-back). Consider: Orchestrator reports = [Implementer, Tester,
  Reviewer, Fixer]; stages report to nobody; instructions tell the orchestrator
  the order and the gates (tests green before review, review findings fixed
  before retest). Keep the chain form documented as an alternative.
- Round 2 (orgs): resuming the OUTERMOST org call's task_id directly loses the
  org's max_depth/max_concurrent overrides (worker's LEFT OPEN); fix by storing
  the overrides on the task record.
- Round 2 (orgs): no Tab completion for org and position names in `/org ...`
  (roles got it in round 1); add in the fix pass or round 3.
- Round 1 (roles): `halo stats --roles` shows no price column (needs a parent
  model to resolve against); acceptable, documented in docs/ROLES.md.
- Round 2 (orgs), live on Kali: `/org run solo "..."` works end to end (pong
  came back) but the transcript shows the raw `<task_result task_id="...">`
  XML block; render it as a sub-agent result (card or plain text with the
  position title), not raw tags. The status bar's ctx/cost stayed at 0 for
  the whole run: an org run outside a parent turn does not feed the session
  counters; count its spend (and show "agents N" while it runs, round 3).
- Test hygiene (round 4 worker's flag): running one module directly (`python
  tests/test_x.py`) is NOT hermetic by itself -- only tests/run_all.py sets
  BRIDGE_TEST_HOME before import. Standalone runs of the MCP manager tests
  wrote fake-server logs into the REAL ~/.halo/mcp/ (fake.log, fake.log.1,
  plugin_*fakeserver.log; found and removed 2026-10-03). Fix in the shared
  runner: `tests/helpers/runner.run_all()` (or the module `__main__` path)
  sets a temp BRIDGE_TEST_HOME and BRIDGE_TEST_NO_BACKGROUND_NET when unset,
  so a standalone module can never touch the real state dir; add a test that
  imports a module standalone and asserts bridge_home() is under the temp.
- Flaky under load, seen in three worker runs: tests/test_cc_session.py::
  test_steer_between_tool_calls_is_absorbed_into_one_result (a 10 s thread
  join loses to CPU contention). Make the wait bounded by progress, not a
  fixed deadline, or lengthen it the way the W5b determinism pass did for its
  siblings.
- Round 4 (MCP repair): a bare HTTP 401 does not surface as needs_auth with
  the installed MCP SDK (generic MCPError); the fix line suggests `l` for any
  unrecognised http/sse failure. Revisit when the SDK exposes the status.
- Same hygiene issue, older: the real `~/.halo/mcp/` on the build host also
  holds a.log, b.log, c.log, big.log, crash.log, eager1.log from earlier
  standalone test runs (fixture server names). Left in place (not uniquely
  attributable); the runner fix above stops new ones. `halo doctor` could
  list state-dir files that match the test fixtures' names as "probably test
  leftovers, safe to delete".
- Round 4 (MCP), live on Kali: an http server entry pointing at a closed
  local port (127.0.0.1:9) failed only after the full MCP_TIMEOUT (30 s,
  "startup exceeded MCP_TIMEOUT") instead of an immediate "connection
  refused"; the TUI's first build waited the whole 30 s. Make connection
  refused (and DNS failure) fail fast in the http/sse connect path, and keep
  the first TUI build from blocking on a dead server (connect in the
  background, show the row as connecting).
- Owner on macOS (2026-10-03): "ctrl+e or command+e does not work on the mac
  using halo". Cmd+E never reaches a terminal program (the terminal app owns
  Cmd shortcuts), so only Ctrl+E can work; the app-level `Binding("ctrl+e",
  "open_editor")` in tui/app.py has no `priority=True`, so a focused widget
  that binds ctrl+e (Textual's Input and TextArea bind it to end-of-line)
  can swallow it, and some terminals (VS Code's integrated terminal, some
  tmux/iTerm2 key maps) intercept Ctrl+E before the app sees it. Fix pass:
  (1) `priority=True` on the Ctrl+E binding plus a pilot test that presses
  ctrl+e with the chat input focused and sees the editor action fire;
  (2) a `/editor` slash command as the keyboard-independent way to open the
  draft in $VISUAL/$EDITOR, listed in the F1 help next to Ctrl+E;
  (3) a `/keys` tester dialog that shows the key name halo receives for
  each press (Esc to leave), so a user can see whether the terminal
  delivers a shortcut at all; `halo doctor` prints TERM_PROGRAM/TERM;
  (4) docs/TROUBLESHOOTING.md "a shortcut does nothing on macOS" entry: use
  Ctrl not Cmd, check `/keys`, VS Code terminal: add the key to
  terminal.integrated.commandsToSkipShell or use `/editor`, iTerm2 profile
  key maps, `$EDITOR` unset shows a toast (already does). Ask the owner
  which terminal app the Mac uses and whether `/keys` shows ctrl+e once it
  ships.
  Owner's Mac terminal: VS Code's integrated terminal. The TROUBLESHOOTING
  entry must carry the two VS Code remedies verbatim: setting
  `"terminal.integrated.sendKeybindingsToShell": true`, or releasing one key
  with `"terminal.integrated.commandsToSkipShell": ["-<command owning ctrl+e>"]`
  (find the command in Keyboard Shortcuts, Cmd+K Cmd+S, search ctrl+e).
  `halo doctor` on TERM_PROGRAM=vscode should print that hint itself.
- Round 6 (update), live on Kali: a source directory with no `.git` and no
  dist metadata (the tar copy the suites run from) makes `halo --version`
  show no commit and `halo update` say "could not determine how halo was
  installed -- nothing to run". Say instead "running from a plain source
  directory (<path>) with no git metadata: replace the directory to update",
  and treat it as a known kind (`source_dir`) in doctor's install line.
- Round 6 (update), seen on the installed builds right after the commit:
  (a) an explicit `halo update --check` or `/update` must query GitHub
  every time (5 s cap, cache only as the fallback when the network fails);
  the 24 h cache is for the startup note only, and its TTL should be 1 h
  (`update.cache_ttl_s`). Both installs reported a stale "available"
  commit from a cache written an hour earlier, and the Windows one then
  said "update available" (exit 10) although its installed commit was
  newer. (b) When installed and available differ and no ordering is known,
  print "differs from <channel>" rather than claiming an update, and use
  `git merge-base --is-ancestor` when a checkout is available. (c) A
  `dir_info` install from a local path (`uv tool install .` from a clone,
  the Kali case) shows no commit: read `git rev-parse --short HEAD` in that
  path when it is a git checkout, editable or not, so `halo --version`
  shows the commit there too.

- Owner report (2026-10-04, round C before the tag): "when I am running a
  task ... my next question dumps like all the background tasks that were
  done at once, and kind of lost what was happening until I sent a message,
  then got flooded with what was happening." Two halves to fix:
  (a) user-visible flow: everything a background sub-agent or job does must
  land in the transcript AS IT HAPPENS (its card ticking with the phase word,
  its completion as a system note with a one-line result summary and a
  pointer to `/tasks`), and the status bar must keep a live signal while the
  main turn is idle (`agents N`, `bg jobs N`, the oldest one's elapsed time);
  the "hang" feel comes from a quiet screen while work runs elsewhere.
  (b) the model-facing side: the H6 rule that background completions reach
  the MODEL as a user-role notice on the next turn stays (Claude Code
  parity), but the notice must be one compact block per turn ("3 background
  tasks finished while you were away: ...", each with its task id and a
  short result), never a flood of raw results; and the drain loop must
  never hold events back until the next submit (audit `_pending_agent_
  notices`, `tui/dispatch.py` background paths, `--bg` job completion, and
  org runs for anything that only surfaces on `turn()`). Pilot test: start
  two background jobs, wait for both to finish with no input, assert both
  notes are on screen before any prompt is sent; then send a prompt and
  assert exactly one compact notice block reached the model.
