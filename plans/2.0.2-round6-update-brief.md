## 1. Know what is installed (`halo_harness/update.py`, new)

- `installed_build()`: version from `halo_harness.__version__` plus the
  source commit and requested revision from the installed distribution's
  PEP 610 `direct_url.json` (`importlib.metadata.distribution("halo-
  harness").read_text("direct_url.json")`: `vcs_info.commit_id` and
  `vcs_info.requested_revision` for a git install; `dir_info.editable` plus
  the checkout URL for an editable install, in which case run `git rev-
  parse --short HEAD` and `git branch --show-current` in that checkout;
  nothing for a plain PYTHONPATH run from a checkout, in which case use the
  checkout that contains the package). `halo --version` prints
  `halo 2.0.2 (c93480d, master)` when the commit is known, and `halo
  doctor` gets an "install" line: how it was installed (uv tool, pipx, pip,
  editable checkout, checkout on PYTHONPATH), from where, which commit.
- `install_kind()`: uv tool (the `uv-receipt.toml` next to the tool's venv,
  or `uv tool list` naming halo-harness), pipx (`pipx list --json`), pip
  (`direct_url.json` present, neither uv nor pipx), editable checkout,
  bare checkout. Each kind knows its own reinstall command:
  `uv tool install --reinstall <spec>`, `pipx install --force <spec>`,
  `python -m pip install --upgrade <spec>`, `git pull` then the editable
  reinstall, `git pull` alone for a bare checkout. `<spec>` is the source
  the install came from (`git+https://github.com/roloVibes/Halo-Harness`
  with the requested revision kept, or the checkout path).

## 2. Know what is available

- `latest_available(channel)`: `channel` is `main` (the branch the install
  came from, default when the install tracks a branch) or `stable` (the
  newest `v*` tag, default when the install was pinned to a tag). Read it
  with `git ls-remote --heads --tags https://github.com/roloVibes/Halo-
  Harness` when git is on PATH, else the GitHub REST API without auth
  (`/repos/roloVibes/Halo-Harness/commits/master`, `/tags`); 5 s timeout;
  never raises, returns "unknown" with the reason. Honour
  `BRIDGE_TEST_NO_BACKGROUND_NET` and a config `update.check: false`.
- The answer is cached in `~/.halo/update-check.json` for 24 hours (the
  commit seen, the time, the channel); `--refresh` ignores the cache.

## 3. `halo update` on the CLI (`update_cli.py`, wired in `cli.py`)

- `halo update --check`: prints installed vs available, the commits
  between them (`git log --oneline` when a checkout is available, else the
  count from the API), and the exact command an update would run. Exit 0
  up to date, 10 update available, 1 unknown.
- `halo update` (apply): refuses while another `halo` process is running
  on this machine (a reinstall under a running TUI broke the install on
  Windows; detect other halo processes by command line, excluding this
  one; `--force` overrides) and says which pids. Otherwise prints the
  command, runs it with live output, then runs `halo --version` from the
  new install and reports the before and after commits. `--to <tag|branch|
  commit>` picks the revision; `--channel stable|main` switches channel
  and remembers it in config (`update.channel`).
- Everything subprocess goes through one `run(cmd)` seam; tests fake it.

## 4. `/update` inside the TUI (`tui/slash.py`, a small dialog)

- `/update` runs the check on a worker (never the UI thread) and shows a
  dialog: installed build, available build, the commits between them (up
  to 15 one-liners), the command that would run, and two actions:
  `Enter: update and restart halo` and `Esc: not now`. Restart flow: the
  TUI quits with a special exit that makes `cli.main` run the update
  command in the terminal (output visible), then relaunch `halo` with
  `--continue` so the session resumes on the new code. On Windows this is
  the only safe order (the venv cannot be replaced under the running
  process). A failed update prints the error and relaunches the old halo
  with `--continue` anyway.
- A one-line transcript note at startup when the cached check says an
  update is available (`update available: 2.0.2 c93480d -> 2.0.3 e1f2a3b,
  /update`), at most once a day, background only, off with
  `update.check: false` or `update.notify: false`.

- README.md: an "Install" section with three paths (one line each with
  the exact command): the curl one-liner for Linux and macOS
  (`scripts/install-halo.sh`), the uv one-liner for any OS (`uv tool
  install git+https://github.com/roloVibes/Halo-Harness`), pipx; then
  `cd anywhere && halo`. An "Update" section: `halo update` (or `/update`
  inside halo), what it does, the manual line per install kind, and the
  Windows note (close halo sessions first; `/update` handles it). A
  "Check what you have" line: `halo --version`, `halo doctor`.
- docs/INSTALL.md rewritten to the same structure, with per-platform

  stays in its own short section. docs/HANDBOOK.md and docs/COMMANDS.md
