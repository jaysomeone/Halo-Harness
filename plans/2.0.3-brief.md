# Halo 2.0.3: hardening release (approved by rolo 2026-10-01: "Let's add all of those and to the versions you chose")

Source: Fable's own recommendations given in chat on 2026-10-01 after the
2.0.1 list. 2.0.3 ships after 2.0.2 and contains no new user-facing
features except the watchdog line and the deprecation. Same rules as
every round: one worker in the tree at a time, hermetic tests scoped
with BRIDGE_TEST_HOME, no safety/refusal wording, commits as
rolo <roloVibes@users.noreply.github.com> with the Co-Authored-By line
and no Claude-Session line, verified on Windows, WSL and the Kali VM.

## 1. Model gym (the models get tested, not only the harness)

- `tools/gym/tasks/*.json`: 15 to 20 live tasks, each with `prompt`,
  `fixture` (files to create in a temp repo), `checks` (file content
  regex, command exit status, transcript assertions such as "Edit used
  exactly once", "no repair-layer hits", "no tool errors", `max_turns`,
  `max_cost_usd`), and `tags` (edit, multi-step, claude-md, recovery,
  compaction, mcp, plan). Starter set: single-line Edit with a unique
  match; Edit needing three lines of context; create then verify a file
  with a shell command; follow a CLAUDE.md rule that forbids a word;
  recover from a failing command and fix it; read a 400-line file and
  answer a question that needs lines near the end; two tool calls in one
  message; a Grep then Edit chain; resume after a forced `/compact`;
  call a fake MCP tool through ToolSearch; refuse nothing (a task whose
  only check is that the model did the ordinary work asked); answer from
  auto-memory; AskUserQuestion in print mode handled as the docs say.
- Runner: `halo gym --model <ref> [--tasks tag|name ...] [--repeat N]
  [--out DIR]` runs each task in a fresh temp repo via print mode against
  the REAL route, scores pass/fail per check, records turns, cost,
  time-to-first-token, repair hits, edit failures and tool errors from
  the session log, and writes `gym-<model>-<date>.json` plus a markdown
  table. `--update-baseline` rewrites that model's section in
  `docs/harness/FAMILY-BASELINE-<date>.md` from the results.
- Hermetic self-test: the runner against the mock upstream with a
  scripted perfect model and a scripted failing model, asserting the
  scoring, so the gym's own code is covered without credentials.
- Docs: `docs/harness/GYM.md` with cost estimates per provider and the
  work-VM recipe (`halo gym --model dbx:databricks-glm-5-3`).

## 2. Soak test and watchdog (the idle-freeze class)

- `tools/soak.py`: a headless Textual pilot run for a configurable
  duration (10 minutes in CI, hours by hand) against the mock upstream,
  injecting in sequence: idle gaps, a monotonic clock jump (sleep/wake
  seam), terminal resizes, the fake MCP server killed and restarted, a
  connection reset mid-stream, a DNS failure, a 429 with retry_after,
  a permission card left unanswered for a while then answered, a steer
  during a silent call, and a `/compact`. After every event a prompt
  must get a response within a deadline. Assertions: the drain timer's
  tick count rises monotonically; no traceback in harness.log; RSS
  growth bounded (threshold in the script); the status cluster returns
  to idle after each turn.
- Kali runbook addition: tmux session detach/reattach and a real
  30-minute idle, added to `docs/harness/LIVE-CHECKS.md`.
- Product watchdog: a daemon thread checks the UI drain heartbeat and
  each worker's progress stamp. If the UI thread has not ticked for 5 s
  while a turn runs, or a worker is past its own deadline, it writes
  `[watchdog] ui stalled 5 s` (or `worker <name> blocked 60 s in
  <phase>`) plus a dump of all thread stacks to harness.log, at most once
  a minute. It never kills or restarts anything. `bugreport` includes
  the last watchdog lines.

## 3. Continuous integration and a release script

- `.github/workflows/ci.yml`: matrix ubuntu-latest and windows-latest
  with Python 3.11, 3.12 and 3.13, plus macos-latest on 3.12 (rolo has a
  Mac). Steps: pip install `.[dev]`, `python test_bridge.py`,
  `python tests/run_all.py`, `python test_tui.py`, with the hermetic env
  (`BRIDGE_TEST_NO_BACKGROUND_NET=1`, a temp `BRIDGE_TEST_HOME`). A
  separate ruff job. Logs uploaded as artifacts on failure. Badge in
  the README.
- `tools/release.py --version X.Y.Z`: checks a clean tree on the
  expected branch, bumps `__version__` and pyproject, verifies the
  CHANGELOG has the section, runs the three suites, commits with the
  required author and Co-Authored-By lines and no Claude-Session line,
  tags `vX.Y.Z`, and prints the push command. It never pushes by itself.
- `docs/harness/RELEASING.md`: the checklist the script automates, plus
  the three-platform manual verification and the Kali live checks.

## 4. Invariants as a test

- `docs/harness/INVARIANTS.md` lists the standing rules with the reason
  for each: never read `~/.claude/.credentials.json`; never write
  `~/.claude.json` or `~/.claude/settings.json` except through `mcp add`;
  no safety, refusal or "not allowed in auto mode" wording in prompts,
  tool descriptions, UI strings or docs; the Databricks workspace host in
  the repo is always the placeholder; no provider key or key-shaped
  token in the tree; every test scopes its home; POSIX launchers are LF;
  version strings agree across pyproject, `__version__` and the
  CHANGELOG head; `rolo-claude` appears only in the deprecation notice
  and in history docs; tool child env never carries the provider keys.
- `tests/test_invariants.py` checks every mechanically checkable rule:
  grep-based scans with explicit allowlists (for example the flag name
  `--dangerously-skip-permissions` is not safety wording), an AST or
  grep check that every `tests/test_*.py` uses the scoped-home helper or
  sets `BRIDGE_TEST_HOME`, the LF check on `bin/*` POSIX files, the
  version agreement check, a key-pattern scan (`sk-`, `dapi`, `Bearer`,
  long hex or base64 runs) over tracked files.
- The existing scattered guards (REAL SESSIONS GUARD, REAL STATE DIR
  GUARD, hermetic child env) stay where they are and are referenced from
  the doc.

## 5. Deprecations

- Stop reading the legacy env file `~/.config/vibes-hacker/env`. 2.0.1
  and 2.0.2 CHANGELOGs announce it; 2.0.2's doctor WARNs when the legacy
  file is the only source and names `halo init` as the migration (the
  copy-forward behind the import marker already does the work on the
  next write). 2.0.3 removes the fallback read and the marker logic
  becomes a no-op kept only for the test seams. The legacy file itself is
  never modified or deleted (other tools on rolo's boxes read it).
- `halo proxy` is maintained, not developed: its tests keep running, the
  README says so in one line, no new features.
- The deprecated `rolo-claude` alias code path is removed (2.0.1 already
  ships only the `halo` executable; 2.0.3 deletes `main_deprecated_alias`
  and `bin/rolo-claude`).
