## A. OpenRouter: enumerate everything, pick hierarchically

Today `/model` shows only the configured OpenRouter default (DeepSeek)
because the picker lists the cached `models.json` subset. rolo: "there are
tons of models in openrouter and there were no other models ... We need to
figure out how to enumerate with the openrouter api all the models that
are available ... plus we'd have to find ways to distinguish between each
model and if it has that data protection option or region too ... Maybe
each main provider is listed in the model display, then you open that and
it shows the models, then you click into there and have the options of
which one to pick, plus their prices."

1. Catalog: `GET /api/v1/models` (464 entries today) cached per user with
   id, name, context, pricing (prompt/completion/cache, strings to float),
   `supported_parameters` (tools, reasoning, response_format, ...),
   modalities, `top_provider.max_completion_tokens`, `created`. Per model
   on demand: `GET /api/v1/models/{id}/endpoints` (provider name, context,
   max completion, pricing, quantization, uptime/status, supported
   parameters per endpoint). Data policy: OpenRouter's ZDR endpoint list
   (`/api/v1/endpoints/zdr` if present in the current API, else the
   endpoints' data-policy fields) and the routing preferences the request
   can carry (`provider.zdr: true`, `provider.data_collection: "deny"`,
   `provider.order`, `allow_fallbacks`, `require_parameters`). Region is
   only known where a provider name implies it; show it when known, blank
   otherwise, never guessed.
2. Picker: NO levels or drop-downs. rolo (2026-09-30, final): "I like how
   this looks seeing every model at once, let's just add more columns to
   say if the data protection is enabled, region, and speed. I know other
   providers may not have it ... I think we can just add those 3
   columns." So the flat grouped list stays and gains three columns after
   the prices, blank wherever a provider does not expose the fact:
   - `data`: the data-protection state of the route. OpenRouter: `ZDR`
     when the model has a zero-data-retention endpoint (OpenRouter's ZDR
     endpoint listing, else the endpoints' data policy), `no-train` when
     every endpoint declares no training on prompts, blank otherwise.
     Databricks: `workspace` (requests never leave the workspace's own
     serving). Anthropic API and Claude Code subscription: `no-train`
     (API data is not used for training by default). TypeSafe: blank
     until the docs state a policy.
   - `region`: only where a provider states one (an OpenRouter endpoint
     whose provider name carries it, a Databricks workspace region when
     derivable from the host), else blank. Never guessed.
   - `speed`: the harness's own observed figure first, since it is the
     only source that works for every provider: median time-to-first-token
     and tokens per second from telemetry (`stats --models` already has
     `ttft_ms`), shown as `1.2s · 48 t/s` once a model has been used at
     least three times, blank before; OpenRouter's reported endpoint
     latency/throughput fills the column for unused models when the API
     exposes it.
   Sorting: `s` cycles the sort key (name, price, ctx, speed); the filter
   box still narrows by text. Picking a row never pins routing options;
   `/zdr` and `/fast` (already in the design: `provider.zdr`,
   `provider.sort: throughput`) remain the way to constrain OpenRouter
   routing, and the `data` column shows what the constraint can achieve.
   Note from live use: `rolo-claude models --refresh` alone solved the
   "only one OpenRouter model" case; the launch-time auto-fetch in 1.0.1
   part 2 makes that step unnecessary. Enter at level 3 picks the model and
   stores the chosen options in `~/.halo/config.json` under
   `model_options[<ref>]`; Enter at level 2 picks the model with defaults.
   Left/Right or Backspace go up a level; typing filters the current
   level; the Databricks level 2 is the existing grouped list.
3. `/model` with an argument keeps working for hand-typed refs; the
   `models.json` refresh happens from the picker (`r`) and from
   `/models refresh`; the OpenRouter catalog is refreshed when older than
   24 h on launch, in the background, never on the UI thread.
4. Docs: `docs/MODELS.md` gets the OpenRouter section (how the levels map
   to the API, what each badge means, how pinned options are sent).

## B. Balances and usage per provider

rolo: "on api calls, excluding databricks, is there a way to do a call to
see how much money you have left on that API?"

1. OpenRouter: DONE in 1.0.1 part 2 (H15 addendum 4): `GET /api/v1/credits`
   and `GET /api/v1/auth/key`, a status-bar segment `OR $12.40 left` next
   to the session cost (rolo: "put the remaining balance of an api key in
   the bottom set of insights"), also in `/cost` and `/providers`. 2.0.2
   extends the same segment to any other provider that gains a balance
   source below.
2. Anthropic API: no balance endpoint for a plain API key. When an Admin
   API key is configured (`ANTHROPIC_ADMIN_KEY`), the organisation usage
   and cost reports (`/v1/organizations/usage_report/messages` and
   `/v1/organizations/cost_report`) give spend for the period; otherwise
   `/providers` says "balance not exposed by this API" and shows the
   session's own computed spend.
3. Claude Code subscription: usage limits are visible inside `claude`
   (`/usage`); the harness never reads the OAuth credentials, so the only
   honest options are driving `claude` headlessly if a non-interactive
   usage query exists in the installed version, or showing "see /usage in
   claude". Research item: check the installed `claude --help` and
   `claude /usage` behaviour in print mode before promising anything.
4. TypeSafe: check docs.typesafe.ai for a usage or balance endpoint; else
   show the session's computed spend from the published price.
5. Databricks: explicitly excluded by rolo (DBU billing is on the
   workspace side); keep the per-session computed cost only.
6. All of these are bounded requests (item 2 fail-fast), cached for a few
   minutes, never on the UI thread, and never block a turn.

## C2. OpenAI parity: Codex subscription and the OpenAI API

rolo (2026-09-30): "I'm not sure if we do the same thing for codex like we
do for Claude Code with the intuitive understanding where tokens or
sessions are saved, but the same should be for codex. I just never use
that but if a user does it should show up like Claude Code does in the
model list with what models they can use with their subscription version.
Same with OpenAI's api version of connection."

1. Codex subscription route (`cx:` prefix, group label "Codex subscription
   (ChatGPT)"): mirrors the `cc:` design. Detection: the installed `codex`
   binary on PATH and `codex login status` reporting a ChatGPT login; the
   harness never reads `~/.codex/auth.json` or any OAuth token, it only
   drives the binary headlessly. Execution: `codex exec` in JSON event
   mode with `--model`, approvals off and sandbox off for auto/bypass
   modes (Codex's own flags), the harness's tools exposed to Codex through
   an inline MCP server override (`-c mcp_servers.halo.command=...`,
   the Codex counterpart of the `--mcp-config` bridge used for `cc:`),
   steering through the event stream, and the same stripped child
   environment rules as `cc:`. Model list: the ids the installed Codex
   version accepts for a ChatGPT login (research: `codex` has no list
   command, so start from its documented model set, confirm each by a
   one-token headless call on `/models refresh`, mark the refused ones),
   shown with resolved ids like the `cc:` rows. Init tab "Codex
   subscription" with the same picked-up/not-set-up/reachable tags.
   Auto-enabled only on a genuine ChatGPT login (the `cc:` rule).
2. OpenAI API route (`oai:` prefix, group label "OpenAI API (key)"):
   `OPENAI_API_KEY` from the env file, shell env or settings env chain
   auto-enables it; catalog from `GET https://api.openai.com/v1/models`
   cached like the others, prices from models.dev's `openai` provider;
   chat-completions dialect through the existing OpenAI-family compat
   profile, plus the Responses API dialect for models whose
   reasoning-with-tools needs it (the gpt-6 follow-up from 1.0.1 item
   22); effort sets per the OpenAI family table; balance: the OpenAI API
   has no public balance endpoint for ordinary keys, so `/providers` says
   so and shows computed spend (part B rule).
3. Both routes appear in `/model`, `models`, init and `/providers` with the
   item-12 columns and the three new columns, and both follow the
   enablement rule (detected = on, explicit override off).
4. Verification: a fake `codex` binary in the test fixtures that speaks
   the JSON event protocol (the `cc:` suite's fake `claude` is the
   template); a mock OpenAI `/v1/models` and chat/responses endpoints;
   rolo's live check on the Mac if he logs into Codex there.

## F. Research corrections (see RESEARCH-2.0.2.md, 2026-09-30)

- OpenRouter: key info is `GET /api/v1/key`; `GET /api/v1/credits` needs
  a Management key (optional `OPENROUTER_MANAGEMENT_KEY`); `/api/v1/
  endpoints/zdr` is a global listing, not per model; the endpoints API
  has no region field anywhere, so the region column is blank for
  OpenRouter; `ProviderPreferences` covers zdr, data_collection, order,
  sort, allow_fallbacks, require_parameters, quantizations, max_price.
- OpenAI: `reasoning.effort` values none/minimal/low/medium/high/xhigh/
  max; reasoning items replay via `previous_response_id` or by including
  encrypted reasoning content; the tools-plus-effort rule on chat
  completions differs by model (GPT-5.4+ reject when effort is not none;
  GPT-6 Astra and 6.1 Sol reject unconditionally), which the Databricks
  per-endpoint learned rule already absorbs; org usage and cost reports
  need an Admin key and their exact paths are still unverified.
- Codex CLI: `codex exec --json` emits NDJSON events (thread.started,
  turn.started, turn.completed, turn.failed, item.started, item.completed,
  error); approval and sandbox flags documented; the MCP TOML shape and
  the `-c` override semantics are unverified; nothing documents which
  models a ChatGPT-subscription login may use, so the probe-on-refresh
  approach stands.
- Anthropic: `GET /v1/models` and the Admin usage/cost report shapes are
  documented; the `claude` CLI has no non-interactive usage command, so
  the subscription shows "see /usage in claude" and nothing else.
- TypeSafe: the "Is Jev deterministic?" FAQ answer is JS-rendered and
  could not be retrieved; the SDK's retry and timeout defaults are
  documented; no balance endpoint. Repeatability stays a measured item.
- models.dev: `openai` (53 ids) and `anthropic` (16 ids) carry cost and
  limit for current models; fetch with a non-default User-Agent.

## G. Additions approved by rolo 2026-10-01 (Fable's recommendations)

G1. Learned gateway rules, generalised from the 1.0.1 gpt-6 rule
(`providers/learned_rules.py`): on any 400 or 422 whose body names a
request field (reasoning_effort, temperature, top_p, tool_choice,
max_tokens, max_completion_tokens, thinking, output_config,
response_format, parallel_tool_calls, strict, store, stream_options,
metadata, and the Databricks allowlist words), apply the smallest fix:
drop the field, or when the message lists allowed values clamp to the
nearest allowed one; retry ONCE; persist `{provider, endpoint}:
{field: action, error, date}` in `~/.halo/learned-rules.json`; print one
transcript line (`Databricks rejected thinking on this endpoint;
dropped it and retried; remembered for this endpoint`). `halo rules`
and `/rules` list the rules; `--forget <endpoint>` and `models refresh
--forget-rules` clear them; rules older than 30 days are re-tried once
before being reapplied. `doctor --probe-all --learn` pre-learns by
sending minimal requests with each optional parameter to each
Databricks endpoint (opt-in, a few cents). Tests against the mock
Databricks server returning parameter errors in each shape seen so far
(gpt-6 reasoning_effort with tools, GLM thinking, Claude output_config
xhigh, unknown field 400).

G2. Error translation: a table mapping known upstream error shapes to
one plain sentence and the fix (applied or suggested command). The
transcript error card shows the sentence and the fix; the raw body goes
to harness.log and Ctrl+O on the card expands it. Unknown errors show
the provider's message trimmed to three lines plus the log pointer.

G3. Catalogs refresh themselves (no maintenance command on the normal
path): a background refresh when a provider's cache is older than 24 h,
when a provider becomes enabled and its cache is empty, and when the
picker opens with an empty group. The picker shows `refreshing…` with a
spinner on that group and fills it in when done; the status bar shows
nothing for it. `/models refresh` stays as the manual force. Never on
the UI thread; respects `BRIDGE_TEST_NO_BACKGROUND_NET`.

G4. Fewer, stronger commands: in the picker `r` refreshes the current
group and `R` all groups; `/dbx` becomes an alias that opens the picker

`/providers` is the one place for enablement reason, balance, cache age
and a refresh key. No command is removed in 2.0.2.

G5. Names by what things are: picker and `/providers` group labels are
`Claude Code subscription (cc:)`, `Anthropic API key (ant:)`,
`Databricks (dbx:)`, `OpenRouter (or:)`, `OpenAI API key (oai:)` and the
Codex label with its prefix; the prefix follows the label in parentheses

G6. Codex: doctor pins the tested Codex CLI version range like the `cc:`

G7. Deprecation: doctor WARNs when the legacy env file

## H. `cc:` route v2 (rolo 2026-10-02: "the whole v1 issue ... going through literally Claude Code")

Today the subscription route runs the real `claude` binary headlessly as
the model (`claude -p --input-format stream-json --output-format
stream-json --permission-mode bypassPermissions --tools "" --strict-mcp-
config --mcp-config <bridge>`), with halo's tools bridged in as one MCP
server, so halo's permissions, hooks, log and telemetry already govern
every tool call and Claude Code's own gating and built-ins are out of the
loop. The v1 limits documented in docs/HANDBOOK.md are protocol gaps:

1. Steer: use the stream-json control channel (`control_request` subtype
   `interrupt`, the same message the Claude Agent SDK sends) to cut the
   current reply cleanly, then send the steer as the next user message, so
   a `cc:` steer behaves like every other route's; keep today's "queued for
   Claude Code" path only as the fallback when the installed version lacks
   the control channel (detect once per process).
2. Model and mode changes without a restart: `control_request`
   `set_model` and `set_permission_mode` where the installed version
   supports them; otherwise the current restart-with-summary path.
3. Compaction: forward `/compact` as a user-message slash command to the
   child (verify the installed version honours it in print mode); surface
   PreCompact/PostCompact through `--include-hook-events` or the hook
   callback channel so halo's transcript shows the compaction and its
   summary the way native routes do.
4. History when switching into `cc:` mid-session: research whether a
   session transcript halo writes can be resumed with `--resume` so the
   child starts with native history instead of a capped summary; if the
   format is stable, do it behind a flag; else keep the summary and say so.
5. Context duplication audit: the child loads the cwd's CLAUDE.md, rules
   and memory itself while halo also injects its own snapshot; measure the
   overlap and pass only what Claude Code would not load on its own.
6. Cost: present `cc:` usage as "subscription turns" with Claude Code's
   estimate labelled as an estimate, never as spend; unchanged otherwise.
7. Conformance: a protocol test against tests/helpers/fake_claude_cc.py
   for every control message, and the real-binary interop test on the
   Kali VM in the release round; cc_tested.json widened to the versions
   that pass it. Keep bypass + `--tools ""` + bridged tools: that is what
   keeps halo's rules authoritative.
