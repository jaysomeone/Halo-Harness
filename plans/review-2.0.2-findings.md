# Halo 2.0.2 release review (Opus) -- findings

Scope: `git diff v2.0.1..d65cdd3 -- halo_harness scripts pyproject.toml` (54 files), read file by file against the seven part
commits, plans/WORKER-RULES.md and plans/2.0.2-release-notes-for-fix-pass.md. Every "Verified" below was either traced through the
current code or run as a targeted snippet / Textual pilot with `BRIDGE_TEST_HOME`/`BRIDGE_STATE_DIR` pointed at a scratch temp dir
(provider env scrubbed, fake keys only). No repo file was edited and no suite was run.

Counts: 3 critical, 15 major, 21 minor.

## Findings

1. **critical** — `halo_harness/tui/dialogs/init_wizard.py:582-606` (+ `:774-783,886-910`) — The Default model step calls `option_list.action_first()` on mount, and `commit()` saves whatever is highlighted. So Next with nothing picked overwrites `config.model` with the first catalog row, even though the step says "Next keeps the current default if you don't pick one". This brings back the 1.0.1 fixpass finding 9 (a re-run of init must keep an existing default). RolesStep does the same thing on purpose: Next applies the auto-highlighted `balanced` preset over the existing `roles.researcher`/`roles.small`. — Verified: Textual pilot with `config.model = or:deepseek/deepseek-chat` and only `ANTHROPIC_API_KEY` set. One Ctrl+N gave `config.model = ant:fable`. — Fix: highlight the current default (or nothing) on mount, and only write when the user actually picked a row (track OptionSelected or a highlight change after mount). Give RolesStep an explicit "keep current roles" first row.

2. **critical** — `halo_harness/update.py:426-459` + `update_cli.py:54-69` + `cli.py:323-341` — On Windows, `halo update` always refuses and `/update`'s Enter flow always fails. The uv launcher `~/.local/bin/halo.exe` stays alive as the parent of the `python.exe` that runs halo. `other_halo_pids()` only leaves out `os.getpid()`, so it always lists that parent, and the `/update` handoff calls `apply_update()` without force: it refuses, then relaunches the old build. Two more problems: any process with "halo" anywhere in its command line also blocks the update (an editor open on the repo, `tail -f ~/.halo/...`), and with `--force` the reinstall still runs inside the same tool-venv `python.exe` that the docstring's "quit, then update" order promises to avoid. — Verified: polled the installed `halo.exe --version` with psutil (scratch state dir). The tree was `halo.exe (cmdline ...halo.exe --version)` with a `python.exe` child, and the parent's cmdline matches `_is_halo_cmdline`. `_is_halo_cmdline` is also true for `Code.exe ...\Halo-Harness` and `tail -f ~/.halo/bridge.log`. The in-process `--force` reinstall failing is PLAUSIBLE (uv cannot replace a running venv on Windows); not run. — Fix: leave this process's whole ancestor chain out of the check (ParentProcessId from the same CIM query, `ps -o ppid` on POSIX), and match only processes whose argv[0]/module is halo or `halo_harness`. On Windows, hand the reinstall to a detached helper that waits for the pid tree to exit, or print the command and exit.

3. **critical** — `halo_harness/update.py:229-238` + `update_cli.py:79` — For an editable or bare-checkout install, the update command is `git pull [&& <tool> install -e .]`, and it runs with `shell=True` and no `cwd`. The pull therefore runs in the user's current directory, which is usually an unrelated project repo, and `.` installs that project. — Verified: `install_kind(direct_url=editable)` returns `git pull && python -m pip install --upgrade -e .` with `spec` set to the checkout. Calling `apply_update(cmd="git pull")` from a scratch "project" cwd ran `('git pull', cwd=None)`. — Fix: run with `cwd=spec`, or emit `git -C <checkout> pull --ff-only && <tool> install ... <checkout>`. Never use a bare `.`.

4. **major** — `halo_harness/agent/subagent.py:1088-1091,1459-1463` + `tui/slash.py:291,315-329` — `run_agent_call` and `_resume_task` don't guard `_build_child_session`, so their "never raises" contract is false. A model that won't resolve throws `InvalidModelError` out of `run_org_call`. That can be an org position `model: "Qwen3-Coder"`, which `validate_org` and the org editor both accept, or a role set by the unvalidated `/role coder qwen3coder`. In the TUI, `_run_org_worker` is a thread worker with Textual's default `exit_on_error=True`, so `/org run` takes down the whole TUI. A fan-out job that fails the same way stays "queued" in meta.json forever. — Verified: `resolve_agent_model(frontmatter_model="Qwen3-Coder")` and a role-table value `qwen3coder` both raise `InvalidModelError`. `inspect.signature(App.run_worker)` shows `exit_on_error` defaults to True. `_run_org_worker` has no try. — Fix: wrap the build in both functions (return an `is_error` ToolResult and mark the meta "error"), add try/except in `_run_org_worker`, and validate position models and `/role` models with `parse_model_ref` at save/set time.

5. **major** — `halo_harness/agent/subagent.py:1053,1210-1214,1322-1326,1413` + `orgs.py:447-500` — Org budgets aren't enforced.
   - `baseline_usd` comes from the caller's CostMeter, but every later check passes the spawning position's own fresh meter. After any earlier session spend, `max(0, position_total - baseline)` stays 0, so the org budget never trips.
   - Even with a zero baseline, the "org total" leaves out sibling subtrees and still-running children.
   - The post-rollup delta (`total - _cost_before`) double-counts children that finish at the same time.
   - Fan-out (`count`/`batch`) jobs and task resumes never call `record_spend` or the refusal check.

   So "hard stop at 100, enforced before each spawn" isn't delivered. — Verified: `OrgBudgetTracker(budget 1.00, baseline 3.00)`, then `refusal_before_spawn(.., 2.50)` returns None and `record_spend(.., 2.50, 2.50)` returns None. The fan-out and resume paths contain no `org_budget` use. — Fix: keep an org-wide spent counter inside the tracker under a lock, and add each child's own `child.cost_meter.total_usd` (the call's delta) to it. Check it in every spawn path: single, fan-out per job, and resume.

6. **major** — `halo_harness/agent/subagent.py:549-553` + `tui/dispatch.py:596-606` + `tui/widgets/transcript.py:784` — `_tag` overwrites `ev.agent_id` for every event coming up through a child's turn. A delegate's `subagent_start` (for example a VP's under the CEO) therefore reaches the TUI tagged with the root's id. Its card is stored under the root's key in `subagent_cards`, so the root's card is orphaned, never finished, and ticks "thinking Ns" forever. The delegate's text also streams into the root's stream. This hits every org with delegation and any `agents.max_depth > 1` run; the live check used `solo` only. — Verified: `_tag(Event(agent_id="vp000001"), agent_id="ceo00001")` gives `agent_id == "ceo00001"` while `data.agent_id == "vp000001"`. The dispatch key is `agent_id or data.get("agent_id")`. — Fix: in `_tag`, set `agent_id` only when the event has none (keep the deepest id, add `root_agent_id`), and key subagent_start/end on `data["agent_id"]`.

7. **major** — `halo_harness/controller.py:241-249` + `headless.py:747-755` + `config/agents_md.py:259-273` — Sending a decision-only endpoint to `roles.judge` leads nowhere. The only judge consumer is the built-in `Judge` agent, which always carries Explore's six tools, so every request it makes on that endpoint raises `ToolsNotSupported`. Update `runtime.role_table` live and keep any existing effort.

8. **major** — `halo_harness/headless.py:747-755` + `init_cli.py:513-543` — The claim "a session can never start on it" fails when the configured default is the decision-only endpoint. That default can be `config.model`, `HALO_MODEL`, routes `default`, or the work-env `dbx:<ANTHROPIC_MODEL>`. The fallback calls `resolve_default_model_raw` again, gets the same model back, and doesn't check it a second time. Filter decision-only rows out of the init/wizard default-model lists.

9. **major** — `halo_harness/agent/subagent.py:1413-1418` — `run_org_call` copies the caller's `depth` but sets an absolute `max_depth = org_tree_depth + 1`. A sub-agent already at its depth cap can start a deep org, which bypasses "Sub-agents cannot spawn further sub-agents". An org started below depth 0 also loses that many bottom levels (`company` from depth 1 never reaches its workers). — Verified: an `AgentRuntime` at depth 1 has `effective_max_depth == 1`, and `run_org_call(org="company")` built an org runtime with `{'depth': 1, 'max_depth': 4}`. — Fix: `max_depth = runtime.depth + org_tree_depth(org) + 1`, and decide (and document) whether the caller's own cap must allow the first hop.

10. **major** — `halo_harness/agent/subagent.py:912` + `agent/loop.py:4945` — `agents.max_concurrent` caps one pool at a time; nothing caps the session. Two `count` calls in one turn each get their own pool, nested levels multiply, and an org's `max_concurrent` only limits one position's batch. That contradicts "how many sub-agents one call/turn may run at once" and the queueing claim. — Verified: two concurrent `_run_agent_fanout(count=6)` calls with a sleeping fake child peaked at 8 concurrent children with the cap at 4. — Fix: one `threading.BoundedSemaphore` per top-level session (or per org run), sized by `effective_max_concurrent`, acquired around each child's run in every spawn path.

11. **major** — `halo_harness/agent/subagent.py:901-910,935-990` — The fan-out pool never checks `parent.abort`. 13. **major** — `halo_harness/roles.py:114-129` — The documented `roles.editor: "external"` switch lives in the same `roles` map, so `configured_role_table()` reads it as a custom role "editor" with model "external". 14. **major** — `halo_harness/controller.py:953-971` + `mcp_cli.py:248-279` + `mcp/oauth.py:152,179-188` + `tui/dialogs/mcp_status.py:128-141` — In the TUI, `/mcp` `l` hides the authorization URL. `run_login` keeps oauth's default `print_fn=print`, and Textual drops `print()` from a worker because halo never calls `begin_capture_print`. 16. **major** — `halo_harness/update.py:139-150,224-243` (+ `scripts/install-halo.ps1:118-121`, `install-halo.sh:112-113`) — Both installers by default clone and run `uv tool install --reinstall .`, which records a non-editable `dir_info` install.
