# Halo 2.0.4: local and LAN Ollama models (rolo, 2026-10-01 ~23:00)

rolo: "2.0.4 let's add research and functionality of local ollama
models. This will be complicated. I want the intuitiveness and ability to
know where these settings are so they can work. One huge issue is that
there are complicated settings that limit the amount of input a model can
take depending on the model and the hardware ... sometimes ollama is
hosted on the network and other halo sessions on different devices should
access it. maybe there should be an analysis of the hardware running the
models ... I do not know if ollama models can even run a full session or
if a breakout window should occur ... maybe it should be a sub agent
resource? ... modular agents from different repos, I want to save that for
later releases."

rolo's setup: Ollama on the Windows host <lan-host>:11434 (RTX 4090,
24 GB; shares the GPU with Plex hardware transcode and ComfyUI), a
"no-think" proxy on 11435 used by agent loops from the Kali VM, model
`bugtrace` among others; `expanded-models` MCP server has `ask_local`.
Known from memory: Ollama 27B loads contributed to Windows low-memory
session drops; Ollama cannot do images on that host.

Fable's position (given in chat, binding for the brief): local models
join as a first-class provider `ol:` on Ollama's NATIVE API, with roles
(main, small, sub-agent, compaction) instead of a breakout window; the
default role for a local model is support, main is opt-in with plain
consequences shown, never a block; the harness owns the context setting
per request so the user never has to find a server knob to make it work;
the gym (2.0.3) decides which local models can run a session.

## Phase 0: research (first worker, docs only, no code)

Write `docs/harness/OLLAMA-RESEARCH.md` from the current Ollama docs and
release notes (verify every item below; mark anything that changed):
- Native API: `/api/chat` (NDJSON stream, `message.content`,
  `message.thinking`, `message.tool_calls` without ids, `done`,
  `done_reason`, timing fields `prompt_eval_count`, `prompt_eval_duration`,
  `eval_count`, `eval_duration`, `load_duration`), `options.num_ctx`,
  `keep_alive`, `think` (bool, and low/medium/high for gpt-oss),
  `format` (json or schema), `/api/tags`, `/api/show` (`model_info` keys:
  `general.parameter_count`, `<family>.context_length`,
  `<family>.block_count`, `<family>.attention.head_count_kv`,
  `<family>.embedding_length`; `details.quantization_level`,
  `details.family`; `capabilities` list incl. `tools`, `thinking`,
  `vision`, `embedding`), `/api/ps` (`size`, `size_vram`, `expires_at`,
  `context_length`), `/api/version`, `/api/embed`.
- OpenAI-compatible endpoint limits: no `options` (so no per-request
  context), tool-call ids synthesised, reasoning exposure, streaming with
  tools; conclude why Halo uses the native API.
- Server settings and WHERE each lives per OS: `OLLAMA_HOST` (bind
  0.0.0.0 for LAN; no authentication exists), `OLLAMA_CONTEXT_LENGTH`
  (default when unset), `OLLAMA_NUM_PARALLEL` (multiplies KV memory),
  `OLLAMA_MAX_LOADED_MODELS`, `OLLAMA_KEEP_ALIVE`, `OLLAMA_KV_CACHE_TYPE`
  (q8_0/q4_0 need `OLLAMA_FLASH_ATTENTION`), `OLLAMA_MAX_QUEUE`,
  `OLLAMA_MODELS`; Windows (user env vars, restart from the tray), Linux
  systemd (`systemctl edit ollama`, `Environment=`), macOS (launchctl or
  the app's settings), Docker (`-e`). Modelfile `PARAMETER num_ctx`.
- Prompt truncation: what the server does when a prompt exceeds
  `num_ctx` (silent truncation from the front, logged server-side), and
  prefix caching behaviour per slot (why a cache-stable system prompt
  matters locally and why `num_parallel` slots split it).
- KV-cache arithmetic: bytes per token = 2 x block_count x head_count_kv
  x head_dim x bytes_per_elem (f16 2, q8_0 1, q4_0 0.5); worked examples
  for the models below on 24 GB, 16 GB, 12 GB and CPU-only.
- Model table for agent use as of the research date, per VRAM tier:
  tool-calling support in the Ollama template, thinking, trained context,
  weights size per quant, expected tok/s class on a 4090; candidates to
  check: gpt-oss:20b, qwen3-coder:30b (MoE A3B), qwen3:32b, devstral,
  mistral-small, glm-4 family, gemma3 (tool status), deepseek-r1 distills
  (no tools), plus whatever is current in 2026. The table is a starting
  list; the gym ranks them.
- Ollama Cloud models (`-cloud` tags, `ollama signin`, API key for
  ollama.com): whether `ol:` can point at ollama.com with a key for free.
- Other local servers with OpenAI-compatible endpoints (LM Studio,
  llama.cpp server, vLLM): what a generic `local:` route would need
  (base URL + model list + context discovery per server) so it can be a
  cheap follow-up, not part of 2.0.4.

## Phase 1: provider `ol:` on the native API

- Config: `ollama.hosts` in `~/.halo/config.json` (`name`, `url`,
  `default: true`, `keep_alive`, `max_ctx`, `num_parallel_hint`); the env
  var `OLLAMA_HOST` seeds the default host; refs `ol:<model>` use the
  default host, `ol:<model>@<hostname>` a named one. Enablement: a host
  answers `/api/version` (background probe with a short timeout; never
  on the UI thread; `BRIDGE_TEST_NO_BACKGROUND_NET` honoured).
- Catalog from `/api/tags` + `/api/show` per model, cached per host with
  a short TTL: name, size, quant, family, parameter count, trained
  context, capabilities (tools, thinking, vision), loaded now (`/api/ps`),
  measured tok/s (from telemetry once seen). Picker columns for local
  models: size, quant, ctx (effective/trained), tools, loaded now, tok/s;
  group label `Ollama (ol:)` plus the host name when several exist.
- Dialect `ollama` in the provider layer: request builder (messages with
  system first, tool results as `role: tool` with `tool_name`, tools in
  OpenAI function shape, `options.num_ctx` computed per request,
  `options.temperature` per family table, `keep_alive` from config,
  `think` from the effort setting: off for low on hybrid models, on
  otherwise, low/medium/high for gpt-oss), NDJSON stream decoder
  (content, thinking, tool_calls accumulated, Halo assigns tool ids,
  `done_reason` length -> provider failure path, `done_reason` load ->
  retry once), timing stats into telemetry (`prompt_tok_s`, `gen_tok_s`,
  `load_ms`, `prompt_eval_count`).
- Context ownership: Halo requests `num_ctx = min(trained context,
  host.max_ctx, fit estimate from Phase 2, 131072)` and budgets
  `max_tokens` against it; compaction triggers at 75 percent of
  `num_ctx` for local routes. Learned token ratio: after every turn,
  compare Halo's estimate with `prompt_eval_count` and keep a per-model
  ratio in the catalog cache so the estimate converges on the server's
  count.
- Tool catalog for local mains: compact tool descriptions (per-family
  flag in model_table.json), built-ins plus ToolSearch for MCP tools,
  cap on wire tools from the host's context class (for example 16 tools
  under 32k).
- Thinking display and the liveness line work unchanged (Part A of the
  liveness brief); `ol:` adds `load_ms` to the phase line as
  `loading model (8 s)` when the first chunk reports a load.
- Tests: a fake Ollama server (`tests/helpers/mock_ollama.py`) serving
  tags, show, ps, version and chat with scripted NDJSON including tool
  calls, thinking, `done_reason` variants, timing fields and the
  truncation case; pinning tests for `num_ctx` on the wire, tool ids,
  keep_alive, think mapping, the learned ratio, picker columns.

## Phase 2: hardware and host analysis (`halo ollama`, `/ollama`)

- One panel and one CLI page per host: version, URL, reachable, models
  loaded now with `size` vs `size_vram` (partial offload shown as
  `offloaded to CPU: 6.2 GB`, with the plain consequence: slow), queue and
  parallel hints, keep_alive policy, and for each model the trained
  context, the effective context Halo will request, the KV bytes per
  token, and the largest context that fits fully in VRAM given the
  loaded set (remote hosts: inferred from `/api/ps` numbers and the
  research arithmetic; local hosts: also `nvidia-smi` or `rocm-smi`
  totals and the other GPU processes, and the server env vars actually
  set, with the per-OS place to change each one).
- Recommendations as sentences, never blocks: `qwen3-coder:30b at 65k
  would offload; 32k fits with q8_0 KV cache`, `two devices share this
  host; set OLLAMA_NUM_PARALLEL=2 on <host> and expect 2x KV memory`.
- Multi-device etiquette: Halo prefers the model already loaded on the
  host (picker badge `loaded now`), uses the configured keep_alive on
  every request so sessions do not fight over it, shows `host busy
  (model loading)` or `queued behind N` from timing and `/api/ps`, and
  warns when a chosen model would evict another loaded model.
- Doctor: `halo doctor` gains an Ollama section with the same facts
  compressed to one line per host.

## Phase 3: roles (local models in a supporting role by default)

- `roles` config: `main`, `small` (summaries, WebFetch digests, hook
  prompts, title generation), `compaction`, `subagent_default`,
  `embeddings` (reserved). Audit and reuse the existing plumbing
  (`--small-model`, `compactionModel`, sub-agent `model:` frontmatter)
  rather than adding a second mechanism. The picker gets a `u` action:
  `use as main / small / sub-agent default / compaction` so roles are set
  without editing JSON; `/roles` shows the current assignment.
- Capability label per local model from measured and declared facts:
  `session-capable` (tools in template, effective ctx >= 32k, gen tok/s
  >= 15 measured or expected), `assistant` (tools but small ctx or slow),
  `chat only` (no tools). Choosing a non-session-capable model as main
  prints the consequences in one sentence (`no tool calling: the model
  can answer but not edit files`) and proceeds.
- `/local <question>` answers inline from the `small` role without
  entering the main transcript or the main model's context (replaces
  rolo's `ask_local` MCP usage); `/local` with no text opens a one-line
  input.
- Sub-agents: `Agent(model: ol:...)` and frontmatter `model: ol:...`
  work; the Explore built-in may default to the local sub-agent model
  when `roles.subagent_default` is local; children get the compact tool
  catalog.
- rolo's no-think proxy on 11435 becomes unnecessary (`think: false`
  per request); docs say so.

## Phase 4: measurement, init, docs

- Gym (2.0.3) run against the local candidates on <host> from the
  Kali VM and from Windows; results into FAMILY-BASELINE and into the
  recommendation table in `docs/OLLAMA.md`.
- Init tab `Ollama (local or LAN)`: URL with discovered defaults
  (`OLLAMA_HOST`, localhost, configured hosts), probe, model list with the

- `docs/OLLAMA.md`: "where every setting lives" (server env per OS,

  slower prefill per turn, more repair hits, compaction more often.
