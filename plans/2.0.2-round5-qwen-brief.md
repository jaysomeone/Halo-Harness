Read plans/WORKER-RULES.md first and follow it exactly (writes of 250 lines

The owner sees "bad calling errors" on a Databricks endpoint named like
`databricks-openjev-qwen35-4b` at work. The research's leading hypothesis:
that endpoint is a decision-only judge model (it answers with a verdict,
not tool calls), and separately the repair layer declares two leak
patterns it never implemented. Build for both, and for the general Qwen3
tool-call conventions, so the fix holds whichever the exact error is.

## What to build

1. Model classification: `providers/model_table.json` (or the profile
   code) gains `capabilities.decision_only` for endpoints matching
   `openjev`/`jev`-judge names; a decision-only model is routed to the
   `judge` role automatically, never used as the session model (the
   picker shows it under a "judge / decision" group with that note), and
   a request that would send tools to it gets one clear error naming the
   role to use. Keep the heuristic in one table entry with a comment, so
   a wrong guess is a one-line fix.
2. Qwen family profile row (Qwen3, Qwen3-Coder, Qwen2.5 on Databricks and
   OpenRouter): Hermes-style `<tool_call>{json}</tool_call>` parsing,
   parallel calls, `arguments` arriving as a JSON string (decode once,
   never twice), no `strict` schemas, `tool_choice` auto only, the Qwen3-
   Coder XML shape (`<function=name><parameter=k>v</parameter></function>`),
   a bare `</think>` prefix stripped, `enable_thinking` passed through the
   gateway's `extra_body` when the gateway supports it. Replay rules for
   tool results follow what the research found per gateway.
3. Repair layer (`providers/hooks.py`, `agent/repair.py`): implement the
   declared-but-missing `python_repr_args` (single-quoted dict/list
   arguments converted to JSON) and `missing_tool_call_opener` (a `}
   </tool_call>` tail without its opener) leak patterns, plus id
   normalisation for calls that carry none. Each pattern gets a mock-
   server scenario from a captured shape in the research doc.
4. Databricks schema limits found in the research: tool schemas with
   `prefixItems` are rewritten to `items` + a description, and a tool with
   more than 16 top-level properties is split or its rarely used keys
   moved under one object, with a learned-rule entry so a new 400 shape is
   remembered per endpoint (`~/.halo/learned_rules.json`, the mechanism
   2.0.3 extends).
5. A `docs/harness/FAMILY-BASELINE-qwen.md` row set with the measured
   mock rates, docs/MODELS.md section "Qwen at work" (what to configure,
   how to read `halo bugreport` for the exact 400 text, where the judge
   routing shows), CHANGELOG [2.0.2] item.
