# Halo 2.0.3 round 2 (DRAFT): implementation rounds for Ollama + Hugging Face

Draft written by the round-1 research worker per
`plans/2.0.3-ollama-round1-research-brief.md`'s deliverable list. Not
binding until Fable reviews it. Builds on `docs/harness/
LOCAL-MODELS-RESEARCH.md` (this round's research doc) and
`plans/2.0.5-ollama-brief.md` (the original Ollama-only design, written
under its old number; still the reference for Ollama-specific detail
this draft doesn't repeat). Scope per `plans/ROADMAP.md`'s "ADDED
2026-10-03" section: 2.0.3 covers Ollama (local, LAN, cloud) **and**
Hugging Face (router, dedicated endpoints, local OpenAI-compatible
servers) behind one shared `/local` discovery view. The model-gym
ranking stays deferred to 2.0.5; this release ships the capability
probe described in research doc section 6 instead.

Round numbering continues from round 1 (this research round). Each
round below is sized to land independently and leave both suites green.

## Round 2: `ol:` provider on the native API

- `halo_harness/providers/`: a new `ollama` dialect alongside the
  existing `openai`/`anthropic-passthrough` dialects `profiles.py`
  already resolves (`resolve_profile`, `ProviderProfile` -- follow the
  existing shape, don't add a second mechanism). Request builder: native
  `/api/chat` body, `options.num_ctx` on every request (research doc
  Q1/Q2: the OpenAI shim has no equivalent, and relying on a Modelfile
  default is unconfirmed/unnecessary once Halo always sends the field),
  `keep_alive` from host config, `think` mapped from the session's
  effort setting, tools in the already-OpenAI-shaped function format
  the native API also expects.
- NDJSON streaming decoder: accumulate `message.content`,
  `message.thinking`, `message.tool_calls`; **synthesize tool-call ids**
  on the way in (research doc Q1: Ollama sends none, only a 0-based
  `index`) so the rest of the tool-result/replay path never needs a
  second code path for this one provider. Map `done_reason: "length"`
  to the existing length-stop handling; `"load"`/`"unload"` semantics
  are **unconfirmed** (research doc Q1) -- treat `"load"` as "retry
  once" per the 2.0.5 brief's own assumption, but add a pinning test
  that would fail loudly if a live server's actual behavior disagrees,
  so round 3's live-check (below) has something concrete to check
  against.
- Host config: `ollama.hosts` (`name`, `url`, `default`, `keep_alive`,
  `max_ctx`, `num_parallel_hint`, optional `api_key` for a cloud entry --
  research doc Q7). `OLLAMA_HOST` seeds the default host if set.
  Enablement probe: background `GET /api/version` with a short timeout,
  honoring `BRIDGE_TEST_NO_BACKGROUND_NET` like every other background
  probe in the codebase.
- Catalog: `/api/tags` + `/api/show` per model, cached per host with a
  short TTL; capture `model_info["<family>.context_length"]` (trained
  context), `details.quantization_level`/`family`, and `capabilities`.
- **Capability probe** (research doc Q5/Q6, replacing the deferred gym
  for this release): one cheap real tool-call turn per newly-seen model
  digest, cached; records whether `tool_calls` actually came back
  non-empty, independent of what `capabilities` claims. Exposed later in
  the picker/`/local` as a measured badge, not a vendor claim.
- Context ownership: `num_ctx = min(trained context, host.max_ctx,
  fit estimate, 131072)`; compaction trigger at 75% for local routes.
- Tests: `tests/helpers/mock_ollama.py`, same shape as
  `tests/helpers/mock_openai.py` (`BaseHTTPRequestHandler` +
  `ThreadingMixIn`, `free_port()`) -- serves `/api/version`, `/api/tags`,
  `/api/show`, `/api/ps`, and scripted NDJSON `/api/chat` covering: plain
  text, `tool_calls` (single and parallel), `thinking`, each
  `done_reason` value, timing fields, and a prompt that exceeds the
  scripted `num_ctx` (truncation case). Pinning tests: `num_ctx` actually
  on the wire every request, synthesized tool-call ids stable across a
  multi-turn replay, `keep_alive` forwarded, `think` mapping per effort
  level, capability-probe result cached and not re-sent on a second
  catalog read within the TTL.

## Round 3: hardware/host analysis (`/ollama`) and roles

- One panel/CLI page per host (research doc Q3): version, URL,
  reachable, loaded models (`size` vs `size_vram`, offload shown as a
  plain sentence, never a block), the per-model trained vs. effective
  context and the KV-bytes-per-token figure computed from
  `model_info` (research doc Q2's formula -- mark the formula's origin
  as "standard GGML/llama.cpp accounting, not independently re-derived
  this round" in the panel's own help text, not just in the research
  doc). Remote hosts: inferred from `/api/ps` numbers alone. Local
  hosts: also the OS GPU-memory tool for the detected vendor (research
  doc Q3 -- `nvidia-smi`, `rocm-smi`/sysfs, `system_profiler`; every one
  of these is flagged **UNCONFIRMED at the exact-flag level** in the
  research doc, so this round's implementation work doubles as the
  live verification: if the chosen flags don't parse on a real machine,
  fix the research doc too).
- `halo doctor` gains an Ollama section, one line per host.
- Roles: local models default to a supporting role
  (`small`/`researcher`/`judge`/`subagent_default`), never `main` by
  default; wire into the existing `halo_harness/roles.py` role table
  (`ROLE_NAMES`, `_role_value_parts`, the existing precedence chain) --
  do not add a second roles mechanism. Picker gets a `u` action to set
  a role without editing JSON. Choosing a non-session-capable local
  model as main prints the plain consequence sentence and proceeds.
- `/local <question>` (Ollama-only in this round; Hugging Face joins in
  round 5) answers from the `small` role inline.
- Tests: extend `mock_ollama.py`'s scripted responses with a partial-
  offload case (`size` > `size_vram`) and a multi-host config; pinning
  tests for the offload sentence wording, the role table round-trip,
  and `/local` not touching the main transcript's context.
- Hand-off from round 2 (2026-10-04, after the live run on a 24 GB card):
  `providers.ollama.compute_num_ctx(trained, host.max_ctx, fit_estimate)`
  already takes the fit estimate but every caller passes `None`, so a
  27B model whose trained context is 262144 got `num_ctx` 131072 (the hard
  cap) and the server accepted it only because that card had the room.
  This round owns `fit_estimate`: from the KV-bytes-per-token figure and
  the detected free GPU memory (local host) or `/api/ps` numbers (remote),
  pick the largest context that fits with the weights resident, round
  down to a power of two, and thread it through the one helper
  `agent/loop.py` uses (`_build_ollama_body_for_ref`). `self.model_
  profile.context_tokens` already follows the sent `num_ctx`, so the
  status bar and compaction threshold come along for free. Also from the
  live run: every request carried the full 24-tool catalog (about 10k
  prompt tokens before the user says a word); size the catalog to the
  host's context class here (the deferred capping item), and show the
  per-request prompt cost in the host panel so the trade-off is visible.

## Round 4: `hf:` route -- router and dedicated endpoints

- New `huggingface` dialect, OpenAI-compatible (reuse the existing
  `openai`-shaped request/response code paths -- research doc Q9
  confirmed the router's chat-completions path is a drop-in OpenAI
  shape, so this should be mostly config/routing, not a new wire
  format):
  - `hf:<org>/<model>` (optional `:fastest`/`:cheapest`/`:preferred`/
    `:<provider>` suffix, passed through verbatim in the `model`
    field) -> `https://router.huggingface.co/v1`, `Authorization:
    Bearer $HF_TOKEN`.
  - `hf:endpoint/<name>` -> looks up `{url, token}` from a new
    `huggingface.endpoints` config list (mirrors `ollama.hosts`'
    shape); each entry is a fully separate base URL + token (research
    doc Q9: dedicated endpoints don't share the router's auth or URL).
- Catalog: `GET /v1/models` on the router (research doc Q9: this
  response includes per-provider pricing/context-length/latency where
  available -- surface context length the same way the Ollama catalog
  surfaces trained context, so the picker's context column means the
  same thing across both routes).
- Tests: a fake OpenAI-compatible server in `tests/helpers/` --
  reuse `tests/helpers/mock_openai.py`'s `MockUpstream`/`SCENARIOS`
  machinery rather than writing a second one from scratch; parameterize
  its base path so the same scripted scenarios serve as the router
  stand-in (round 4), the dedicated-endpoint stand-in (round 4, same
  handler on a second port with a different token check), and the
  `hf:local/*` stand-in (round 5, same handler again on 8080/8000/1234).
  Pinning tests: provider-suffix passthrough on the `model` field,
  bearer header built from `HF_TOKEN` vs. a configured endpoint token
  (never cross-wired), `X-HF-Bill-To` header when an org is configured
  (research doc Q9) -- do not store or log the token value itself in
  any test assertion message.

## Round 5: `hf:local/*`, shared `/local` discovery, init tab

- `hf:local/<model>` resolves against `huggingface.local_servers`
  config plus auto-detection on the default ports research doc Q8
  confirmed (8080 llama-server, 8000 vLLM/`transformers serve`, 1234 LM
  Studio, 8080 TGI -- note in code comments that 8000 is shared by two
  different servers and both are treated identically since both are
  plain OpenAI-compatible, per the research doc). Since most of these
  servers fix context length at server-launch time rather than per
  request (research doc Q8/Q10), Halo reads back whatever the server
  reports instead of trying to request a specific size.
- Manual server entries (added 2026-10-04 after the round 2 live-check
  staging): `huggingface.local_servers` is a list of `{name, url,
  api_key, default}` just like `ollama.hosts`, and `hf:local/<model>@<name>`
  picks an entry by name. Auto-detection only ever finds servers on the
  machine Halo runs on; a LAN box that fronts its models with an
  OpenAI-compatible proxy behind a bearer token (the common "one GPU box,
  several laptops" setup) is reachable ONLY through a manual entry, so
  `api_key` must be sent as `Authorization: Bearer` on every call to that
  entry and the init tab must offer "add a server by URL (+ key)" next to
  auto-detect. A manual entry is never probed in the background unless the
  user asks (`/local refresh`); the enablement probe for it is the same
  `GET /v1/models` the auto-detected servers get.
- HF Hub cache scan: walk `~/.cache/huggingface/hub/models--*` (or
  `$HF_HUB_CACHE` if set) for models present on disk but not
  necessarily being served right now -- second input to `/local`
  alongside the live server probe and the Ollama catalog.
- Shared `/local` view merges all three sources (Ollama hosts, HF cache,
  HF/Ollama running servers) into one list: size, quant where known,
  context, capability badges (same probe idea as round 2's, generalized
  across providers), "loaded now" where the concept applies, group
  label per provider/host.
- `/local <question>` now also considers `hf:` small-role refs.
- Init tab: `Ollama (local or LAN)` (round 2/3) plus a new `Hugging
  Face` step -- paste `HF_TOKEN`, add a dedicated endpoint, or rely on
  auto-detection; both steps skippable, matching the existing round-7
  init-wizard Back/Skip/Next pattern.
- Tests: a background-probe test across all the default ports at once
  using the round-4 fake-server helper bound to several of them
  simultaneously; a Hub-cache-scan test against a fixture cache
  directory tree (never the real `~/.cache/huggingface`); pinning tests
  for `/local`'s merged list ordering and group labels.

- Lean prompt for small windows (follow-up measured on the round 3 live
  run, 2026-10-04): a single-word turn on a 27B model fitted to a 16384
  context cost about 10.2k prompt tokens before the user said anything:
  roughly 6.7k of tool definitions for the 24 built-ins plus the system
  prompt. The round 3 tool cap cannot go below the built-in set (the
  frozen catalog seeds every built-in), so for windows of 16k and below
  Halo needs a lean mode: compact tool descriptions (one line each, the
  long guidance moved behind ToolSearch), a reduced built-in set chosen
  per context class, and a shorter system prompt variant; show the
  resulting prompt cost in `/ollama`. Decide in this round whether it
  ships in 2.0.3 or moves to 2.0.5 hardening, and say so in the docs.
