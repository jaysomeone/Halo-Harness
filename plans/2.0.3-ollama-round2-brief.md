# Halo 2.0.3 round 2 (DRAFT): implementation rounds for Ollama + Hugging Face

Draft written by the round-1 research worker per
`plans/2.0.3-ollama-round1-research-brief.md`'s deliverable list. Not
binding until Fable reviews it. Builds on `docs/harness/
LOCAL-MODELS-RESEARCH.md` (this round's research doc) and
`plans/2.0.5-ollama-brief.md` (the original Ollama-only design, written
under its old number; still the reference for Ollama-specific detail
this draft doesn't repeat). Scope per `plans/ROADMAP.md`'s "ADDED
2026-10-03" section: 2.0.3 covers Ollama (local, LAN, cloud) **and**
Hugging Face (router, dedicated endpoints, local OpenAI-compatible
servers) behind one shared `/local` discovery view. The model-gym
ranking stays deferred to 2.0.5; this release ships the capability
probe described in research doc section 6 instead.

Round numbering continues from round 1 (this research round). Each
round below is sized to land independently and leave both suites green.

## Round 2: `ol:` provider on the native API

- `halo_harness/providers/`: a new `ollama` dialect alongside the
  existing `openai`/`anthropic-passthrough` dialects `profiles.py`
  already resolves (`resolve_profile`, `ProviderProfile` -- follow the
  existing shape, don't add a second mechanism). Request builder: native
  `/api/chat` body, `options.num_ctx` on every request (research doc
  Q1/Q2: the OpenAI shim has no equivalent, and relying on a Modelfile
  default is unconfirmed/unnecessary once Halo always sends the field),
  `keep_alive` from host config, `think` mapped from the session's
  effort setting, tools in the already-OpenAI-shaped function format
  the native API also expects.
- NDJSON streaming decoder: accumulate `message.content`,
  `message.thinking`, `message.tool_calls`; **synthesize tool-call ids**
  on the way in (research doc Q1: Ollama sends none, only a 0-based
  `index`) so the rest of the tool-result/replay path never needs a
  second code path for this one provider. Map `done_reason: "length"`
  to the existing length-stop handling; `"load"`/`"unload"` semantics
  are **unconfirmed** (research doc Q1) -- treat `"load"` as "retry
  once" per the 2.0.5 brief's own assumption, but add a pinning test
  that would fail loudly if a live server's actual behavior disagrees,
  so round 3's live-check (below) has something concrete to check
  against.
- Host config: `ollama.hosts` (`name`, `url`, `default`, `keep_alive`,
  `max_ctx`, `num_parallel_hint`, optional `api_key` for a cloud entry --
  research doc Q7). `OLLAMA_HOST` seeds the default host if set.
  Enablement probe: background `GET /api/version` with a short timeout,
  honoring `BRIDGE_TEST_NO_BACKGROUND_NET` like every other background
  probe in the codebase.
- Catalog: `/api/tags` + `/api/show` per model, cached per host with a
  short TTL; capture `model_info["<family>.context_length"]` (trained
  context), `details.quantization_level`/`family`, and `capabilities`.
- **Capability probe** (research doc Q5/Q6, replacing the deferred gym
  for this release): one cheap real tool-call turn per newly-seen model
  digest, cached; records whether `tool_calls` actually came back
  non-empty, independent of what `capabilities` claims. Exposed later in
  the picker/`/local` as a measured badge, not a vendor claim.
- Context ownership: `num_ctx = min(trained context, host.max_ctx,
  fit estimate, 131072)`; compaction trigger at 75% for local routes.
- Tests: `tests/helpers/mock_ollama.py`, same shape as
  `tests/helpers/mock_openai.py` (`BaseHTTPRequestHandler` +
  `ThreadingMixIn`, `free_port()`) -- serves `/api/version`, `/api/tags`,
  `/api/show`, `/api/ps`, and scripted NDJSON `/api/chat` covering: plain
  text, `tool_calls` (single and parallel), `thinking`, each
  `done_reason` value, timing fields, and a prompt that exceeds the
  scripted `num_ctx` (truncation case). Pinning tests: `num_ctx` actually
  on the wire every request, synthesized tool-call ids stable across a
  multi-turn replay, `keep_alive` forwarded, `think` mapping per effort
  level, capability-probe result cached and not re-sent on a second
  catalog read within the TTL.

## Round 3: hardware/host analysis (`/ollama`) and roles

- One panel/CLI page per host (research doc Q3): version, URL,
  reachable, loaded models (`size` vs `size_vram`, offload shown as a
  plain sentence, never a block), the per-model trained vs. effective
  context and the KV-bytes-per-token figure computed from
  `model_info` (research doc Q2's formula -- mark the formula's origin
  as "standard GGML/llama.cpp accounting, not independently re-derived
  this round" in the panel's own help text, not just in the research
  doc). Remote hosts: inferred from `/api/ps` numbers alone. Local
  hosts: also the OS GPU-memory tool for the detected vendor (research
  doc Q3 -- `nvidia-smi`, `rocm-smi`/sysfs, `system_profiler`; every one
  of these is flagged **UNCONFIRMED at the exact-flag level** in the
  research doc, so this round's implementation work doubles as the
  live verification: if the chosen flags don't parse on a real machine,
  fix the research doc too).
- `halo doctor` gains an Ollama section, one line per host.
- Roles: local models default to a supporting role
  (`small`/`researcher`/`judge`/`subagent_default`), never `main` by
  default; wire into the existing `halo_harness/roles.py` role table
  (`ROLE_NAMES`, `_role_value_parts`, the existing precedence chain) --
  do not add a second roles mechanism. Picker gets a `u` action to set
  a role without editing JSON. Choosing a non-session-capable local
  model as main prints the plain consequence sentence and proceeds.
- `/local <question>` (Ollama-only in this round; Hugging Face joins in
  round 5) answers from the `small` role inline.
- Tests: extend `mock_ollama.py`'s scripted responses with a partial-
  offload case (`size` > `size_vram`) and a multi-host config; pinning
  tests for the offload sentence wording, the role table round-trip,
  and `/local` not touching the main transcript's context.
- Hand-off from round 2 (2026-10-04, after the live run on a 24 GB card):
  `providers.ollama.compute_num_ctx(trained, host.max_ctx, fit_estimate)`
  already takes the fit estimate but every caller passes `None`, so a
  27B model whose trained context is 262144 got `num_ctx` 131072 (the hard
  cap) and the server accepted it only because that card had the room.
  This round owns `fit_estimate`: from the KV-bytes-per-token figure and
  the detected free GPU memory (local host) or `/api/ps` numbers (remote),
  pick the largest context that fits with the weights resident, round
  down to a power of two, and thread it through the one helper
  `agent/loop.py` uses (`_build_ollama_body_for_ref`). `self.model_
  profile.context_tokens` already follows the sent `num_ctx`, so the
  status bar and compaction threshold come along for free. Also from the
  live run: every request carried the full 24-tool catalog (about 10k
  prompt tokens before the user says a word); size the catalog to the
  host's context class here (the deferred capping item), and show the
  per-request prompt cost in the host panel so the trade-off is visible.

## Round 4: `hf:` route -- router and dedicated endpoints

- New `huggingface` dialect, OpenAI-compatible (reuse the existing
  `openai`-shaped request/response code paths -- research doc Q9
  confirmed the router's chat-completions path is a drop-in OpenAI
  shape, so this should be mostly config/routing, not a new wire
  format):
  - `hf:<org>/<model>` (optional `:fastest`/`:cheapest`/`:preferred`/
    `:<provider>` suffix, passed through verbatim in the `model`
    field) -> `https://router.huggingface.co/v1`, `Authorization:
    Bearer $HF_TOKEN`.
  - `hf:endpoint/<name>` -> looks up `{url, token}` from a new
    `huggingface.endpoints` config list (mirrors `ollama.hosts`'
    shape); each entry is a fully separate base URL + token (research
    doc Q9: dedicated endpoints don't share the router's auth or URL).
- Catalog: `GET /v1/models` on the router (research doc Q9: this
  response includes per-provider pricing/context-length/latency where
  available -- surface context length the same way the Ollama catalog
  surfaces trained context, so the picker's context column means the
  same thing across both routes).
- Tests: a fake OpenAI-compatible server in `tests/helpers/` --
  reuse `tests/helpers/mock_openai.py`'s `MockUpstream`/`SCENARIOS`
  machinery rather than writing a second one from scratch; parameterize
  its base path so the same scripted scenarios serve as the router
  stand-in (round 4), the dedicated-endpoint stand-in (round 4, same
  handler on a second port with a different token check), and the
  `hf:local/*` stand-in (round 5, same handler again on 8080/8000/1234).
  Pinning tests: provider-suffix passthrough on the `model` field,
  bearer header built from `HF_TOKEN` vs. a configured endpoint token
  (never cross-wired), `X-HF-Bill-To` header when an org is configured
  (research doc Q9) -- do not store or log the token value itself in
  any test assertion message.

## Round 5: `hf:local/*`, shared `/local` discovery, init tab

- `hf:local/<model>` resolves against `huggingface.local_servers`
  config plus auto-detection on the default ports research doc Q8
  confirmed (8080 llama-server, 8000 vLLM/`transformers serve`, 1234 LM
  Studio, 8080 TGI -- note in code comments that 8000 is shared by two
  different servers and both are treated identically since both are
  plain OpenAI-compatible, per the research doc). Since most of these
  servers fix context length at server-launch time rather than per
  request (research doc Q8/Q10), Halo reads back whatever the server
  reports instead of trying to request a specific size.
- Manual server entries (added 2026-10-04 after the round 2 live-check
  staging): `huggingface.local_servers` is a list of `{name, url,
  api_key, default}` just like `ollama.hosts`, and `hf:local/<model>@<name>`
  picks an entry by name. Auto-detection only ever finds servers on the
  machine Halo runs on; a LAN box that fronts its models with an
  OpenAI-compatible proxy behind a bearer token (the common "one GPU box,
  several laptops" setup) is reachable ONLY through a manual entry, so
  `api_key` must be sent as `Authorization: Bearer` on every call to that
  entry and the init tab must offer "add a server by URL (+ key)" next to
  auto-detect. A manual entry is never probed in the background unless the
  user asks (`/local refresh`); the enablement probe for it is the same
  `GET /v1/models` the auto-detected servers get.
- HF Hub cache scan: walk `~/.cache/huggingface/hub/models--*` (or
  `$HF_HUB_CACHE` if set) for models present on disk but not
  necessarily being served right now -- second input to `/local`
  alongside the live server probe and the Ollama catalog.
- Shared `/local` view merges all three sources (Ollama hosts, HF cache,
  HF/Ollama running servers) into one list: size, quant where known,
  context, capability badges (same probe idea as round 2's, generalized
  across providers), "loaded now" where the concept applies, group
  label per provider/host.
- `/local <question>` now also considers `hf:` small-role refs.
- Init tab: `Ollama (local or LAN)` (round 2/3) plus a new `Hugging
  Face` step -- paste `HF_TOKEN`, add a dedicated endpoint, or rely on
  auto-detection; both steps skippable, matching the existing round-7
  init-wizard Back/Skip/Next pattern.
- Tests: a background-probe test across all the default ports at once
  using the round-4 fake-server helper bound to several of them
  simultaneously; a Hub-cache-scan test against a fixture cache
  directory tree (never the real `~/.cache/huggingface`); pinning tests
  for `/local`'s merged list ordering and group labels.

## Round 5b: local-model excellence (added 2026-10-04 at rolo's request)

rolo: "being able to use local llms as best as possible or better than
anything out there would be a huge win" and "maybe halo needs gpu tools
and intuitive know how to pull gpu info". Measured facts this round rests
on (2026-10-04 live runs): a remote host with nothing loaded has no fit
estimate, so the 131072 cap loaded a 30B MoE partially offloaded on a
24 GB card; a local host fitted the same class of model to 16384 fully in
GPU; a one-word turn costs about 10k prompt tokens of system prompt plus
24 tool definitions; the Windows tray app's own "expose" switch decides
the bind, not the environment.

- **Fit calibration from Ollama's own telemetry, no GPU tool required.**
  `halo ollama calibrate <model> [--host NAME]`: load the model at a
  candidate `num_ctx` (the GPU-based estimate when a local read exists,
  else 32768), read `/api/ps` back (`size` vs `size_vram`,
  `context_length`), and step down by powers of two until the model is
  fully resident, then record `{host, model digest, max_full_gpu_ctx,
  measured_at, ollama_version}` in `~/.halo/ollama-fit.json`. Run it
  automatically the first time a model is used on a host (one plain
  notice; opt out with `ollama.auto_calibrate: false`). `compute_num_ctx`
  consults the learned cap first, then `ollama.hosts[].max_ctx`, then the
  live fit estimate, then (remote host, nothing known) a conservative
  32768 default, never the 131072 cap for an unknown remote host. `/ollama`
  shows the learned cap per model and a "what fits" column.
- **Optional GPU read for remote hosts.** `ollama.hosts[].ssh:
  "user@host"` runs the same probe commands round 3 uses locally over ssh
  (BatchMode, 3 s timeout, read-only), so a remote Linux or Windows box
  with sshd gets real free-memory numbers; documented as optional because
  calibration already works without it. Never required, never prompted for.
- **Stable request prefix for KV reuse.** Ollama and llama.cpp reuse the
  cached prefix when the prompt is byte-identical up to the first change,
  so the system prompt and tool list must not carry per-turn volatile
  content on `ol:` sessions (timestamps, context percentages, counters)
  and `options` must be identical across turns. Audit and pin it; measure
  `prompt_eval_count` across two turns on the live host in round 6 and
  record the hit rate in the docs.
- **VRAM-aware role defaults.** When the main model is `ol:` on a host
  that cannot hold a second model beside it, the small / researcher /
  judge / subagent roles default to the same loaded model instead of a
  different local one, so a sub-agent never evicts the main model.
  `/local <question>` follows the same rule.
- **Throughput in the UI.** For `ol:` turns the status bar's model chip
  shows tokens per second and prefill seconds from `/api/chat`'s
  `eval_count` / `eval_duration` / `prompt_eval_duration`, and an
  "offloaded" marker when `/api/ps` says so; `halo ollama` prints the
  last turn's numbers.
- **Host setup checklist.** `halo ollama doctor [--host NAME]` prints what
  the host exposes (version, loaded context, offload) and the documented
  recommendations it cannot read (OLLAMA_FLASH_ATTENTION=1,
  OLLAMA_KV_CACHE_TYPE=q8_0, OLLAMA_NUM_PARALLEL=1 on a single-user box,
  OLLAMA_KEEP_ALIVE, and on Windows the tray app's "Expose Ollama to the
  network" switch, which overrides OLLAMA_HOST), with the per-OS place each
  one lives. Plain sentences, never a block.
- **The machine Halo runs on is a host too, and the Mac is different.**
  rolo (2026-10-04): the PC's Ollama serves the LAN, but the Mac has its
  own Ollama models that are NOT shared on the network; Halo on the Mac
  must scan and tune that loopback daemon on its own terms, and Hugging
  Face local servers get the same treatment as Ollama. So:
  - Apple Silicon memory model: unified memory, no discrete VRAM. The
    local probe reads total memory (`sysctl hw.memsize`), the chip and
    memory line from `system_profiler SPDisplaysDataType` (round 3's probe,
    still unconfirmed on real hardware), and treats the GPU-usable share as
    the OS default (about two thirds to three quarters of RAM depending on
    the machine; `sysctl iogpu.wired_limit_mb` when set raises it). The
    fit estimate uses that share minus what the OS and apps hold; the
    calibration step above is the ground truth and runs the same way.
  - macOS tuning checklist in `halo ollama doctor`: the Ollama menu-bar
    app's "Expose to network" switch (off by default, same settings-store
    override as Windows: the environment alone does not change the bind),
    `OLLAMA_FLASH_ATTENTION=1` and `OLLAMA_KV_CACHE_TYPE=q8_0` (Metal
    supports both), `OLLAMA_CONTEXT_LENGTH`, keep-alive, and HOW to set
    environment variables for a menu-bar app on macOS (`launchctl setenv`
    plus an app restart) -- the research doc marks the macOS method
    unconfirmed; rolo's Mac is the live check for it (he runs `halo ollama
    doctor` there and pastes the output; the worker cannot reach the Mac).
    A loopback-only host gets one plain line: "this daemon is reachable
    from this machine only; to share it on the LAN flip <switch>".
  - Hugging Face on the Mac: detect `mlx_lm.server` (Apple's MLX runtime,
    OpenAI-compatible, default port 8080 -- confirm against the mlx-lm
    docs and record it in the research doc) alongside llama-server and LM
    Studio; list MLX models in the HF hub cache (`mlx-community/*`) as
    runnable through it; LM Studio's own model folder (`~/.lmstudio/models`
    or the path its settings name) joins the hub-cache scan as a source.
  - Same tuning story for HF local servers: context is fixed at launch, so
    the doctor prints the launch flags that fit this machine's memory
    (`llama-server -c <fit> -ngl 99 -fa on`, `mlx_lm.server` options, LM
    Studio's context setting) computed from the same fit arithmetic, and
    reads back what the running server reports to confirm.
  - A LAN host that is loopback-only shows up in `/local` from another
    machine as "not reachable from here" with that same one-line hint,
    never as an error.
- **Reliable tool calls from small models (added 2026-10-04, rolo asked
  what gives Halo the edge).** Local models fail mostly by emitting
  malformed or half-formed tool calls, not by choosing the wrong tool. Two
  measures: (1) when the host supports constrained decoding (Ollama's
  `format` with a JSON schema on local hosts; llama-server's
  `json_schema`), a turn that is expected to call a tool sends the tool
  schema as the output constraint so the call is well-formed by
  construction, falling back to free decoding when the host rejects it or
  when the model should be free to answer in prose; (2) a repair loop:
  a tool call that fails to parse is answered with the exact schema and
  the parse error once, locally, before anything reaches the user. Both
  behind the `ollama`/`huggingface` profiles only; every other dialect is
  untouched. Pin both with mock scenarios (constrained request on the
  wire, fallback on a 400, one repair round and then a plain error).
- **The wizard detects before it asks.** The local-models wizard step
  opens with what it found (GPU or unified memory, Ollama and its models,
  running servers, model folders) and recommends what fits: for each
  installed model the largest fully-resident context, and for a machine
  with free room one or two model classes and quantizations that would fit
  with a 32k context, as plain sentences. No downloads from the wizard.
- Tests: calibration stepping against scripted `/api/ps` sequences
  (fully resident on the first try, after two steps, never), learned-cap
  precedence over host.max_ctx over live fit over the remote default, the
  ssh probe behind an injected runner, the Apple memory-share arithmetic
  with injected sysctl/system_profiler output, the mlx_lm and LM Studio
  detection against the parameterized fake and a fixture folder,
  prefix-stability pinning on the built request, VRAM-aware role defaults,
  the status-bar fields, and the doctor checklist text per OS.

## Round 5c: find local model files and make them usable (added 2026-10-04)

rolo: "halo should be able to find huggingface models saved locally and
use them ... have an option to tell halo where they are either in a
session or in the wizard." A Hugging Face model on disk is inert until a
runtime loads it, so discovery alone is not "use": this round closes the
gap in three ways, each a plain choice the user makes once.

- **Discovery, with the user in control of where.** Sources: the HF hub
  cache (round 5), LM Studio's model folder, Ollama's own store (already
  the catalog), and `huggingface.model_dirs`, a user list of folders
  scanned recursively for `.gguf` files, safetensors model folders (a
  `config.json` beside `*.safetensors`) and MLX folders. `/local add
  <path>` and `/local forget <path>` manage that list in a session; the
  wizard gets a "Local models" step (detects Ollama and running servers,
  scans the default caches, offers "add a folder", and asks which runtime
  to prefer for files that are not served yet). `halo local` shows every
  file-backed model with its format, size and whether anything can run it
  here.
- **Read the file, not the server, for the fit.** A GGUF header carries
  the architecture, trained context length, layer count, KV heads and head
  dimension, so the KV-bytes-per-token figure and the fit estimate come
  straight from the file before anything is loaded; a safetensors folder's
  `config.json` gives the same for transformers models. Reuse round 3's
  arithmetic; no new formula.
- **Use it, option A: serve it with a managed runtime.** `halo local serve
  <model> [--runtime llama-server|mlx_lm|lmstudio]` and the `/local` view's
  `s` key start a child process on a free loopback port with the fitted
  context (`llama-server -m <file> -c <fit> -ngl 99 -fa on --port <p>`;
  `mlx_lm.server --model <dir> --port <p>` on Apple Silicon), record it in
  `~/.halo/run/local-servers.json` (pid, port, model, started), and
  register it as an `hf:local/<model>` entry for this session. Stopped
  when Halo exits unless `keep: true` is set; `halo local stop <model>`
  stops it. When no runtime is present, Halo offers to fetch the pinned
  llama.cpp release for this OS and GPU (CUDA, Metal, CPU) into
  `~/.halo/runtimes/`, verified against the asset `digest` the GitHub
  Releases API reports for that exact asset (round 5a found that llama.cpp
  publishes NO checksum file of its own; see docs/harness/GPU-RESEARCH.md,
  which also gives the asset-name table and the driver-version rule for
  picking the CUDA build), only after a plain consent sentence that names
  the size and the URL; declining prints the one-line install hint per OS
  (brew, winget,
  the release page) and stops there. Never silent, never on PATH, removed
  by `halo local runtime remove`. (rolo 2026-10-04 asked for "no server
  to set up"; the decision is a managed runtime the user never configures,
  not in-process inference: same engine and speed, keeps the model warm
  across sessions, keeps Halo's install free of compiled bindings, and
  still serves the LAN topology. An in-process MLX backend for Apple
  Silicon is parked as a 2.0.5 experiment, see ROADMAP.)
- **Use it, option B: import into Ollama.** For a GGUF on a machine that
  runs Ollama, `halo local import <model>` writes a Modelfile (`FROM
  <path>`) and runs `ollama create <name>`, after a plain sentence that
  says the file will be copied into Ollama's store and how large it is;
  the result is an ordinary `ol:<name>` with all of rounds 2, 3 and 5b's
  tuning. Safetensors import is offered only for architectures Ollama
  documents as importable; otherwise option A is the answer.
- **Roles follow.** A file-backed model that becomes servable gets the
  same default role treatment as any other local model (small by default,
  picker `u` to change).
- Tests: GGUF header parsing against tiny hand-built fixture files (never
  a real model), the safetensors `config.json` path, the folder scan
  against a fixture tree with all three formats, the managed-server
  registry (start, record, stop on exit, keep) against a fake runtime
  binary (a Python stub that opens the port and serves the parameterized
  mock_openai shape), the Ollama import path against mock_ollama (the
  `ollama create` call recorded, the consent sentence pinned), `/local add`
  and `forget`, and the wizard step's Save for every path.

## Round 5d: the model gym on this machine, and the acceptance check (moved into 2.0.3 by rolo, 2026-10-04)

- **The gym runs here, on these models.** `halo gym [--models ol:a,ol:b,...]
  [--roles small,judge,...]` runs a fixed task battery against each local
  model on this hardware and scores it per role: tool-call accuracy
  (schema-valid calls out of N, with and without round 5b's constrained
  decoding), edit success (apply a known edit to a fixture file), context
  recall (a needle at 12 percent depth of a prompt sized to the model's
  fitted window), instruction adherence (the plain-sentence reply rules),
  tokens per second and prefill seconds. Results land in
  `~/.halo/gym/<host>/<digest>.json` with the Ollama version, quant and
  fitted context they were measured at, and `halo gym show` prints a
  per-model card. Cloud models may be included for comparison, never by
  default (cost).
- **From data to the role table.** `halo gym propose` turns the scores
  into a role table (the existing roles v2 shape, nothing new): the best
  local model per supporting role, main left as configured unless the user
  asks, with one sentence per choice naming the score behind it; `halo
  roles template import` applies it. The picker shows the gym score beside
  a model when one exists.
- **The 60-second acceptance check.** `halo doctor --local [--model ol:x]`
  loads the model, makes one real tool call, one constrained structured
  output and one compaction summary against a fixture transcript, and
  prints PASS or FAIL per step with the plain reason; it is the "works out
  of the box" proof per machine and the first thing the docs tell a new
  local-model user to run.
- Tests: the task battery against mock_ollama scenarios that pass, fail
  and half-pass; the scoring arithmetic; `propose` on fixture score files
  (ties, a model with no tools capability, a role with no candidate);
  the acceptance check's step sequencing and its FAIL text; nothing in the
  suite ever loads a real model.
