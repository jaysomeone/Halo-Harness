# Halo 3.0.1.1: Halo instances working together with no cloud and no hosted server (research first)

Owner's request (2026-10-03): "Need to find a secure way, with no cloud or
external hosted server, for different halo instances to work together,
like a team at work or friends between each other, or personal separate
sessions connected whether they are on the same network or not. Just
perform immense research on how to make this possible when the time
comes." Do NOT start this research or any implementation until every
task through 2.0.9 is complete and released.

## What "working together" has to cover

- A team at work: several people, several machines, one or more shared
  goals; a work box may sit behind a corporate NAT and a proxy, with no
  inbound ports and no permission to run a server for others.
- Friends: machines on different home networks, each behind its own NAT,
  no shared infrastructure of any kind.
- One person's separate sessions: a laptop, a desktop and a VM, on the same
  LAN or not, sharing state (memory, task board, roles, orgs) and
  delegating work to each other (for example the box with the GPU runs the
  local models for the others; see 2.0.5 Ollama).
- Nothing leaves the participants' own devices except end-to-end encrypted
  traffic between them. No cloud account, no vendor relay, no rendezvous
  service run by anyone outside the group. A relay or rendezvous that one
  participant runs on their own machine for the group is acceptable only
  as a documented fallback, never a requirement for the LAN case.

## Research questions (answer each with sources and a recommendation)

1. Transport and NAT traversal with no third-party server: direct QUIC/
   UDP hole punching (what succeeds behind which NAT types, and how the
   peers exchange their candidate addresses without a server: a pairing
   code typed by a human, a QR code, a Signal message (2.0.8), a file on
   a USB stick); UPnP/NAT-PMP/PCP port mapping; IPv6 end to end; Tor onion
   services (no server of ours, but the Tor network is third-party, so it
   is an opt-in fallback at most); a WireGuard tunnel with manually
   exchanged endpoints and keys. Survey the libraries that do this in the
   open: iroh (QUIC + hole punching, self-hostable relays), libp2p (hole
   punching, relays, mDNS), Hyperswarm/holepunch (DHT based, no servers),
   Yggdrasil, Nebula (needs a lighthouse), Syncthing's discovery and relay
   protocols (self-hostable), Magic Wormhole (PAKE pairing, rendezvous
   self-hostable), Tailscale/Headscale (control server needed, so only as a
   comparison). For each: Python availability, licence, maturity, how it
   behaves on Windows, Linux and macOS, and what it needs that is not ours.
2. Discovery on the same network with no server: mDNS/DNS-SD (Zeroconf),
   UDP broadcast, and how to pair safely the first time (a short PAKE code
   so a stranger on the LAN cannot join).
3. Identity and trust: per-instance long-term keys (Ed25519) with pairing
   through SPAKE2 or a Magic-Wormhole-style code, pinned peer identities
   (the 2.0.8 safety-number model), per-group membership lists signed by
   the group's members, revocation when a laptop is lost, and what a
   teammate can and cannot see (sessions, memory, credentials never).
4. Encryption and protocol: Noise (IK/XX) or TLS 1.3 with pinned raw
   public keys, forward secrecy, replay protection, message signing for
   commands (the 2.0.8 HMAC design generalised), and an audit log per
   instance with hashed content only.
5. What flows between instances, in priority order: a shared task board
   (2.0.2 round 3) with claims and results; delegating a sub-agent to a
   peer (the peer runs it under its own permission rules and returns the
   result, like the Agent tool across machines); shared read-only session
   viewing and steering with the owner's consent (the 2.0.8 control socket
   generalised); shared memory and `plans/`-style handoff files with
   conflict rules; a model pool (one instance's local models, Databricks
   or OpenRouter quota offered to the group with per-peer limits).
6. Offline and intermittent peers: store-and-forward through any peer that
   is online, CRDT or append-only logs for the shared board and memory so
   partitions merge without a coordinator.
7. The corporate case specifically: HTTP proxies, blocked UDP, no inbound
   ports, device policy; what still works (outbound-only connections to a
   peer that happens to be reachable, a teammate's box as the group relay
   on the office LAN, QR/Signal based candidate exchange) and what cannot.
8. Comparison with what exists: Claude Code's own remote control (relay
   through Anthropic), OpenCode and other harnesses' sharing features,
   CRDT-based editors (Automerge, Yjs), the Syncthing and Magic Wormhole
   security papers, the NAT traversal literature (ICE, RFC 8445 and 8489,
   the Tailscale NAT traversal write-up).

## Deliverables of the research round (docs only, no code)

- `docs/harness/P2P-RESEARCH.md`: findings per question with URLs, a
  comparison table of candidate stacks, a threat model (LAN stranger,
  compromised peer, lost device, malicious relay, corporate middlebox),
  and one recommended architecture with a fallback ladder: LAN mDNS +
  direct QUIC first, hole punching with human-exchanged candidates second,
  a participant-run relay third, Tor or Signal-carried candidates as
  opt-ins.
- A draft `plans/3.0.1.1-p2p-brief.md` with rounds, each with tests
  against fake peers, and the live-check plan (two VMs on different
  virtual networks, the Kali VM and the Windows host, a phone hotspot).
- The security review of 2.0.9 is a prerequisite: whatever it finds in the
  control socket, the connector bridge and the permission engine must be
  closed before any instance accepts commands from another.
