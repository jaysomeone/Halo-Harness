# Halo 2.0.3 round 1: local and cloud models research, Ollama and Hugging Face (docs only)

Read plans/WORKER-RULES.md first (no code changes in this round, docs
only; no commit, no push; hand-back format RESULT LINES / FILES TOUCHED /
WHAT YOU FOUND). The design is plans/2.0.5-ollama-brief.md (written under
its old number; Ollama now ships as 2.0.3, see plans/ROADMAP.md
REORDERED). The model-gym ranking it mentions belongs to a later release;
this release gets a built-in capability probe instead.

Write docs/harness/LOCAL-MODELS-RESEARCH.md answering, with URLs and version
numbers as of today:

1. The native Ollama API (`/api/chat`, `/api/generate`, `/api/tags`,
   `/api/show`, `/api/ps`, `/api/embed`): streaming shapes, tool calling
   (which models, the `tools` field, how tool calls come back, parallel
   calls, the `think` option for reasoning models), `options` (num_ctx,
   num_predict, temperature, keep_alive), structured output (`format`),
   images; the OpenAI-compatible endpoint and what it lacks.
2. Context windows: how `num_ctx` defaults, how to read a model's trained
   context from `/api/show`, the memory cost per token of KV cache per
   model family and quantisation, and how to size `num_ctx` for a given
   GPU or RAM budget (a table for 8, 12, 16, 24, 32, 48 GB and CPU-only).
3. Hardware and host analysis: what `/api/ps` and `/api/show` expose
   (size, VRAM split, quantisation), how to detect GPU vendor and memory
   on Windows (nvidia-smi, WMI), Linux (nvidia-smi, rocm-smi, /sys) and
   macOS (system_profiler), and a rule set for "this model will run with
   this context on this host".
4. Network hosting: `OLLAMA_HOST=0.0.0.0`, `OLLAMA_ORIGINS`, the lack of
   auth in Ollama itself and the safe ways to expose it on a LAN (bind to
   the LAN interface, firewall rule, a reverse proxy with a token); how
   another Halo session on a different device discovers and uses it
   (config `ollama.hosts`, mDNS later with 3.0.1.1).
5. Which local model families behave well as a full session model versus
   as a sub-agent resource (tool-call reliability, instruction following,
   context handling): Qwen3, Llama 3.x, Gemma 3, DeepSeek-R1 distills,
   Mistral, Phi-4; cite benchmarks and community results; what Claude
   Code-style harnesses do with local models today.
6. A recommended design for 2.0.3: the `ol:` route (native API, not the
   OpenAI shim), the capability probe (context, tools, streaming, think),
   the `/local` command (hosts, models, VRAM fit, probe results), roles
   for local models (researcher, small, judge first), the init tab, and
   the config keys with defaults.

7. Ollama cloud (owner 2026-10-03: "local and cloud hosted models on
   ollama and huggingface"): how `ollama.com` hosted models work (the
   `-cloud` model tags, `ollama signin` and the API key, pointing
   `OLLAMA_HOST` or the client at `https://ollama.com`, pricing or quotas,
   which models are offered, whether tool calling and streaming behave like
   the local API), and how one `ol:` route can address a local daemon, a LAN
   host and the cloud by host name.
8. Hugging Face, local (owner 2026-10-03: "users should be able to call
   their local hugging face models too like we're doing with ollama";
   research how people actually interact with them): the ways a local HF
   model is run today and what each exposes: `llama-server` from llama.cpp
   (GGUF from the Hub, OpenAI-compatible), `transformers serve` (HF's own
   OpenAI-compatible local server), vLLM, text-generation-inference,
   LM Studio and Jan (OpenAI-compatible, download from the Hub), and plain
   `transformers` in-process (not a server; decide whether Halo should
   ever load weights itself, and recommend against it unless a server is
   absent). How models arrive on disk (`hf download`, the Hub cache under
   `~/.cache/huggingface/hub`, loose GGUF files), how to list what is
   present, how to read a model's context length, chat template and tool-
   calling support from its config, and which runtimes honour tool calling
   and structured output. Default ports and health endpoints to detect a
   running local server (llama-server 8080, vLLM and transformers serve
   8000, LM Studio 1234, TGI 8080 or 3000, Ollama 11434).
9. Hugging Face, cloud: Inference Providers through the HF router
   (`router.huggingface.co`, OpenAI-compatible chat completions,
   `HF_TOKEN`, provider selection and the `:provider` suffix, billing),
   dedicated Inference Endpoints (a per-endpoint URL and token), and the
   older serverless Inference API: what is current, rate limits, which
   models support tools and streaming, how errors look.
10. The recommended design for Halo: one `ol:` route for Ollama (local,
   LAN, cloud by host), one `hf:` route whose target is either the HF
   router (`hf:<org>/<model>` with HF_TOKEN), a dedicated endpoint
   (`hf:endpoint/<name>` from config) or a local OpenAI-compatible server
   (`hf:local/<model>` with `huggingface.local_servers` in config, auto-
   detected on the default ports), a shared "local models" discovery that
   lists Ollama models, HF cache models and running servers in one `/local`
   view with the capability probe, roles for local models, the init tab,
   and the config keys with defaults.

Deliverable: the research doc (`docs/harness/LOCAL-MODELS-RESEARCH.md`,
covering Ollama and Hugging Face), and a draft plans/2.0.3-ollama-round2-
brief.md with the implementation rounds and tests (fake Ollama server in
tests/helpers). Report what you could not confirm.
