## A. Deep code review as a Halo feature

- `/review [target]` and `halo review [target]` where target is a diff
  range, a branch, a pull request number (through `gh`) or the working
  tree; default: the current branch against its base.
- Modelled on Claude Code's current `/code-review` (research its present
  behaviour first and mirror it): reviewers run in parallel, one per
  dimension (correctness, security, performance, tests, docs and
  consistency), each producing typed findings {file, line, severity,
  summary, failure scenario}; then a verification pass adjudicates every
  finding (confirmed / plausible / dismissed with reasons); the result is a
  ranked list rendered as cards in the TUI and as JSON in print mode (the
  same shape as the ReportFindings contract: file, line, short summary,
  summary, failure_scenario, verdict); optional `--fix` runs a fix pass per
  confirmed finding and re-verifies.
- Built on 2.0.2: the `reviewer` role for dimensions, the `judge` role for
  verification, the `coder` role for fixes, an `org` template `code-review`
  so the user can change which model does which part; concurrency from
  `agents.max_concurrent`; the tasks panel shows the reviewers live.
- Docs: `docs/REVIEW.md`; tests with scripted reviewer and judge outputs
  against the mock upstream; a live run on a real branch of this repo as
  the acceptance check.

## A2. Security review of the code (rolo 2026-10-03)

A review of the harness's own attack surface, run by the same reviewer
pattern as the release review (an Opus reviewer with the threat model in
hand, a fix pass, pinning tests), with findings closed before the 2.0.9
tag:

- Credentials: every place a key or token is read, cached, logged, shown
  (bugreport, timeline, debug output) or sent; the env-file and keyring
  paths; redaction coverage (`redact.py`) against the real request and log
  shapes.
- Subprocesses and shells: how Bash/PowerShell commands, hook commands,
  MCP server commands, `claude` child argv and the install script are
  built; quoting, environment inheritance, working directory; process
  group and kill handling.
- File tools: path handling in Read/Write/Edit/Glob/Grep/NotebookEdit and
  the shadow store (traversal, symlinks, the working-dir rules the user
  configured), the worktree code, session logs and `~/.halo` permissions
  (0600/0700 where it matters).
- Trust boundaries: MCP servers and claude.ai connectors (what a malicious
  server response can do to the catalog, the transcript and the tool
  results), OAuth token storage and refresh, the ccbridge MCP, hook
  payloads, settings precedence (managed, user, project, local) and
  `.mcp.json` approval.
- 2.0.8 remote control: pairing, safety-number pinning, HMAC signing and
  replay window, the local control socket's token and permissions, rate
  limits, the audit log; a written threat model with the attacks it stops
  and the ones it does not.
- Permission engine: correctness of the user's own allow/deny/ask rules
  (pattern matching, precedence, mode switching, queued asks), never new
  heuristics.
- Supply chain: pinned dependencies, `pip-audit`/`uv` vulnerability check
  as a CI step (2.0.4), the curl install one-liner's integrity story.
- Output: `docs/harness/SECURITY-REVIEW-2.0.9.md` (findings, fixes,
  residual risks) and a short `SECURITY.md` at the repo root (how to report
  an issue, what the harness does and does not protect against).

## B. Privacy and secret audit (repo, code, docs, tests, git history)

- `halo audit privacy [--history] [--terms FILE]` and
  `tools/privacy_audit.py`: scans the working tree and, with `--history`,
  every revision, for secret shapes (provider keys, tokens, PEM blocks,
  Bearer values, JWTs), LAN addresses and hostnames, home paths and
  usernames, emails, phone numbers, Signal numbers, machine names,
  workspace names, and a user-supplied private terms file that is never
  committed (`~/.halo/privacy-terms.txt`: employer and team names, project
  codenames, colleagues, hostnames). Output: a report listing file, line
  (or commit), category and a masked excerpt (never the full secret);
  exit code non-zero when anything is found; an allowlist file in the repo
  for known fakes (test fixtures carry a `FAKE` marker by convention).
- Remediation workflow documented in `docs/PRIVACY.md`: scrub the tree,
  rotate any real credential found, then, when history carries anything,
  the exact `git filter-repo` recipe with a `--mirror` backup first, the
  force push, and the checklist for clones (owner's machines, teammates),
  GitHub secret-scanning alerts and caches. The history rewrite is the
  owner's decision at that moment, never automatic.
- CI gate (with the 2.0.4 CI work): the audit runs on every push with the
  repo allowlist; the 2.0.4 invariants test gains the same patterns.

  mention the legacy env file by its personal name (functional until
