## W3: open defects, consistency gaps, hygiene, model quality

Section 1, open defects (deferred in 1.0.1):
- Finding 16, single pending-card slot: `tui/app.py` `self.pending_card`
  is one attribute; a second concurrent sub-agent permission ask
  overwrites the first; answering the visible card clears the "permission
  needed" tag while the first child is still blocked. Fix: a queue keyed
  by request_id (like `_permission_waiters`); the status tag stays up
  while any entry remains; cards are shown one at a time in arrival
  order, each naming its agent.
- Finding 18, the "8 s" connect cap is really about 16 s plus a socket
  leak: `providers/http.py:146-180` covers DNS+TCP+proxy+TLS in one 8 s
  budget and phase 1 retries the whole connect once; an abandoned connect
  thread that later succeeds never closes its socket. Fix: no phase-1
  retry for connect-phase failures (a retry cannot help DNS), so the
  documented 8 s is real; a close-callback for the abandoned thread's
  socket.
- Finding 24, misleading "refresh failed": a `/models refresh` or `/dbx`
  that loses the single-flight lock must say "a refresh is already
  running, try again in a second", not "refresh failed".
- Finding 25, silent SIGUSR1 cap: after the per-process dump cap, a
  SIGUSR1 writes one log line saying the cap was reached.
- Finding 26, `claude auth status` on the UI thread for the bare alias
  path (`/model opus` with ANTHROPIC_API_KEY unset): route it through
  the cached status or a worker, never a spawn on the UI thread.

Section 2, provider/env resolution consistency:
- Finding 20: `credentials_present` for OpenRouter/Anthropic/TypeSafe
  reads bare os.environ; give all three the same settings-env-chain
  fallback Databricks has.
- Finding 21: verify end to end that settings-only keys get their
  catalogs through the refreshers' `env=` (test it, not assume it).
- Finding 22: `listing_effective_env()` honours `--cwd`.
- Finding 23: `--settings` env block reaches the listing surfaces
  (`/providers`, doctor, init tabs) via `settings_flag`.

Section 6, hygiene:
- The 33 ruff/pyflakes findings (unused imports and variables, B904/B905).
- The ResourceWarning for an unclosed socket at interpreter shutdown on
  Windows and GC-time unclosed-socket warnings from mock servers.
- Status-bar progress glyph stuck non-idle after a completed turn (seen
  once live): find the root cause; at minimum the glyph resets on
  `turn_done`.
- `permissions.add_allow_rule` re-serialises `.claude/settings.local.json`
  from pretty to compact: preserve the file's indentation (2-space) and
  key order; add a test with a pretty-printed input.
- `halo models` with no OpenRouter key prints an empty table while doctor
  claims the vendored fallback applies: make the two agree (show the
  vendored rows, labelled).
- Docs drift: README's stale `--debug` troubleshooting line; comments in
  `agent/loop.py:204-220` and `tui/dispatch.py:74-79` saying terminal
  pixel rendering is out of scope while the README ships kitty/sixel
  inline images (fix whichever is stale); README names `Notification`
  among never-fired hooks although it is not in NOT_EMITTED_V1.

Section 8, model-quality signal (1474 sessions):

### W4 MCP: claude.ai connectors bridge, IN SCOPE (rolo 2026-10-01 ~13:10: "yes let's add all that to 2.0.1")

Supersedes the "optional, only if rolo asks" line above. Everything in
this section ships in 2.0.1.

1. Explain the zero. `/mcp`, `halo mcp list` and doctor's MCP line list
   every scope searched (user scope in ~/.claude.json, project-local scope
   for this cwd, .mcp.json in this directory, plugins, managed) with the
   count found in each, and when `claude` is installed they add the
   claude.ai connectors it reports, labelled `claude.ai connector (via
   claude)`. A directory with a project-scoped .mcp.json elsewhere is
   named when the user's history shows one (for example
   ~/Documents/serverMode/.mcp.json: "loads only when halo runs there").
2. Discovery of connectors: when `claude` is on PATH and the cached auth
   status says claude.ai login, run `claude mcp list` once per session in
   a background worker (never on the UI thread; 20 s timeout; cached
   under ~/.halo/mcp/connectors.json with the time) and parse the
   `claude.ai <name>: <url> - <status>` lines into name, URL host and
   status (connected / needs authentication / failed). Tool names come
   from one headless `claude -p --output-format stream-json` start whose
   `system/init` line lists `mcp__claude_ai_<name>__<tool>` names; the
   process is ended right after that line so no model turn is spent.
   Both are refreshed by `/mcp` reconnect and `halo mcp list --refresh`.
3. The bridge tool. Each connector becomes one Halo tool
   `connector__<slug>` (for example `connector__gmail`,
   `connector__claude_docs`) with the schema `{request: string (what to
   do, in plain words), tool: string (optional, one of the connector's
   tool names), args: object (optional, arguments for that tool)}` and a
   description that lists the connector's tool names. Running it spawns
   `claude -p` with `--allowedTools "mcp__claude_ai_<name>__*"`,
   `--max-turns 4`, `--output-format json`, a system prompt that says it
   is a tool proxy which performs exactly the request with the connector
   tools and returns the results verbatim as JSON with no commentary, and
   the request (plus the tool name and args when given). The tool result
   is the returned text; cost and duration are recorded in telemetry as a
   `connector` call; the usual MCP result caps and spill apply. Deferred
   through ToolSearch like other MCP tools; `alwaysLoad` honoured per
   connector in config.
4. Status and re-auth: `/mcp` shows each connector with its status; a
   connector in "needs authentication" state shows the exact step
   (authorize it at claude.ai or inside `claude` with /mcp, then `/mcp`
   reconnect here), since the OAuth grant belongs to the claude.ai
   account and halo never reads the credentials file. When `claude` is
   missing or gateway-driven, the connectors section says so in one line
   instead of being absent.
5. Config: `connectors.bridge` (default true when a claude.ai login is
   detected; false disables discovery and the tools), per-connector
   `enabled`, `alwaysLoad`, `max_turns`. Doctor shows the bridge state.
6. Permission rules: `connector__gmail` follows the ordinary tool rules;
   the user's own deny/ask rules for `mcp__claude_ai_Gmail__*` in Claude
   Code's settings are translated to the matching `connector__gmail` rule
   so an ask rule written for claude still asks here.
7. Tests: a fake `claude` on PATH (the existing fake-claude subprocess
   pattern) that answers `mcp list` with the four connector lines in all
   three states and answers `-p --output-format stream-json` with an init
   line listing tool names, then a json result for the bridge call;
   pinning tests for discovery (parse, cache, refresh, never on the UI
   thread), the tool schema and description, the spawned command line
   (allowedTools, max-turns, system prompt), the result passthrough and
   the cap, the needs-authentication display, the gateway and missing
   `claude` cases, the config switches, and the rule translation. Live
   check on the Kali VM once `claude` is reinstalled there: `/mcp` lists
   the four connectors, `connector__gmail` with "list my 3 most recent
   email subjects" returns them through a non-Claude main model.
