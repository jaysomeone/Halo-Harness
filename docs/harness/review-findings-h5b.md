## Findings

1. **critical** — `halo_harness/agent/loop.py:776` + `agent/prune.py:167-176` (+`loop.py:1394,1469,1514-1518`) — `_derive_and_build` now runs `prune_messages` on every request, and prune rule 1 head/tail-truncates any tool_result over 8,192 chars regardless of position, including the result the tool returned a moment ago. — Verified: the model Reads a 600-line, 28,690-char file. The log keeps all 32,889 chars, but request 2 sends 5,150: lines 76-580 become `... [27769 chars pruned] ...` with no spill path. This hits every Read of a file over about 200 lines, and every Bash, Grep, WebFetch or MCP result over 8 KB (Playwright or Chrome snapshots, test logs). A list-shaped MCP result also loses all but its first text block. The TUI shows the full output, so nothing looks wrong. Compaction selects its verbatim tail from the pruned list, so after a compaction the truncated copies are written permanently into the log. `test_h5b_f04_prune_is_wired_into_every_ordinary_step` (`tests/test_compaction_integration.py:367`) asserts this truncation as correct. — Never prune results inside the 40k-token protection window: over-cap results are already spilled by `spill_and_truncate`. Prune as a persisted, batched step (OpenCode's PRUNE_MINIMUM of 20k) rather than recomputing it per request, and select the compaction tail from unpruned messages.
2. **major** — `agent/prune.py:157-166` + `loop.py:776` — Rule 2 (stub results older than 40k newer tokens) is recomputed on every request, so the stub boundary slides forward one result per step. — Verified by simulation with the snapshot's `prune_messages` and 6,000-char results: from step 28 on, every step changes an earlier message, re-sending about 169.7k chars (about 42k tokens) uncached where only 6.2k chars are new. On DeepSeek, Kimi and GLM automatic prefix caching, and on OpenRouter or native Claude `cache_control`, tool-heavy sessions pay full-price input for about 40k tokens per step and incur the matching prefill latency. On Claude preserved-thinking models (Fable 5.1, Opus 5.5), editing earlier tool results invalidates every later thinking signature. — Record prune decisions in the log (a node naming the stubbed ids), and only advance them in chunks of at least 20k tokens, or only at compaction.
3. **major** — `halo_harness/agent/compact.py:149-155` (+`loop.py:1220-1242`) — Finding 1 is closed only for large windows. `min(usable, floored)` lets `usable` override the "≈70 % floor" whenever `context - min(out,32k) - min(20k,out) ≤ 0`. The back-to-back guard only skips the step immediately after a compaction. The finding also asked for a skip when the post-compaction estimate is still at or above the trigger; that was not done, and the requested `max_tokens` is still not what is reserved. — Verified: 21 of 458 real models.json rows still have a trigger of 0. Five of them are in the target families: `z-ai/glm-5.2:free`, `deepseek-r1-distill-llama-70b`, and `qwen-2.5-coder-32b`, `qwen-2.5-7b` and `qwen-2.5-72b`. Nine more rows sit under 50 %, for example 65,536-window rows at 13,536. With a 32,768/29,491 profile, a 5-step Read turn made 3 summariser calls (steps 1, 3 and 5). Each skipped step emits `compaction phase="failed"`, which the TUI shows as "✗ Compaction failed". — Apply the floor after the `usable` cap (or cap reserve at the requested max_tokens), skip when the post-compaction estimate is still at or above the trigger, and emit a non-failure phase for a skip.
4. **major** — `loop.py:1171-1173` (+`1644-1646,1756-1759,1395`, `model.py:209-215`) — `_account_usage` sets `_last_prompt_tokens = usage.input_tokens`. Now that `message_start` usage is merged (F15 point 3), native Anthropic routes report only the uncached portion, excluding `cache_read_input_tokens` and `cache_creation_input_tokens`. — Verified with the 200k/8,192 profile, whose trigger is 140,000: `message_start` reports input 40 plus cache_read 150,000, and no summariser call is made (`_last_prompt_tokens=40`). With the same prompt reported uncached, compaction runs. Auto-compaction therefore never fires on cached `ant:` or Databricks Claude sessions until a hard overflow. Context %, the status-bar tokens, "freed ~N tokens" (it goes negative) and the fallback cost are wrong as well. — Use input + cache_read + cache_creation everywhere a prompt size is needed, and price cache tokens separately.
5. **major** — `loop.py:1007-1022,1146-1154,1752-1755` + `providers/request.py:470-505` — Finding 5's "never log an empty assistant node for a cut" is not done. A steer noticed before any block completes logs `content: []`. A steer during thinking, before the `signature_delta`, logs an unsigned thinking block, which `prepare_anthropic_messages` then drops, leaving the message with empty content. — Verified (wire shape): steering at the first `thinking_delta` logs `[{'type':'thinking','text':'hmm let me','signature':''}]`, and request 2 carries `{"role":"assistant","content":[]}`. Steering at `message_start` logs `[]` and produces the same request. Anthropic rejects non-final assistant messages with empty content, and the node stays in the log, so every later request on `ant:` or Databricks Claude 400s. A steer typed during a retry wait always takes this path: the new request is cut at its first chunk. — When a cut leaves no replayable block, log nothing, or keep the partial text with a marker as the abort path does (`loop.py:998-1004`). In `prepare_anthropic_messages`, drop assistant messages that end up empty and merge the adjacent user turns.
6. **major** — `loop.py:2448-2610` (check only at `2587`) — The per-call steer check runs after each solo dispatch, never before one. Closed `tool_use` blocks from a steered cut are also always dispatched. — Verified: a steer ("STOP-DO-NOT-WRITE") queued at `message_end` still ran the pending `Write`, and the file was created. 7. **major** — `loop.py:1546` + `agent/subagent.py:186` — Sub-agents now share the parent's abort Event, but every child `turn()` begins with `self.abort.clear()` on that shared Event. — Verified: 5 Agent calls, so the pool of 4 queues one.
