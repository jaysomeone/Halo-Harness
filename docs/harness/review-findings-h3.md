# H3 review findings (commit 5fe491b = H3; MCP client, frozen catalog, `mcp` CLI, `--chrome`/`--playwright`)

Format: severity — file:line — defect — failure scenario — fix. "Verified" = reproduced against a `git archive 5fe491b` snapshot with mcp 2.2.0 on Windows (Python 3.11.7, the build host) and WSL Ubuntu (Python 3.12.3). Scratch repro scripts only; no repo file was touched except this one.

Known/in-flight, not repeated here: the Windows exit-139 teardown crash (`client.py` `McpLoop.stop()`/atexit, `tests/test_mcp_manager.py`) and the slow-init stack leak the same worker is patching in `manager.py::_connect_once`. Pre-fix at 5fe491b, a server slower than MCP_TIMEOUT stayed alive after `close_all` on both OSes.

1. **critical** — `halo_harness/agent/catalog.py:60-63,166` + `headless.py:254-257` + `tools/tool_search.py:75-90` — `select_preload` fills the whole remaining cap with alphabetical MCP tools, but the brief says preload is `alwaysLoad` + `mcpPreload` only, with a default of none. The frozen catalog therefore sits exactly at the cap, and `_evict_if_needed` evicts the tool it just loaded (the only entry in `_loaded_order`), while ToolSearch still returns that tool's schema plus a `tool_reference`. — Verified with headless's formula: at caps 32 and 128, a `select:` load leaves the tool out of `names` and not dispatchable. On the owner's box (~213 tools with Chrome), OpenRouter preloads the first 114 by name (daw through the first 5 hardware tools). `expanded-models` happens to sort into that set, which is why the live acceptance passed. About 99 tools (jam, kb, mix, drums, samples, most of hardware) are unreachable, and every request carries ~114 schemas. Databricks preloads 18 daw tools and leaves ~195 unreachable. — Preload only `alwaysLoad`/`mcpPreload`. Before appending, evict an older loaded-deferred tool, never the one being loaded. If nothing can be evicted, return an error with no `tool_reference`. Lock `load()`, because ToolSearch runs in the read-only pool and two ToolSearch calls in one turn change the catalog at the same time.
2. **critical** — `halo_harness/agent/repair.py:85-87` via `agent/loop.py:1044` — Unknown tool names are auto-renamed with difflib (cutoff 0.85) against the live registry only. MCP sibling tools are often one edit apart, so a call to a deferred, evicted or resumed-session tool runs a different MCP tool. — Verified with `resolve_tool_name`: `mcp__hardware__hw_clock_stop` becomes `hw_clock_start`, `mcp__plugins__presets_scan` becomes `presets_plan`, and `mcp__kb__kb_plugin_params` becomes `kb_plugin_card`. Each is then dispatched with the original arguments. By construction the same happens after `--session-id <existing>`: the logged catalog is replayed, but the new registry has those tools deferred. — Never fuzzy-rename `mcp__` names. If the name is in `catalog.deferred`, auto-load it (or answer "load it with ToolSearch select:<name>"); otherwise only suggest names.
3. **critical** — `halo_harness/mcp/stdio.py:94-97` — `StdioServerParameters` keeps the SDK default `encoding_error_handler="strict"`. One non-UTF-8 byte on a server's stdout kills the SDK reader, which then silently reads and throws away every later response. — Verified on both hosts with a raw server that emits `FF FE 41 0A` before a response. From then on, every call to that server waits its full timeout (default 1e8 ms ≈ 27.8 h, see finding 4) while the handle stays `✔ Connected`. A realistic trigger is a cp1252 `print()` in a Windows Python server. Monkeypatched to `"replace"`, the same server answers instantly. — Pass `encoding_error_handler="replace"` and add the dead-connection detection from finding 6.
4. **major** — `halo_harness/tools/mcp_tool.py:212`, `mcp/manager.py:57-70,524-530`, `agent/loop.py:1115`, `tools/registry.py:148-150` — In-flight MCP calls ignore `ctx.abort` and default to a 100 000 s limit. The H2 must-do was done only for read-only batches of 2 or more calls. Also, `MCP_TOOL_TIMEOUT` below 1000 falls through to 1e8 instead of being clamped to 1000 (binary §9). — Verified: with `abort` set at 1 s, both a solo `McpTool.run` and a one-item read-only batch return at 6.0 s (the tool's own sleep). A hung daw `live_action` while the DAW is frozen would hold the turn, and U2's Esc, for up to 27.8 h. — Spawn the call and wait in slices of 0.2 s or less on `ctx.abort` (cancel and return an "interrupted" result). Clamp the env value, and route single read-only calls through the same wait.
5. **major** — `halo_harness/agent/loop.py:71,84-118,924-927,1055` + `tools/mcp_tool.py:149-173,221-223` — `_finalize_tool_result` turns every list result into text: a vision image becomes `[image: image/png]` and a `tool_reference` becomes `[tool_reference block]`. It then cuts again at a hard-coded 25 000 tokens. Separately, `cap_and_spill` never names its spill file, and pooled read-only calls pass it `tool_use_id=None`. — Verified: a 200 000-char result reaches the model ending in `... [MCP result truncated at ~25000 tokens]`, so Claude Code's exact string is cut off and no spill path is given. With `MAX_MCP_OUTPUT_TOKENS=50000`, a 150 000-char result is not spilled and loses 50 000 chars. Chrome/Playwright screenshots never reach a vision model. — Log MCP results as blocks: send vision images as an image part and strip `tool_reference`. Skip the loop-level cut for results that are already capped (or read the env var). Append "Full output saved to <path>" to the truncation line, and give each pooled call its own `tool_use_id`.
6. **major** — `halo_harness/mcp/manager.py:483-507,524-530,694-707` — Nothing notices when the transport dies: after the server exits or the reader stops, `state` stays `connected` and `_session` stays set. — Verified on both hosts: if the server is killed mid-call, that call returns `MCPError: Connection closed` promptly. After that, every call fails the same way instantly, `mcp list`, `/mcp` and the prompt's server list still show the server, and nothing reconnects for the rest of the session. — On `Connection closed`, `ClosedResourceError` or `BrokenResourceError` (and in a done-callback on the lifecycle future), mark the handle `failed`, drop `_session`, and reconnect once on the next call.
7. **major** — `halo_harness/mcp_cli.py:84-85,100,118-119` + `headless.py:327` — `mcp list` and `mcp get` resolve with `print_mode=True`, which approves and spawns every `.mcp.json` server. The header prints `...` and only after the connects finish. Stream-json `init.mcp_servers` is a list of bare names. — `halo mcp list` in a cloned repo runs every unapproved `.mcp.json` command and can never print `⏸ Pending approval`. The 2.1.281 `mcp list` description says: "Unapproved .mcp.json servers are shown as ⏸ Pending approval and not connected to". SDK consumers that expect Claude Code's `{name, status}` objects break. — Resolve list/get with `print_mode=False` and don't start pending servers. Print "Checking MCP server health…" first, and emit `{name, status}` in `init`.
8. **major** — `halo_harness/mcp_cli.py:163-185` — `_write_claude_json_raw` re-dumps with `ensure_ascii=True` and always adds a trailing newline. It also strips a BOM and replaces the file with a temp file that has the default umask mode. — Verified in memory against the owner's real 66 837-byte `~/.claude.json`: any `mcp add/remove` rewrites all 40 non-ASCII characters as `\uXXXX` escapes (starting at the first U+2014) and appends a newline the file never had. Dumping with `ensure_ascii=False` and no added newline reproduces the file byte for byte. On Kali, a 0600 file becomes 0644. — Use `ensure_ascii=False`, keep the original's trailing-newline and BOM state, copy the file mode onto the temp file before `os.replace`, and compare bytes (not parsed dicts) in the test.
9. **major** — `halo_harness/mcp_cli.py:258-285` — `_parse_add_argv` treats `--` as the command. — Verified: `halo mcp add airtable -- npx -y airtable-mcp-server` (Claude Code's documented form) stores `{"command": "--", "args": ["npx", …]}`, a server that can never start. — Consume the `--` separator, and also accept `--env=K=V` and `--scope=x`.
10. **major** — `halo_harness/mcp/manager.py:249-252` — Every `--mcp-config` value is first checked with `Path.exists()`, which raises on Linux when the name is too long. — Verified in WSL: an inline 418-char JSON value with no `/` raises `OSError: [Errno 36] File name too long` out of `build_manager`. The result is a traceback and no session. Windows just returns False. — Parse the value as JSON when it starts with `{`, otherwise treat it as a path, and catch `OSError` around `exists()`.
11. **major** — `halo_harness/mcp/manager.py:322-359` — The approval and policy inputs are incomplete. `enabledMcpjsonServers`, `disabledMcpjsonServers` and `enableAllProjectMcpServers` are read only from `~/.claude.json` projects, never from the settings files where Claude Code documents and writes them. Managed `allowedMcpServers`/`deniedMcpServers` are not implemented. And `disabledMcpjsonServers` also deletes a same-named user, local or flag server (lines 356-357). — A project `.claude/settings.json` with `"disabledMcpjsonServers": ["x"]`, or a managed `deniedMcpServers` entry, still lets `-p` spawn `x`. Rejecting a repo's `github` entry silently removes the owner's own user-scope `github`. — Read the three keys from the resolved settings as well as `~/.claude.json`, apply the policy lists after resolution, and drop only the `.mcp.json` entry.
12. **major** — `pyproject.toml:15` (+ `tools/mcp_tool.py:76,191-194,217,224`, `mcp/manager.py:528`) — `mcp>=1.26,<3` allows SDK 1.x, but the code reads field names that exist only in 2.x (snake_case) and passes a float `read_timeout_seconds` where 1.x expects a `timedelta`. — Not run; reasoned from the 1.x API. In a Kali venv that already has mcp 1.2x, servers show ✔ Connected, but every tool is sent with an empty schema, `isError`/`readOnlyHint`/`structuredContent` are ignored, and every call fails with `AttributeError: 'float' object has no attribute 'total_seconds'`. — Pin `mcp>=2.2,<3` (the lockfile has 2.2.0) and have `available()` report a 1.x install as unsupported.
13. **minor** — `halo_harness/tools/tool_search.py:22-30` (+ `agent/catalog.py:53,111-121`, `mcp_setup.py:149`, `permissions.py:810,987`) — Several catalog inputs are wrong or unused: ToolSearch's description still says "This build has no deferred MCP tools yet", keyword search ignores `_meta anthropic/searchHint`, and nothing keeps ToolSearch when `--tools` or a deny rule filters it out. Server-level `alwaysLoad` and `mcpLazy` are parsed but never used. Deny rules naming a whole tool (`mcp__srv__tool`) leave it in the catalog, and because they are parsed with `rsplit`, they never match a tool whose name contains `__`. — Models read the tool text and call deferred names directly, which leads to finding 2. `--tools Read,Bash` strands every deferred tool while the prompt still says "call ToolSearch". A denied tool still takes one of Databricks' 32 slots. — Use Claude Code's deferred-tool wording, score `searchHint`, and keep ToolSearch whenever the deferred pool is non-empty. Honour config `alwaysLoad` and `mcpLazy`, and remove tools matched by those deny rules from the catalog (split on the first `__`).
14. **minor** — `halo_harness/mcp_setup.py:59-66` + `mcp/manager.py:319-320,352-354` — `claudeInChromeDefaultEnabled` is honoured in print mode and `CLAUDE_CODE_ENABLE_CFC` is ignored. The 2.1.281 enable check goes: flag, then `CLAUDE_CODE_ENABLE_CFC`, then off for non-interactive sessions, and only then `claudeInChromeDefaultEnabled`. The `--chrome`/`--playwright` server entries also rank below user scope and disappear under `--strict-mcp-config` or `managed-mcp.json` with no notice. — On the owner's box, every `halo -p` spawns `claude.CMD --claude-in-chrome-mcp` and adds 22 tools, which `claude -p` never does. A user-scope `playwright` entry silently overrides `--playwright-cdp` and `--playwright-headless`. `--chrome --strict-mcp-config` drops Chrome without a message. — Follow the binary's order, give flag-created servers the same precedence as other flags, and print a notice when strict or managed config drops a server the user asked for.
15. **minor** — `halo_harness/mcp/manager.py:470`, `mcp/stdio.py:100-103`, `mcp/http_sse.py:205-208,226-229` — The transport is opened (and `_do()` runs) inside `asyncio.wait_for`, which on Python 3.11 and earlier runs them in a separate Task. The anyio cancel scopes are therefore entered in a short-lived task and exited in `_lifecycle_task`. — Verified on the host's 3.11.7 but not on 3.12.3: every normal `close()` ends in `RuntimeError('Attempted to exit cancel scope in a different task than it was entered in')`, which `close()`'s bare `except` swallows. The child is still killed and no tasks are left pending. The lifecycle design assumes open and close happen in one task, and that is false on the build host. The in-flight fix's detached `_cleanup` task also closes from a different task. — Use `anyio.fail_after` inside the lifecycle task (same task on 3.10-3.13), and close the stack in that task's `except BaseException`.
16. **minor** — `tests/test_mcp_catalog.py:180-254`, `tests/test_mcp_cli.py:93-102`, `tests/test_mcp_manager.py:400-419`, `tests/test_mcp_tool.py:171-181` — Several H3 tests pass for the wrong reason, and the high-value cases are missing. — `test_toolsearch_next_request_carries_the_loaded_tool` passes because `slow_tool` is already preloaded (cap 30 minus 12 built-ins leaves room for all 7 fake tools). Every eviction test passes a `cap_budget` below the headroom and never uses headless's `cap - len(registry)`, which is the path finding 1 breaks. The "preserves unrelated keys" test compares parsed dicts on an ASCII-only fixture. The MCP_TIMEOUT test never checks that the slow child died. The truncation-string test stops at `cap_and_spill`, so it misses finding 5 replacing the string. — Add these tests: (1) headless preload formula plus a ToolSearch load at caps 32 and 128, then check the next request carries the tool; (2) an unknown `mcp__` name one edit away from a loaded tool is not dispatched; (3) fake-server `badbytes` and `die-mid-call` modes, checking the call returns within its limit and status is no longer connected; (4) abort during an MCP call returns in under 1 s; (5) on 3.11 and 3.12, no child pid survives a startup timeout plus `close_all`, and the lifecycle future holds no exception; (6) a vision image block reaches the request body, and the exact truncation string reaches the model; (7) a `~/.claude.json` with non-ASCII text and no trailing newline is byte-identical after add plus remove, plus `mcp add n -- cmd`; (8) `mcp list` with an unapproved `.mcp.json` shows `⏸ Pending approval` and spawns nothing, plus a long inline `--mcp-config` on Linux.

## No findings in
- **Scope resolution, for the keys that are read:** `managed-mcp.json` is exclusive, even when it fails to parse; `--mcp-config` accepts files or inline JSON (`{"mcpServers":…}` or a bare map); `--strict-mcp-config`; local `projects[cwd].mcpServers` under both key forms; `.mcp.json` approval order including `-p` auto-approve and `disabledMcpjsonServers` beating `enableAllProjectMcpServers`; `disabledMcpServers`.
- **`${VAR}`/`${VAR:-d}` expansion:** a set-but-empty variable wins, and an unset one is left verbatim with a notice. Credential blanking is limited to remote url/headers. Note that it applies to every scope, so a user-scope `"Authorization": "Bearer ${API_KEY}"` header (Claude Code's documented pattern) connects as `Bearer `. Confirm that is intended.
- **Naming and catalog order:** name sanitising `[^a-zA-Z0-9_-]` to `_` and the split on the first `__`; server-level deny rules (`mcp__srv`, `mcp__*`, `mcp__gith*`) remove tools from both the catalog and the ToolSearch pool; the frozen catalog lists built-ins then MCP tools and only ever appends; each growth is logged as a meta node; the system prompt lists servers with one-liners, never tools.
- **Result handling:** `_meta` checks (`alwaysLoad` must be exactly true, `maxResultSizeChars` must be positive and finite and is combined with `MAX_MCP_OUTPUT_TOKENS`×4); the 1 600-token reservation per image; embedded resources; the `structuredContent` fallback; `isError` (SDK 2.x); `readOnlyHint` routing calls to the read-only pool (the pool itself is abort-aware and time-limited for 2 or more calls).
- **Child processes:** children get `tool_child_env` (the owner's `expanded-models` loads its own env file, so stripping breaks nothing) and `CLAUDE_PROJECT_DIR`. The SDK kill scope works: a Job Object with KILL_ON_JOB_CLOSE on win32 (no survivors after process exit) and a new session on POSIX. PATHEXT/`npx.cmd` resolution works. Parallel startup is capped at MCP_TIMEOUT + 3 s and failures don't stop the session. A server dying mid-call returns promptly, and a 30 MB single-line response works.
- **Other checks:** the `headersHelper` contract (four error kinds, helper headers override static ones); `mcp add` refuses to write when the file doesn't parse; tmp + `os.replace`; UTF-8 stdout for the status glyphs; doctor checks never raise; the `--chrome` entry matches 2.1.281's `Ktt()` shape, and its permission env is set only in auto/bypass; print-mode `permission_denials`.

## U2/H4 must-do
- **U2 `/mcp` reconnect:** `reconnect()` keeps the old `error` and `tools_fetch_failed` values, a still-running old lifecycle task can overwrite `_stack`/`_session`, and a reconnected server's tools never enter the SessionCatalog's deferred pool (it is built once at start). Reset the fields, wait for the old task, and refresh the pool.
- **U2 Esc/quit:** Esc during an MCP call needs finding 4. `close_all` closes handles one at a time, so one slow server uses up the 5 s quit budget and the rest get 0.1 s each; set every close event first, then wait once. Build MCP inside the session's `try/finally`: headless starts servers before validating `--session-id`, so a bad id returns 2 without `close_all`.
- **U2 approvals:** interactive sessions must resolve with `print_mode=False` and implement the pending-approval `question`, stored in `~/.halo/mcp-approvals.json` keyed by each entry's sha256 (D-CFG). Today approvals are keyed by name and nothing writes them. The status bar's "MCP n/m" count needs finding 6's liveness tracking.
- **H4 PostToolUse:** MCP output is capped inside `McpTool.run`, so PostToolUse would see truncated text. Move capping into the finalize step after PostToolUse. Hook matchers must see the model's original tool name, not a repair rename (finding 2).
- **H4 `mcp_tool` handlers:** these go through `McpManager.call`, so give them the hook timeout instead of 1e8 ms, plus the fixes for findings 3, 4 and 6. Move `headersHelper` off the event loop, since its blocking `subprocess.run` inside `_open_transport` stalls every server for up to 10 s. Only run a repo-provided helper when the project is trusted (binary §9).
- **Kali VM:** re-run findings 3, 10 and 15 and the slow-init repro on the VM's Python. Also run `--playwright` there: check that @playwright/mcp's default browser channel exists, or pass `--browser chromium`.
