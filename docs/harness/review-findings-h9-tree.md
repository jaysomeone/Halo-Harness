## Findings

1. **critical** — `providers/hooks.py:126-131` + `providers/oai_stream.py:57,306-308` + `agent/prune.py:218` (+`agent/invariants.py:78`, `tools/truncate.py:77`, `agent/prompt.py:189-190`) — On every Kimi row (`tool_id_format: kimi_functions_idx`: all 7 OpenRouter Kimi ids plus `databricks-kimi-k3` and `databricks-kimi-k2-7-code`), a non-native upstream id (empty, or an OpenAI-style `call_…`) is renamed from a counter that restarts at 0 on every stream. Every step's first call therefore becomes `functions.<name>:0`. Prune's committed stub set, spill filenames and pairing checks are all keyed by the bare id. — Verified: 6 Reads of 6 different files, with empty upstream ids, were all logged as `functions.Read:0`. From request 3 on, the model's freshest 100,061-char Read result went out as a 2,034-char "[Old tool result content cleared]" stub, because an older `functions.Read:0` had been committed as a stub. The same collision makes `find_unpaired_tool_use_ids` treat a later interrupted call as answered, overwrites `tool-results/functions.Read:0.txt` (an older truncated result's hint then points at another call's output), and merges TUI cards. The Kimi prompt block also tells the model its ids are "never renumbered". Whether Databricks' Kimi endpoints return native ids has not been observed live. — Continue the counter across the session from the highest `functions.*:N` already logged (Kimi's idx is conversation-global), or mint unique ids. Key stubs, spills, pairing and cards by (assistant node seq, id), never by the id alone.
2. **critical** — `agent/subagent.py:209` + `agent/loop.py:2527,2776-2789,2691-2696` + `tui/dispatch.py:122-129` — Every child writes its ask into the parent's single `_permission_waiters` dict, keyed by the bare tool_use id. Kimi's native `functions.<name>:<idx>` restarts at 0 in every fresh child conversation, and the harness preserves it verbatim, so two parallel children that both open with Bash collide. — Verified with two foreground children, both hitting a user ask rule with id `functions.Bash:0`: two cards with the same id, one waiter key. Approving the card that showed child B's `echo B-RAN` ran child A's `echo A-RAN`. Child B then waited forever: answering its card returned False, and only Esc ended the turn. The only gate this harness keeps (the user's own ask rule) approved a command the user never saw. — Namespace the waiter key and the `permission_request` id with the child's `agent_id`, never overwrite a live slot, and test with colliding ids.
3. **major** — `agent/loop.py:746` + `agent/subagent.py:177-202` + `controller.py:167` + `headless.py:988` + `agent/jobs.py:118` / `tools/_proc.py:190` + `cli.py:224` — Every sub-agent Session builds its own `JobRegistry`, and only the top session's registry is killed on quit. Jobs run with `start_new_session=True`, and only SIGTERM is handled. — Verified on WSL: (a) a sub-agent's `Bash(run_in_background) sleep 301` was still alive after `-p` exited 0. (b) SIGHUP to `-p`, which is what closing the terminal or an SSH drop does, exited -1 and left `sleep 302` running. (c) SIGTERM exited 143 and killed its job. The child's completion notices are also never applied: its turn is over. `/tasks`, BashOutput and TaskStop in the parent cannot see child jobs. — Share one registry across a session and its children, or have teardown walk every child registry. Handle SIGHUP (and SIGINT in `-p`) the same way as SIGTERM, plus an `atexit` `kill_all`. Use parent-death cleanup (`prctl(PR_SET_PDEATHSIG)`) for setsid children on Linux.
