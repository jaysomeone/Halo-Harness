# Data-drive the limits, hand-code the replay

Every one of the twelve families in scope can be driven by the same Chat-Completions agent loop, provided the provider layer applies a short list of per-model transforms whose *parameters* live in a data table while the transforms themselves stay in code. The non-negotiable rules are few and exact: DeepSeek V4/V4.1 returns HTTP 400 `The \`reasoning_content\` in the thinking mode must be passed back to the API.` when a tool-bearing request drops any prior assistant turn's `reasoning_content` (an empty string must be echoed too) ([opencode #24190](https://github.com/anomalyco/opencode/issues/24190), [CodeRouter](https://www.coderouter.io/blog/deepseek-reasoning-content-400-error-fix)); Kimi K2-lineage models expect tool-call ids of the exact form `functions.{name}:{idx}` and Moonshot's endpoints reject any sampling value other than the fixed `temperature 1.0 / top_p 0.95` ([HF Kimi-K2 discussion #48](https://huggingface.co/moonshotai/Kimi-K2-Instruct/discussions/48), [Kimi K3 quickstart](https://platform.kimi.ai/docs/guide/kimi-k3-quickstart)); Mistral rejects any tool-call id that is not exactly nine alphanumerics ([eca #233](https://github.com/editor-code-assistant/eca/issues/233)); MiniMax rejects synthesized ids and non-JSON arguments with error code 2013 ([kilocode #3967](https://github.com/Kilo-Org/kilocode/issues/3967)); GLM-5.3 cannot stop thinking (400, code 1210) and Qwen3.5+ chat templates raise `System message must be at the beginning.` for any non-leading system message ([hermes-agent #96373](https://github.com/NousResearch/hermes-agent/issues/96373), [HF Qwen3.5 discussion #5](https://huggingface.co/Qwen/Qwen3.5-35B-A3B/discussions/5)); Gemini 3 demands a `thought_signature` on the first function call of every step and Grok 4.7 returns encrypted reasoning on every response that must round-trip unchanged ([Gemini thought signatures](https://ai.google.dev/gemini-api/docs/generate-content/thought-signatures), [xAI reasoning guide](https://docs.x.ai/docs/guides/reasoning)); gpt-oss speaks the harmony channel format and Gemma 3 has no system role at all ([harmony cookbook](https://developers.openai.com/cookbook/articles/openai-harmony), [Gemma prompt structure](https://ai.google.dev/gemma/docs/core/prompt-structure)). Above the models sit two host contracts: OpenRouter needs `provider.require_parameters: true` plus explicit pins because several endpoints per ID lack `tools` or cap output at 7–16K tokens, and Databricks caps `tools` at **32 functions**, accepts **exactly one leading `system` message**, returns 400 on unknown fields and pre-rejects any `max_tokens` above its output-tokens-per-minute budget ([OpenRouter endpoints](https://openrouter.ai/api/v1/models/deepseek/deepseek-v3.2/endpoints), [Databricks FMAPI reference](https://docs.databricks.com/aws/en/machine-learning/foundation-model-apis/api-reference), [Databricks limits](https://docs.databricks.com/aws/en/machine-learning/foundation-model-apis/limits)). The `model_table.json` in the final section carries limits, effort vocabularies, sampling profiles, id formats, replay modes, overflow regexes and pin lists as data; **eight named code branches** (reasoning echo, id normalisation, system normalisation, leak parsing plus argument repair, streaming aggregation, `max_tokens` budgeting with overflow classification, loop and empty-completion guards, and per-host field allow-listing) consume that data. Two values stay unverified and are flagged in the table: whether GLM-5.2 rejects or silently coerces `thinking.type: disabled`, and whether Databricks forwards a replayed `reasoning_content` into DeepSeek, Kimi or GLM on the turn after a tool call.

## Native tool calling is universal, but ids, parallelism and leaked markup are not

Every family except Gemma 3 does native OpenAI-style function calling on its vendor API, so halo never needs a text protocol; what differs is what each vendor tolerates around the call. DeepSeek supports tools inside thinking mode "from DeepSeek-V3.2" but its API returns **400 for `tool_choice: required` or a named tool in thinking mode**, while V3.1 supports tools only in non-thinking mode ([DeepSeek tool calls](https://api-docs.deepseek.com/guides/tool_calls), [DeepSeek chat completion reference](https://api-docs.deepseek.com/api/create-chat-completion), [HF DeepSeek-V3.1](https://huggingface.co/deepseek-ai/DeepSeek-V3.1)). Z.ai documents `tool_choice` as "`auto` (only supported value)" with a 128-function cap, and forcing `required` on a self-hosted GLM-5.2 made the model emit a JSON array inside `<tool_call>` that the `glm47` parser left as text ([Z.ai chat completion reference](https://docs.z.ai/api-reference/llm/chat-completion), [vLLM #48095](https://github.com/vllm-project/vllm/issues/48095)). Moonshot allows `auto/none/required` on `kimi-k3` but only `auto/none` on `kimi-k2.7-code` and `kimi-k2.6` ("other values error" with thinking enabled), DashScope states `required` is "not supported for Qwen models", Mistral's vocabulary is `auto/any/none`, and Databricks accepts `auto/required/none` or a named function ([Kimi models overview](https://platform.kimi.ai/docs/api/models-overview.md), [Model Studio function calling](https://www.alibabacloud.com/help/en/model-studio/qwen-function-calling), [Mistral function calling](https://docs.mistral.ai/capabilities/function_calling), [Databricks function calling](https://docs.databricks.com/aws/en/machine-learning/model-serving/function-calling)). Gemma 3 is the outlier: "there are no dedicated tool/function calling special tokens", so the `tools` flag OpenRouter and LiteLLM report for `google/gemma-3-27b-it` is provider-side prompt emulation with a ```tool_code``` convention, and Gemma 4 only gained real `<|tool_call>` tokens and a `system` role ([philschmid Gemma 3](https://www.philschmid.de/gemma-function-calling), [Gemma 4 prompt formatting](https://ai.google.dev/gemma/docs/core/prompt-formatting-gemma4)). The practical consequence is a `tool_choice_modes` list per row and a rule that the loop runs on `auto` everywhere; the only place halo should force a call is a one-shot retry after a text-serialised call, and for DeepSeek that retry must not use `required` while thinking is on.

Tool-call ids are where three vendors enforce formats the others treat as opaque. Kimi K2 "expects the ID to follow the format functions.func_name:idx" with a global counter starting at 0; a harness that sanitised `functions.read:0` to `functionsread0` dropped K2.5's tool-loop pass rate to **20% (1/5 trials)** versus 100% with native ids, with the symptom being `finish_reason: "stop"` and prose promising to call a tool ([HF Kimi-K2 discussion #48](https://huggingface.co/moonshotai/Kimi-K2-Instruct/discussions/48), [openclaw #62319](https://github.com/openclaw/openclaw/issues/62319)). Mistral's API answers `Tool call id was 2968-LWy3uasib but must be a-z, A-Z, 0-9, with a length of 9` for OpenAI-style `call_…` and Anthropic-style ids alike, also through OpenRouter, which is why OpenCode scrubs every id with `replace(/[^a-zA-Z0-9]/g, "").substring(0, 9).padEnd(9, "0")` and Roo applies `normalizeMistralToolCallId` whenever the model id contains `mistral` ([eca #233](https://github.com/editor-code-assistant/eca/issues/233), [opencode transform.ts](https://github.com/anomalyco/opencode/blob/dev/packages/opencode/src/provider/transform.ts), [Roo openrouter.ts](https://github.com/RooCodeInc/Roo-Code/blob/main/src/api/providers/openrouter.ts)). MiniMax validates ids it issued (`call_function_60llhpv7vhhb_1` style): compaction plugins that regenerated ids got `[Model Rejected] invalid request: tool_call id format is not supported`, and malformed argument JSON gets `invalid params, invalid function arguments json string, tool_call_id: … (2013)` ([openclaw #66892](https://github.com/openclaw/openclaw/issues/66892), [hermes-agent #12167](https://github.com/NousResearch/hermes-agent/issues/12167)). GLM ids are opaque but can change mid-stream on some hosts (`chatcmpl-tool-…` in the first chunk, `toolcall0` in continuations, same `index`), so streaming aggregation must key by `index`, never by id ([mistral-vibe #1127](https://github.com/mistralai/mistral-vibe/issues/1127)). On Databricks-hosted Gemini "the `id` field on `function_call` and `function_response` is not supported" ([Databricks function calling](https://docs.databricks.com/aws/en/machine-learning/model-serving/function-calling)). DeepSeek and DashScope ids (`call_6596dafa2a6a46f7a217da`) are undocumented beyond "opaque". The rule that satisfies all of them is: replay ids byte-for-byte; rewrite only when the row's `tool_id_format` is `alnum9` (Mistral, deterministic scrub applied symmetrically to `tool_calls[].id` and `tool_call_id`) or `kimi_functions_idx` (rename imported history to `functions.{name}:{n}` with a per-conversation counter); never synthesise ids for MiniMax.

Parallel calling is real on the models and inconsistent on the hosts. Meta says Llama 3.3 and Llama 4 "support multiple, and parallel tool calls natively" while Llama 3.1 zero-shot tools support "Only single tool calls", and vLLM's `llama3_json` parser still documents no parallel support on Llama 3 ([llama-models 3.3](https://github.com/meta-llama/llama-models/blob/main/models/llama3_3/prompt_format.md), [llama-models 3.1](https://github.com/meta-llama/llama-models/blob/main/models/llama3_1/prompt_format.md), [vLLM tool calling](https://docs.vllm.ai/en/latest/features/tool_calling.html)). DashScope's `parallel_tool_calls` "appears to be `false`" by default, Mistral defaults it to `true`, OpenRouter lists `parallel_tool_calls` in `supported_parameters` on only **12 of 457 rows** (including `deepseek/deepseek-v4-flash-0731`, `moonshotai/kimi-k2.6`, `kimi-k2.7-code`, `z-ai/glm-5.2`, `glm-5.3`, `glm-5.3-flash`), and Databricks' function-calling page says "Parallel function calling is not supported" while its model row for GLM 5.3 advertises "parallel tool calls" ([Model Studio function calling](https://www.alibabacloud.com/help/en/model-studio/qwen-function-calling), [OpenRouter models](https://openrouter.ai/api/v1/models), [Databricks function calling](https://docs.databricks.com/aws/en/machine-learning/model-serving/function-calling), [Databricks supported models](https://docs.databricks.com/aws/en/machine-learning/foundation-model-apis/supported-models)). Gemini adds a structural constraint: in a parallel response only the **first** `functionCall` part carries the thought signature, so a harness that splits or reorders an assistant turn's tool calls breaks validation ([Gemini thought signatures](https://ai.google.dev/gemini-api/docs/generate-content/thought-signatures)). The portable policy is therefore "accept parallel, keep the assistant turn atomic, send `parallel_tool_calls` only where the host lists it (DashScope `true`, OpenRouter endpoints that support it), never on Databricks", and execute according to each tool's own safety class as dsh does rather than trusting the model to serialise.

Strict schemas are not portable and should stay off by default. DeepSeek's strict mode needs `base_url=https://api.deepseek.com/beta`, `"strict": true` per function, every property in `required` and `additionalProperties: false`, with `minLength`/`maxLength`/`minItems` unsupported, which Claude Code's optional-heavy tool schemas do not satisfy ([DeepSeek tool calls](https://api-docs.deepseek.com/guides/tool_calls)). Kimi K3 documents `strict: true` only for `response_format.json_schema`, Z.ai's `response_format` accepts only `json_object`, DashScope and MiniMax do not document strict functions, and Databricks' structured output forbids `pattern`, `anyOf/oneOf/allOf`, `$ref` and more than 16 keys ([Kimi K3 quickstart](https://platform.kimi.ai/docs/guide/kimi-k3-quickstart), [Z.ai structured output](https://docs.z.ai/guides/capabilities/struct-output), [Databricks function calling](https://docs.databricks.com/aws/en/machine-learning/model-serving/function-calling)). OpenRouter's Response Healing plugin repairs JSON only for `response_format` outputs, non-streaming, and "does not indicate support for tool calls" ([Response healing](https://openrouter.ai/docs/guides/features/plugins/response-healing)). Schema *tolerance* matters more than strictness: OpenCode's Kimi K2 failures on `bash` were "completely fixed" by making `description` optional ([OpenCode #1334](https://github.com/sst/opencode/issues/1334)).

The families each have a text wire format that leaks into `content` whenever a host's parser is missing or mis-configured, and the harness must recognise all of them because OpenRouter routes to whichever third-party stack is up. Because these leaks are provider-parser failures rather than refusals, the right response is a narrowly scoped content-side fallback: only when a tool call was expected, `finish_reason == "stop"`, `tool_calls` is null and `content` matches one of the row's patterns, parse it (or treat the turn as failed), then retry once. DeepSeek's own docs mark its V3.2 reference parser as "not suitable for production use without robust error handling", and Continue's experience shows that a permissive text parser fires when the model merely *describes* the syntax, so the fallback must be pattern-specific and gated per row ([DeepSeek-V3.2 card](https://huggingface.co/deepseek-ai/DeepSeek-V3.2/raw/main/README.md), [Continue #11070](https://github.com/continuedev/continue/issues/11070)). Two related shape rules round out the tool layer: Kimi's examples always include `name` on tool messages and Moonshot errors with `tool_call_id not found` when any call lacks a `role: tool` reply, DashScope requires tool output "in string format", Databricks documents string-typed content for non-Claude models, MiniMax's self-hosted format uses a content array but its hosted API uses `role: tool` plus `tool_call_id`, and Mistral's API rejects a `tool` message followed directly by `user` (OpenCode inserts an assistant `"Done."`) ([Kimi tool calls guide](https://platform.kimi.ai/docs/guide/use-kimi-api-to-complete-tool-calls), [Model Studio function calling](https://www.alibabacloud.com/help/en/model-studio/qwen-function-calling), [Databricks FMAPI reference](https://docs.databricks.com/aws/en/machine-learning/foundation-model-apis/api-reference), [MiniMax-M2.1 tool guide](https://raw.githubusercontent.com/MiniMax-AI/MiniMax-M2.1/main/docs/tool_calling_guide.md), [opencode transform.ts](https://github.com/anomalyco/opencode/blob/dev/packages/opencode/src/provider/transform.ts)).

## Reasoning replay splits into five modes, each with its own toggle and error text

The reasoning field arrives under six different names and the replay obligation comes in five strengths, and both are data; only the echo/strip/round-trip mechanics are code. Field names: `reasoning_content` on DeepSeek, Moonshot, Z.ai, DashScope, MiniMax (when `reasoning_split` is set), vLLM and Databricks' OpenAI-compatible gateway models; `reasoning` (string) plus `reasoning_details[]` on OpenRouter, which also accepts `reasoning_content` as an alias of `reasoning`; content items of `type: "reasoning"` with `summary_text`/`summary_encrypted_text` on Databricks for Claude, GPT and Gemini versus a top-level `reasoning_content` "on message responses and deltas" validated for DeepSeek V4 Flash, Kimi K3, Grok 4.6 and GLM 5.3; `ThinkChunk` (`type: "thinking"`) on Mistral; `thought_signature` on Gemini function-call parts (exposed on the OpenAI-compatible wire as `tool_calls[].extra_content.google.thought_signature`); `reasoning.encrypted_content` on Grok 4.7; and raw tags in `content` — `<think>` for MiniMax by default and for R1/Qwen/Nemotron on unparsed hosts, `[THINK]…[/THINK]` for Magistral, `<|channel>thought` for Gemma 4, the harmony `analysis` channel for gpt-oss ([OpenRouter reasoning tokens](https://openrouter.ai/docs/use-cases/reasoning-tokens), [Databricks query reasoning models](https://docs.databricks.com/aws/en/machine-learning/model-serving/query-reason-models), [litellm #40449](https://github.com/BerriAI/litellm/pull/40449), [Mistral reasoning](https://docs.mistral.ai/capabilities/reasoning), [Gemini OpenAI compatibility](https://ai.google.dev/gemini-api/docs/openai), [xAI reasoning guide](https://docs.x.ai/docs/guides/reasoning), [MiniMax OpenAI-compatible API](https://platform.minimax.io/docs/api-reference/text-openai-api)).

The strongest mode, `echo_required_400`, belongs to DeepSeek V4/V4.1 alone. DeepSeek's rule is that when a request "carries the `tools` parameter" the `reasoning_content` of all previous turns must be passed back and is concatenated into context, whereas without `tools` it "need not be passed back; ignored if sent"; the failure is HTTP 400 with body `{"error": {"message": "The \`reasoning_content\` in the thinking mode must be passed back to the API.", "type": "invalid_request_error", "param": null, "code": "invalid_request_error"}}`, it "initiates on the second turn after tool invocation", the Anthropic-route variant reads `The \`content[].thinking\` in the thinking mode must be passed back to the API.`, and OpenRouter relays it verbatim ([DeepSeek thinking mode (zh-cn)](https://api-docs.deepseek.com/zh-cn/guides/thinking_mode), [opencode #24190](https://github.com/anomalyco/opencode/issues/24190), [claude-code-router #1378](https://github.com/musistudio/claude-code-router/issues/1378), [openclaw #71160](https://github.com/openclaw/openclaw/issues/71160)). Two details make naive fixes fail: DeepSeek sometimes returns `reasoning_content: ""` on assistant turns in a tool chain "and this empty string must be sent back verbatim", and when a gateway drops the field instead of rejecting it the model "returns `finish_reason: 'stop'`, causing the session loop to exit prematurely" — a silent variant that also hits Kimi K2 ([CodeRouter](https://www.coderouter.io/blog/deepseek-reasoning-content-400-error-fix), [opencode #35689](https://github.com/anomalyco/opencode/issues/35689)). The converged fix across OpenCode, Kilo and Continue is to carry `reasoning_content` on every stored assistant message and inject `reasoning_content: ""` where a turn had none ([kilocode #9501](https://github.com/Kilo-Org/kilocode/issues/9501), [Continue #12246](https://github.com/continuedev/continue/issues/12246)). The V3.2 open-weights template shows why this is cheap: with `drop_thinking=True` the completed earlier turn's reasoning is dropped from the encoded prompt, so the server-side "pass it all back" rule is a validation and cache convenience, and the echoed bytes are cache-hit input ([DeepSeek-V3.2 card](https://huggingface.co/deepseek-ai/DeepSeek-V3.2/raw/main/README.md)).

The `echo_required` mode (vendor says "as-is", no documented error string) covers Kimi K3 and K2.7-code, GLM 4.5+, MiniMax M2.x and Mistral's reasoning models. Kimi K3 "was trained in the preserved thinking history mode" and "requires the complete assistant message returned by the API to be passed back to `messages` as-is — including `reasoning_content` and `tool_calls`"; K2.7-code's `thinking.keep` accepts only `"all"`; K2.6 defaults `keep` to `null` (history ignored) and merely recommends keeping the current turn's reasoning ([HF Kimi-K3](https://huggingface.co/moonshotai/Kimi-K3), [Kimi thinking models guide](https://platform.kimi.ai/docs/guide/use-thinking-models.md), [Kimi K2.6 quickstart](https://platform.kimi.ai/docs/guide/kimi-k2-6-quickstart.md)). The failure for K3 is behavioural rather than a 400: flattening prior thinking into text so that "zero `reasoning_content` fields" remain makes kimi-k3 "drop out of reasoning mode and emit deliberation as ordinary content", and the fix appends `reasoning_content: ""` to assistant messages for the kimi-k3 and deepseek-v4 families only ([kimchi PR #1209](https://github.com/getkimchi/kimchi/pull/1209)). Z.ai states "you must return the complete, unmodified reasoning_content back to the API" and "All consecutive reasoning_content blocks must exactly match the original sequence" ([Z.ai thinking mode](https://docs.z.ai/guides/capabilities/thinking-mode)). MiniMax's card says "Do not remove the `<think>...</think>` part, otherwise, the model's performance will be negatively affected", and its ablation quantifies the cost of dropping interleaved thinking: **Tau² 87 → 64, BrowseComp 44.0 → 31.4, SWE-Bench Verified 69.4 → 67.2** ([HF MiniMax-M2](https://huggingface.co/MiniMaxAI/MiniMax-M2), [MiniMax interleaved thinking](https://www.minimax.io/news/why-is-interleaved-thinking-important-for-m2)). Mistral: "Always replay the full assistant message (including `ThinkChunk`) back into the message history" because stripping it "significantly degrades output quality" ([Mistral reasoning](https://docs.mistral.ai/capabilities/reasoning)).

The `opaque_roundtrip` mode is Gemini 3, Grok 4.7 and every OpenRouter `reasoning_details` array. Gemini 3 "always ha[s] the signature on the first function call part. It is mandatory to return that part"; the 400 reads `Function call <name> in the <index> content block is missing a thought_signature`, validation covers the current turn only, and the sentinels `"context_engineering_is_the_way_to_go"` / `"skip_thought_signature_validator"` are accepted when injecting calls or importing history from another model ([Gemini thought signatures](https://ai.google.dev/gemini-api/docs/generate-content/thought-signatures), [adk-js #149](https://github.com/google/adk-js/issues/149)). Through OpenRouter the same data rides as `reasoning_details[type="reasoning.encrypted", format="google-gemini-v1"]`, the docs require that "the entire sequence of consecutive reasoning blocks must match the outputs generated by the model during the original request; you cannot rearrange or modify the sequence", and Roo injects `{type: "reasoning.encrypted", data: "skip_thought_signature_validator", id: toolCalls[0].id, format: "google-gemini-v1", index: 0}` on Gemini assistant turns that lack one — the only known way to switch into Gemini mid-conversation ([OpenRouter reasoning tokens](https://openrouter.ai/docs/use-cases/reasoning-tokens), [Roo openrouter.ts](https://github.com/RooCodeInc/Roo-Code/blob/main/src/api/providers/openrouter.ts)). Grok 4.7 "returns `reasoning.encrypted_content` on every response, whether or not `include` lists it", to be passed "back unchanged in the next request" ([xAI reasoning guide](https://docs.x.ai/docs/guides/reasoning)). Compaction must therefore treat reasoning, `tool_use` and `tool_result` of a turn as one atomic unit; Roo's Gemini regression came from stripping `tool_use` blocks while the tool result still referenced their id ([Roo #11629](https://github.com/RooCodeInc/Roo-Code/issues/11629)).

The `strip` modes are the mirror image and mixing them up costs quality or 400s. Qwen3-235B-Thinking-2507 and QwQ say "Historical model output should only include the final output part and does not need to include the thinking content" (their output "may contain only `</think>` without an opening `<think>` tag") ([HF Thinking-2507](https://huggingface.co/Qwen/Qwen3-235B-A22B-Thinking-2507), [HF QwQ-32B](https://huggingface.co/Qwen/QwQ-32B)). Gemma 4: "You must remove (strip) the model's generated thoughts from the previous turn", except that "If a single model turn involves function or tool calls, thoughts must NOT be removed between the function calls" ([Gemma thinking](https://ai.google.dev/gemma/docs/capabilities/thinking)). gpt-oss drops prior `analysis` once the assistant answered on the `final` channel but keeps it while the last assistant message was a tool call, and Groq — a major OpenRouter upstream — rejects a replayed `reasoning_content` field outright (`reasoning_content is unsupported`) ([harmony cookbook](https://developers.openai.com/cookbook/articles/openai-harmony), [spring-ai #6968](https://github.com/spring-projects/spring-ai/issues/6968)). Nemotron 3 follows the Qwen convention and needs no replay ([Nemotron-3-Nano card](https://huggingface.co/nvidia/NVIDIA-Nemotron-3-Nano-30B-A3B-BF16)). DashScope adds an opt-in `preserve_thinking: true` for `qwen3.6+`/`qwen3.8-max` and (via Model Studio hosting) `kimi-k2.*`, but not for Qwen3.5, whose replay behaviour is undocumented ([Model Studio deep thinking](https://www.alibabacloud.com/help/en/model-studio/deep-thinking)).

Three cross-cutting rules follow. First, the harness-wide `--effort` flag must be mapped per row through `effort_values` and a per-host alias map (DeepSeek's `medium→high`, GLM-5.2's `low→high`, Databricks' `minimal→low` on V4.1 Flash but `→max` elsewhere) and never sent as `none` blindly — GLM-5.3 on Databricks rejects it and Z.ai returns 1210 ([Databricks query reasoning models](https://docs.databricks.com/aws/en/machine-learning/model-serving/query-reason-models)). Second, "off" for an always-thinking model means `reasoning_effort: low`, which is exactly OpenClaw's mapping for GLM-5.3 and the only safe choice for K3, gpt-oss and Grok ([OpenClaw Z.AI docs](https://docs.openclaw.ai/providers/zai)). Third, the GLM-5.2 conflict cannot be resolved from documentation, so the table encodes it as an `off_strategy: "try_disabled_then_effort_low"` — send `thinking: {type: disabled}`, and on a 400 whose body contains `1210` retry with `reasoning_effort: "low"`; the same branch covers 5.3 whether it rejects or coerces. The Databricks side has one open question that documentation cannot settle: whether the gateway forwards a replayed `reasoning_content` *into* DeepSeek, Kimi or GLM on the turn after a tool call. Databricks only says to pass the whole assistant message back verbatim, so the first live test on the work VPN is a two-turn tool loop on `databricks-deepseek-v4-1-flash`; if it 400s, the fallback for that route is `reasoning_effort: "none"` on DeepSeek (the only hosted family there that can switch thinking off) ([Databricks query reasoning models](https://docs.databricks.com/aws/en/machine-learning/model-serving/query-reason-models)).

## Sampling is "omit or vendor default", while limits and overflow strings are pure data

Temperature is the parameter the harnesses disagree on most, and the disagreement is really about who owns the default: Aider sends 0 unless a row says otherwise, Roo sends 0 on OpenRouter but forces 1.0 for budget-thinking models, OpenCode omits it except for a whitelist of families, and OpenRouter's own `default_parameters` are null for most reasoning models ([aider/models.py](https://github.com/Aider-AI/aider/blob/main/aider/models.py), [Roo model-params.ts](https://github.com/RooCodeInc/Roo-Code/blob/main/src/api/transform/model-params.ts), [opencode transform.ts](https://github.com/anomalyco/opencode/blob/dev/packages/opencode/src/provider/transform.ts)). The vendor facts settle it for the families that matter most: Moonshot fixes `temperature=1.0, top_p=0.95, n=1, presence_penalty=0, frequency_penalty=0` on K3 and K2.7-code and says "omit them from requests", K2.6 fixes 1.0 (thinking) / 0.6 (non-thinking) and "other values will result in an error", and OpenCode's hard-coded title-agent temperature produced `HTTP 400 invalid temperature: only 1 is allowed for this model` ([Kimi K3 quickstart](https://platform.kimi.ai/docs/guide/kimi-k3-quickstart), [Kimi K2.6 quickstart](https://platform.kimi.ai/docs/guide/kimi-k2-6-quickstart.md), [opencode #27796](https://github.com/anomalyco/opencode/issues/27796)). DeepSeek's thinking mode "does not support `temperature`, `presence_penalty`, or `frequency_penalty`" (no error, no effect) and clamps `top_p` below 0.95 to 0.95, while its penalties are deprecated API-wide ([DeepSeek thinking mode (zh-cn)](https://api-docs.deepseek.com/zh-cn/guides/thinking_mode), [DeepSeek reference](https://api-docs.deepseek.com/api/create-chat-completion)). xAI forbids `presencePenalty`, `frequencyPenalty` and `stop` with reasoning models and `logprobs` from 4.20 on; Z.ai bounds temperature to `[0.0, 1.0]` and its Messages route rejects `temperature: 3` with `temperature parameter invalid: value must be within [0,1]`; MiniMax ignores penalties and `logit_bias` and requires `n = 1` ([xAI reasoning guide](https://docs.x.ai/docs/guides/reasoning), [Z.ai reference](https://docs.z.ai/api-reference/llm/chat-completion), [AIHubMix](https://aihubmix.com/blog/glm-5-3-hands-on-guide-always-on-thinking-three-effort-levels-and-the-api-support-matrix), [MiniMax OpenAI-compatible API](https://platform.minimax.io/docs/api-reference/text-openai-api)). A `sampling.mode` of `omit` for those rows, plus an `unsupported_params` list the serializer strips, removes an entire class of 400s.

Where sampling is allowed, the model cards and OpenRouter's `default_parameters` agree closely enough to seed a `vendor_default` profile per thinking state. DeepSeek V4-Flash/Pro cards say `temperature = 1.0, top_p = 1.0`, V4.1-Flash `1.0` with `top_p 0.95 or 1.0`, V3.2 `1.0 / 0.95`, and R1 `0.5–0.7 (0.6)` with no system prompt ([HF DeepSeek-V4-Pro](https://huggingface.co/deepseek-ai/DeepSeek-V4-Pro), [HF DeepSeek-V4.1-Flash](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash), [HF DeepSeek-V3.2](https://huggingface.co/deepseek-ai/DeepSeek-V3.2), [DeepSeek-R1 README](https://github.com/deepseek-ai/DeepSeek-R1)). Kimi K2 instruct is 0.6 in Aider and 0.3 in Moonshot's HF tool-call guide, a conflict that resolves by host: those values apply only to self-hosted or third-party K2 (0711/0905) endpoints, because the first-party Moonshot endpoints on OpenRouter do not even list `temperature`/`top_p` in `supported_parameters` (so `require_parameters: true` would exclude them if sent) ([Aider model-settings.yml](https://raw.githubusercontent.com/Aider-AI/aider/main/aider/resources/model-settings.yml), [HF Kimi-K2-Instruct tool guide](https://huggingface.co/moonshotai/Kimi-K2-Instruct/blob/main/docs/tool_call_guidance.md), [OpenRouter kimi-k3 endpoints](https://openrouter.ai/api/v1/models/moonshotai/kimi-k3/endpoints)). GLM ships `1.0 / 0.95` from 4.6 on (4.5: `0.6 / 0.95`), but Z.ai's own agentic benchmark settings are `0.7 / 1.0` (Terminal-Bench, SWE-bench) and the only measured tool-corruption data — a 2.05-bpw local GLM-5.3-Flash with 16 tools — went from **4.2% malformed calls at T=1.0 to 0.8% at 0.6 and 0% at 0.0**, so the table keeps the vendor default for Z.ai's fp8 endpoints and applies a `0.6–0.7` `agentic_override` on quantised third-party hosts ([HF zai-org/GLM-4.7](https://huggingface.co/zai-org/GLM-4.7), [GLM DGX PR #3](https://github.com/0xSero/GLM-5.3-Flash-DGX-Spark/pull/3)). Qwen publishes per-variant presets: Instruct-2507 and Next-80B-Instruct `0.7 / 0.8 / top_k 20 / min_p 0`, Thinking-2507 and QwQ `0.6 / 0.95 / 20`, Coder-480B `0.7 / 0.8 / 20 / repetition_penalty 1.05`, Coder-Next `1.0 / 0.95 / 40`, Qwen3.5 thinking-general `1.0 / 0.95 / 20 / presence_penalty 1.5` and thinking-precise-coding `0.6 / 0.95 / 20 / 0` ([HF Instruct-2507](https://huggingface.co/Qwen/Qwen3-235B-A22B-Instruct-2507), [HF Thinking-2507](https://huggingface.co/Qwen/Qwen3-235B-A22B-Thinking-2507), [HF Qwen3-Coder-480B](https://huggingface.co/Qwen/Qwen3-Coder-480B-A35B-Instruct), [HF Qwen3-Coder-Next](https://huggingface.co/Qwen/Qwen3-Coder-Next), [HF Qwen3.5-122B-A10B](https://huggingface.co/Qwen/Qwen3.5-122B-A10B)). MiniMax M2/M2.1 cards recommend `1.0 / 0.95 / top_k 40` while the API's `top_p` default is 0.9 — send 0.95 explicitly; Gemma 3 and 4 use `1.0 / 0.95 / top_k 64` (the Gemma 4 `generation_config.json` is ungated and confirms it); gpt-oss recommends `1.0 / 1.0`; Google says to keep Gemini 3 at `1.0` because lowering it "may lead to unexpected behavior, such as looping"; Grok 4.7's OpenRouter default is `0.7 / 0.95`; Devstral 2's `generation_config.json` sets `0.15`, Mistral Large 3 wants "below 0.1", Codestral's OpenRouter default is `0.3`, Magistral `0.7 / 0.95`; Nemotron 3 Nano is the clearest published dual profile, `1.0 / 1.0` with thinking on and `0.6 / 0.95` for tool calling with thinking off ([HF MiniMax-M2.1](https://huggingface.co/MiniMaxAI/MiniMax-M2.1), [Gemma 4 generation_config](https://huggingface.co/google/gemma-4-31B-it/raw/main/generation_config.json), [gpt-oss README](https://github.com/openai/gpt-oss/blob/main/README.md), [Gemini 3 guide](https://ai.google.dev/gemini-api/docs/gemini-3), [Devstral 2 generation_config](https://huggingface.co/mistralai/Devstral-2-123B-Instruct-2512/raw/main/generation_config.json), [Mistral-Large-3 card](https://huggingface.co/mistralai/Mistral-Large-3-675B-Instruct-2512), [Nemotron-3-Nano card](https://huggingface.co/nvidia/NVIDIA-Nemotron-3-Nano-30B-A3B-BF16)). Llama 3.3/4 and Gemma 3 `generation_config.json` files are gated (HTTP 401), so their commonly quoted `0.6 / 0.9` defaults stay `null` in the table.

Context and output limits differ per host for the same model, which is why the table stores them per alias rather than per model, and why `max_tokens` must be computed, never static. DeepSeek's official V4 models have a 1M context and a 384K (393,216) output ceiling with `max_tokens` defaulting to 8K non-thinking, 64K thinking and 128K at `reasoning_effort: max`; its overflow error counts the requested completion — `This model's maximum context length is 1048576 tokens. However, you requested 1787370 tokens (1403370 in the messages, 384000 in the completion). Please reduce the length of the messages or completion.` — so Zed's static 384,000 default halved the usable window, and a terse variant `{"message":"Input token exceed the limit …","type":"api_error","code":"quota_limit_reached"}` was misclassified by one harness as an invalid request so that auto-compaction never fired ([DeepSeek reference](https://api-docs.deepseek.com/api/create-chat-completion), [zed #57718](https://github.com/zed-industries/zed/issues/57718), [deepseek-harness #3399](https://github.com/deepseek-ai/deepseek-harness/discussions/3399)). Moonshot's K3 has 1,048,576 context with `max_completion_tokens` "Defaults to 131072; can be set up to 1048576" (OpenRouter's `top_provider` shows 943,718 — use the official cap), K2.6/K2.7-code have 262,144 with a 32,768 default, the thinking-plus-content sum must fit in `max_tokens`, and overflow reads `Invalid request: Your request exceeded model token limit: 262144 (requested: 269030)` (docs also list `Input token length too long` and `prompt tokens + max_tokens exceeds the model specification`) ([Kimi K3 quickstart](https://platform.kimi.ai/docs/guide/kimi-k3-quickstart), [Kimi K2.6 quickstart](https://platform.kimi.ai/docs/guide/kimi-k2-6-quickstart.md), [kimi-cli #2011](https://github.com/MoonshotAI/kimi-cli/issues/2011), [Kimi error codes](https://platform.kimi.ai/docs/api/errors.md)). Z.ai caps output at 128K (96K on 4.5), gives GLM-5.2/5.3 a 1M window and 4.7 200K, returns `{"code":"1261","message":"Prompt too long"}` on overflow, and on streams signals `finish_reason: "model_context_window_exceeded"` instead of an error code ([Z.ai reference](https://docs.z.ai/api-reference/llm/chat-completion), [pi #9805](https://github.com/earendil-works/pi/issues/9805), [Z.ai errors](https://docs.z.ai/api-reference/api-code)). DashScope's overflow is `InternalError.Algo.InvalidParameter: Range of input length should be [1, 169984]` (the Coding Plan's limit), with `qwen3-coder-plus` at 1,048,576 / 65,536 and `qwq` at only 8,192 output ([hermes-agent #2220](https://github.com/NousResearch/hermes-agent/issues/2220), [models.dev](https://models.dev/api.json)). MiniMax M2.x is 204,800 / 131,072 (M1: 1M / 40,000) and every limit error carries code 2013 — `invalid params, context window exceeds limit (2013)` — which is non-retryable and also fires on the Anthropic route when `max_tokens` is missing ([MiniMax-M2 #119](https://github.com/MiniMax-AI/MiniMax-M2/issues/119), [QwenPaw #1273](https://github.com/agentscope-ai/QwenPaw/issues/1273)). OpenRouter's wording is `This endpoint's maximum context length is X tokens. However, you requested about Y tokens`, vLLM's is `This model's maximum context length is N tokens. However, you requested M tokens (A in the messages, B in the completion)`, Gemini's is `The input token count (1236488) exceeds the maximum number of tokens allowed (1048576).` (with accumulated `thoughtSignature` fields able to push a session over it), xAI's Grok-3-era text is `This model's maximum prompt length is 131072 but the request contains 136973 tokens.`, and Mistral documents only "400 Bad Request" ([agno #3980](https://github.com/agno-agi/agno/issues/3980), [vLLM #20409](https://github.com/vllm-project/vllm/issues/20409), [gemini-cli #12493](https://github.com/google-gemini/gemini-cli/issues/12493), [cline #3120](https://github.com/cline/cline/issues/3120), [Mistral known limitations](https://docs.mistral.ai/resources/known-limitations)). Databricks publishes no context-overflow string at all; what it publishes is a pre-admission rule — "if `max_tokens` would cause you to exceed OTPM limits, Databricks immediately rejects requests with a 429 error" whose body carries `limit_type`, `limit`, `current` and `retry_after` — plus per-model budgets: **ITPM 2,000,000 / OTPM 40,000 / QPH 7,200** for DeepSeek V4.1 Flash, Kimi K3 and GLM 5.3, only **OTPM 4,000** for DeepSeek V4 Pro 0813 and **10,000** for V4 Flash 0731, 200,000 / 20,000 for GLM 5.2, 1,000,000 / 100,000 / 360,000 for Qwen3.5 122B, a 4 MB payload cap that fails as `SSLEOFError` rather than a 4xx, a 597-second execution cap, GLM-5.3 output capped at 65,536 and Qwen3.5 at 25K, and 8,192-token output caps for Gemma/Llama on provisioned throughput ([Databricks limits](https://docs.databricks.com/aws/en/machine-learning/foundation-model-apis/limits), [Databricks supported models](https://docs.databricks.com/aws/en/machine-learning/foundation-model-apis/supported-models), [Databricks KB SSL error](https://kb.databricks.com/en_US/machine-learning/ssl-error-when-invoking-databricks-model-serving-endpoint)).

The budgeting rule that satisfies every host is `max_tokens = min(row.output_cap, endpoint.max_completion_tokens, host.otpm_budget, context − estimated_prompt − buffer)`, sent explicitly on every request, with an `overflow_error_regex[host]` classifier that extracts both numbers where the message provides them and retries once with a recomputed budget before falling back to compaction. On OpenRouter the endpoint you land on may cap far below `top_provider.max_completion_tokens` (7,168 on SambaNova/Mara and 16,384 on DeepInfra fp4 for `deepseek-v3.2`, 16,384 on Venice for `glm-4.6/4.7`, 16,384 on DeepInfra for `kimi-k3`), reasoning tokens count against `max_tokens`, and a 64-tool, ~287k-token prompt on `deepseek-v4.1-flash` returned `finish_reason: "length"` with a single completion token five times out of five — a provider failure to re-route, not a cap to retry in place ([OpenRouter v3.2 endpoints](https://openrouter.ai/api/v1/models/deepseek/deepseek-v3.2/endpoints), [OpenRouter reasoning tokens](https://openrouter.ai/docs/use-cases/reasoning-tokens), [OpenRouterTeam/docs #538](https://github.com/OpenRouterTeam/docs/issues/538)). Prompt caching is automatic on DeepSeek (reads at 0.1x on OpenRouter), Moonshot (hits only when the previous prompt exceeded 256 tokens; `prompt_cache_options.ttl` `5m|1h`), Z.ai (implicit, ~50% discount) and DashScope (≥1,024-token prefix at 20% of input price), so the stable-prefix discipline from the earlier report — system prompt and tool schemas first, byte-identical each turn, reasoning echoed rather than edited — pays on every open family ([OpenRouter prompt caching](https://openrouter.ai/docs/features/prompt-caching), [Kimi chat API](https://platform.kimi.ai/docs/api/chat), [Z.ai context caching](https://docs.z.ai/guides/capabilities/cache), [Model Studio context cache](https://www.alibabacloud.com/help/en/model-studio/context-cache)).

## One leading system message, string tool results and explicit pins make the hosts interchangeable

System-message placement is a hard error on one family, a silent failure on another and a platform rule on Databricks, so a single normaliser has to satisfy all three. Qwen3.5+ chat templates contain `{%- if message.role == "system" %}{%- if not loop.first %}{{- raise_exception('System message must be at the beginning.') }}`, which fires on vLLM, llama.cpp, LocalAI, NVIDIA NIM and any OpenRouter provider using the stock template whenever a harness injects a second or trailing system message — OpenCode hit it with `qwen3.5-397b-a17b` and with `qwen3.5-122b-a10b` on the NVIDIA provider, and memory plugins that "create multiple system messages" break the same way ([HF Qwen3.5 discussion #5](https://huggingface.co/Qwen/Qwen3.5-35B-A3B/discussions/5), [opencode #20785](https://github.com/anomalyco/opencode/issues/20785), [opencode #16560](https://github.com/anomalyco/opencode/issues/16560), [vLLM #41114](https://github.com/vllm-project/vllm/issues/41114)). DeepSeek accepts two-system payloads with HTTP 200 where Qwen errors and rejects the `developer` role, but a request whose *last* message is `system` produced 1–3-token empty completions (`finish_reason: stop`) from DeepSeek V4 Flash via OpenRouter until go-code rewrote every non-leading system message to `user` — "three consecutive production runs … zero empty response retries" ([nearai PR #1026](https://github.com/nearai/cloud-api/pull/1026), [DeepSeek-V3.2 card](https://huggingface.co/deepseek-ai/DeepSeek-V3.2/raw/main/README.md), [go-code PR #1396](https://github.com/dennisonbertram/go-code/pull/1396)). Databricks: "The `system` role can only be used once, as the first message in a conversation"; Z.ai enumerates only `user/system/assistant/tool`; DashScope and MiniMax document no `developer` role ([Databricks FMAPI reference](https://docs.databricks.com/aws/en/machine-learning/foundation-model-apis/api-reference), [Z.ai reference](https://docs.z.ai/api-reference/llm/chat-completion)). Gemma 3 has no system turn at all — instructions go "directly within the initial user prompt", which Aider encodes as `use_system_prompt: false` and LiteLLM as `supports_system_messages: false` — whereas Gemma 4 has a real `system` role ([Gemma prompt structure](https://ai.google.dev/gemma/docs/core/prompt-structure), [Gemma 4 prompt formatting](https://ai.google.dev/gemma/docs/core/prompt-formatting-gemma4)). Mistral's own v2/v3 tokenizers prepend the system prompt "to the last user message", but that is a self-hosted template behaviour; the hosted API takes a leading `system` normally ([Mistral chat-template cookbook](https://docs.mistral.ai/resources/cookbooks/concept-deep-dive-tokenization-chat_templates)). gpt-oss splits roles: `system` carries meta-information and the `Reasoning:` level, `developer` carries instructions and tools rendered as TypeScript namespaces — again a self-hosted concern, since hosted endpoints apply the template ([harmony cookbook](https://developers.openai.com/cookbook/articles/openai-harmony)). R1 wants no system prompt, which Roo implements by converting the system prompt to a user message for `deepseek/deepseek-r1*` ([DeepSeek-R1 README](https://github.com/deepseek-ai/DeepSeek-R1), [Roo openrouter.ts](https://github.com/RooCodeInc/Roo-Code/blob/main/src/api/providers/openrouter.ts)). The single exception to "exactly one leading system message" is Moonshot's dynamic tool loading, where later `system` messages carry tool definitions "without `content` field" and "are not retained by the server" — usable only on Moonshot direct, never on Databricks ([Kimi K3 tool-calling best practice](https://platform.kimi.ai/docs/guide/kimi-k3-tool-calling-best-practice.md)). The normaliser is therefore: merge into one leading `system`; rewrite every later system-role scaffold (Claude Code's system reminders included) to `user`; never end on `system`; map `developer` to `system`; fold into the first user turn when the row says `fold_into_first_user` (Gemma 3, R1).

Multipart content and vision follow the same "string is the portable form" logic. DeepSeek's system message is "Text content only via `content` (string)", user and tool content may be strings or part arrays (`text`, `image_url` with http(s) URLs up to 8,192 characters or base64 and `detail` `low|high|original|auto`, `file`), and only `deepseek-flash` (V4.1) has vision — `deepseek-v4-pro` says "Vision: Not supported" ([DeepSeek reference](https://api-docs.deepseek.com/api/create-chat-completion), [DeepSeek pricing](https://api-docs.deepseek.com/quick_start/pricing)). Moonshot refuses public image URLs: "Use base64 or `ms://<file-id>`", content "must be an array of objects, not a serialized string", bodies under 100 MB, video through `files.create` ([Kimi K3 quickstart](https://platform.kimi.ai/docs/guide/kimi-k3-quickstart), [Kimi K2.6 quickstart](https://platform.kimi.ai/docs/guide/kimi-k2-6-quickstart.md)). GLM-5.3 "currently supports text-only inputs" while 5.3-Flash takes video/image/text/file, and GLM-5.2 on Z.ai intermittently rendered tool results "as image content blocks instead of text" at long context — flatten multipart tool results to plain strings for GLM ([Z.ai GLM-5.3](https://docs.z.ai/guides/llm/glm-5.3), [Z.ai GLM-5.3-Flash](https://docs.z.ai/guides/vlm/glm-5.3-flash), [zai-org/GLM-5 #110](https://github.com/zai-org/GLM-5/issues/110)). Databricks documents list content for Claude but "string-typed content required" for other models, Llama 4 takes up to 5 images, Mistral Large 3 and Medium 3.5 accept images, Grok 4.6 on Databricks has vision "No", and on OpenRouter the V3.x DeepSeek IDs, Kimi K2/K2-0905/K2-thinking, MiniMax and gpt-oss are text-only, so image parts must be dropped or described in text for those rows ([Databricks FMAPI reference](https://docs.databricks.com/aws/en/machine-learning/foundation-model-apis/api-reference), [Meta Llama 4 prompt format](https://dev.meta.ai/llama/docs/model-cards-and-prompt-formats/llama4/), [OpenRouter models](https://openrouter.ai/api/v1/models)). One shape rule protects Kimi specifically: replay assistant messages that carry only `tool_calls` with `content` exactly as returned (`null` or `""`), because vLLM once converted `''` into `[{'type': 'text', 'text': ''}]` and the Kimi template inserted it literally before the tool-call section ([vLLM Kimi K2 accuracy blog](https://vllm.ai/blog/2025-10-28-kimi-k2-accuracy)).

On OpenRouter the model ID is not the model: routing decides which quantisation, output cap and parser you get, and the live endpoint tables show why `provider.require_parameters: true` plus an explicit `order` is mandatory whenever `tools` is sent. Without it, tools are "soft preferences", and when routing lands on a tool-less endpoint the response is `404 No endpoints found that support tool use` ([OpenRouter provider routing](https://openrouter.ai/docs/features/provider-routing), [claude-code-router #409](https://github.com/musistudio/claude-code-router/issues/409)). The tool-less endpoints as of 2026-09-23 include `atlas-cloud`/`mara` on `deepseek-chat-v3.1`, `streamlake` on `v3.1-terminus`, `baidu`/`digitalocean`/`mara`/`sambanova` on `deepseek-v3.2`, `deepinfra`/`streamlake` on `r1-0528`, `dekallm` on `v4.1-flash`, `chutes`/`fireworks/fast` on `kimi-k3`, `mancer` on `glm-4.7`, one `google-vertex` endpoint on `qwen3-235b-a22b-2507`, `siliconflow` on `qwen3.5-122b`, `streamlake` on `qwen3.5-397b`, the official `minimax` endpoint on `minimax-m1`, and `decart` behind `z-ai/glm-5.2:free` ([OpenRouter endpoints API](https://openrouter.ai/api/v1/models/deepseek/deepseek-v4.1-flash/endpoints)). First-party endpoints exist and should be pinned with `allow_fallbacks: false`: `deepseek` on `deepseek-v4.1-flash` and `deepseek-v4-pro-0813` (393,216 output, lowest cache-read price), `moonshotai/int4` on `kimi-k2.6` and `kimi-k2.7-code` (plus `moonshotai/highspeed` at 2x output price), `moonshotai/mxfp4` on `kimi-k3`, `z-ai/fp8` on GLM-5.x (fp4 on 4.6/4.7), `alibaba` as the only provider for `qwen3-max`, `qwen3-coder-plus/flash` and `qwen3-235b-a22b`, and `minimax/fp8` on M2/M2.1 ([OpenRouter kimi-k3 endpoints](https://openrouter.ai/api/v1/models/moonshotai/kimi-k3/endpoints), [OpenRouter glm-5.3 endpoints](https://openrouter.ai/api/v1/models/z-ai/glm-5.3/endpoints)). Quantisation is the main quality variable — OpenRouter itself says provider differences are "mainly because quantization differences across hosts can change the model's responses" — so `quantizations: ["fp8","bf16","unknown"]` (Kimi first-party is natively `int4`/`mxfp4` from QAT and must be allowed) belongs on every pin ([OpenRouter DeepSeek blog](https://openrouter.ai/blog/insights/why-openrouter-for-deepseek/), [GitHub MoonshotAI/Kimi-K3](https://github.com/MoonshotAI/Kimi-K3)). Three catalogue facts change earlier assumptions: `mistralai/devstral*` and `magistral*` are absent from the live OpenRouter list (LiteLLM still carries them; pin Devstral to Mistral's own API or self-host), `qwen/qwq-32b` and `qwen/qwen3-coder:free` no longer exist, and the `~deepseek/*-latest` and `~moonshotai/kimi-latest` router aliases silently change models ([OpenRouter models](https://openrouter.ai/api/v1/models)). The recommended `provider` blocks are in the JSON rows; the family-level defaults are `order: ["deepseek"]` / `["moonshotai"]` / `["z-ai", …]` / `["alibaba", …]` / `["minimax","novita"]` with `allow_fallbacks: false, require_parameters: true`, and for the no-first-party IDs (`v4-flash-0731`, V3.x, R1, K2.x) an `order` plus `ignore` list built from the tool-less, tiny-cap and degraded endpoints.

Databricks is the stricter host and the one with the fewest models. Its pay-per-token catalogue on 2026-09-22 carries `databricks-deepseek-v4-1-flash` (text+image), `-deepseek-v4-pro-0813`, `-deepseek-v4-flash-0731`, `-kimi-k3` (text+image, 1M), `-glm-5-3` (1,048,576 context, 65,536 output, always reasons), `-glm-5-3-flash`, `-glm-5-2`, `-qwen35-122b-a10b` (Public Preview, "always reasons", 256K / 25K), `-qwen3-next-80b-a3b-instruct`, `-llama-4-maverick`, `-meta-llama-3-3-70b-instruct`, `-meta-llama-3-1-8b-instruct`, `-gemma-3-12b`, `-gpt-oss-120b/20b`, `-grok-4-6` and the Gemini 3.x family — and **no DeepSeek V3.x/R1, Kimi K2.x, GLM-4.x, MiniMax, Nemotron or Mistral** ([Databricks supported models](https://docs.databricks.com/aws/en/machine-learning/foundation-model-apis/supported-models)). Every open model there is reachable only through OpenAI Chat Completions or Responses on two namespaces (`/serving-endpoints` with `databricks-*` names, `/ai-gateway/mlflow/v1` with `system.ai.*`), with a strict body allow-list because an unknown field surfaces as `error_code 'BAD_REQUEST' … json: unknown field "tool_choice"`, `stream` documented as defaulting to `true` (send it explicitly), `parallel_tool_calls` absent from the schema (omit it), `tools` capped at 32, function calling "optimized for single turn", and Llama endpoints prepending their own system prompt so `prompt_tokens` include it ([Databricks FMAPI reference](https://docs.databricks.com/aws/en/machine-learning/foundation-model-apis/api-reference), [Databricks community 66927](https://community.databricks.com/t5/generative-ai/trouble-using-foundation-models-api-with-instructor/td-p/66927), [Databricks function calling](https://docs.databricks.com/aws/en/machine-learning/model-serving/function-calling)). The 32-tool cap collides with Claude Code's tool set plus MCP, so the Databricks profile freezes a ≤32-tool catalogue per session (core tools plus top MCP tools) and exposes the rest through a lazy-load tool, exactly the trade-off Moonshot recommends for K3 ("don't put every tool definition into the request — they eat up context") ([Kimi K3 tool-calling best practice](https://platform.kimi.ai/docs/guide/kimi-k3-tool-calling-best-practice.md)). Reasoning-effort defaults on Databricks are `max` for DeepSeek V4.x, Kimi K3 and GLM 5.3 — which inflates latency and cost unless the harness lowers them — and `low` for Gemini 3.x, while `databricks-gemini-*` additionally drop the `id` field on function calls ([Databricks query reasoning models](https://docs.databricks.com/aws/en/machine-learning/model-serving/query-reason-models)).

## Fourteen recurring loop failures reduce to seven mechanical fixes

The issue trackers of OpenCode, Roo, Cline, Kilo, Crush, hermes-agent, pi, Zed, Continue and dsh describe the same handful of failures for every open family, and each maps to a mechanism rather than to prompt advice. The first and most expensive is **dropped reasoning**: the DeepSeek 400 (`opencode #24190`, `#24722`, `kilocode #9501`, `claude-code-router #1378`, `openclaw #71435`, `goclaw #1186`, `oh-my-pi #12977`) and its silent twin where the model "returns `finish_reason: 'stop'`, causing the session loop to exit prematurely" on DeepSeek V4 Flash/Pro and Kimi K2 ([opencode #35689](https://github.com/anomalyco/opencode/issues/35689)); the fix is the `reasoning_echo` branch driven by the row's `reasoning.replay` mode, with `""` injected where a turn had none. Second is **id mangling**: Kimi's 20% pass rate after id sanitisation, Mistral's `invalid_function_call code 3280` through OpenRouter, MiniMax's 2013 after compaction rewrote ids, and Kilo's "missing the assistant message between tool calls" on `kimi-k2-0905` ([openclaw #62319](https://github.com/openclaw/openclaw/issues/62319), [vercel/ai #11802](https://github.com/vercel/ai/issues/11802), [openclaw #66892](https://github.com/openclaw/openclaw/issues/66892), [kilocode #3237](https://github.com/Kilo-Org/kilocode/issues/3237)); the fix is `tool_id_normalize` keyed on `tool_id_format` plus the dsh serialize-time invariant that every `tool_calls[i].id` is answered by a `tool` message in order, with synthetic error results on crash or cancel ([dsh #4843](https://github.com/deepseek-ai/deepseek-harness/discussions/4843)). Third is **leaked markup**, covered above, whose fix is the gated `leak_parser` plus `think_tag_strip` (leading `<think>…</think>`, stray `<｜end▁of▁sentence｜>` tokens seen in reasoning strings on `deepseek-v4-flash-0731`, a dangling `</think>` from GLM-5.3 when `enable_thinking: false` is sent to a template that has no switch) ([hermes-agent #86303](https://github.com/NousResearch/hermes-agent/issues/86303), [vLLM #54744](https://github.com/vllm-project/vllm/issues/54744)).

The fourth class is **malformed or mis-typed arguments**, and the evidence says it is payload-size and host correlated rather than random. Crush's sessions on Fireworks-hosted GLM-4.6/5.2 died with `tool_calls[].function.arguments for function 'edit' must be a JSON object string (or an object), got invalid JSON` only on `edit`/`write` calls carrying multi-line code, while DeepSeek V4 Pro and Kimi K2.7 on the same provider were fine; GLM-5 on NVIDIA NIM emitted arguments missing the closing brace; GLM-5.3 on ds4 emitted `"false"` as a string for booleans; Qwen models emit Python literals that strict providers reject with `tool_calls的function的arguments必须是有效的JSON格式`; Qwen3-Coder's parser hands OpenCode objects where strings were declared (`Invalid input: expected string, received object`); DeepSeek V4 Flash on DeepInfra "repeatedly passes empty 'content'" when the payload contains HTML-like tags; and vLLM's DSML parser sometimes wraps arguments in a spurious `"arguments"`/`"input"` key ([crush #3153](https://github.com/charmbracelet/crush/issues/3153), [zai-org/GLM-5 #15](https://github.com/zai-org/GLM-5/issues/15), [local-llm #41](https://github.com/evanwtf/local-llm/issues/41), [agno #10231](https://github.com/agno-agi/agno/issues/10231), [opencode #6918](https://github.com/anomalyco/opencode/issues/6918), [opencode #26913](https://github.com/anomalyco/opencode/issues/26913), [sglang #38924](https://github.com/sgl-project/sglang/issues/38924)). The fix is one `args_repair` branch — strip fences, `ast.literal_eval`-style repair, brace balancing, unwrap a lone `arguments`/`input` key, coerce objects to strings for `string`-typed parameters and `"false"`/`"true"` to booleans — followed by re-encoding to canonical JSON before replay, with anything still invalid routed to an `invalid` pseudo-tool whose result tells the model what was wrong, never a fatal stream error; and a per-row `prefer_small_edits` hint so GLM on quantised hosts gets several small edits rather than one large `write`. OpenCode's most-cited bug shows the one exception: a tool call truncated by `finish_reason: length` (its output cap was hard-wired at 32k) was misclassified as an invalid tool and the session doom-looped, so the branch must check `length` first and tell the model to split the operation ([OpenCode #18108](https://github.com/anomalyco/opencode/issues/18108)).

The fifth class is **streaming**. Kimi's SGLang-served `KimiK2Detector` "silently drops / hangs" with multiple tool calls per turn, arguments over ~5 KB containing markdown or nested braces, or a marker split across SSE chunks, leaving clients "forever in `partial: true`"; the documented mitigation is `stream: false` for those endpoints, and the vLLM port raised schema accuracy "from 87% → 98–100%" ([sglang #23363](https://github.com/sgl-project/sglang/issues/23363)). GLM ids change mid-stream on Mistral-hosted endpoints, parallel calls collapse when `tool_calls[].index` is missing, and null SSE deltas can wipe a captured id when the client writes explicit nulls ([mistral-vibe #1127](https://github.com/mistralai/mistral-vibe/issues/1127), [WeKnora #3570](https://github.com/Tencent/WeKnora/issues/3570)). The `stream_aggregate` branch therefore keys strictly by `index`, treats a missing index as "same call", never overwrites id or name with null, ignores empty `tool_calls: []` on reasoning-only chunks, and validates the assembled JSON before dispatch, with a per-row `stream_tool_args: false` fallback for Kimi on non-first-party hosts. Sixth is **loop and emptiness**: DeepSeek V4 Pro "collapses into repeated identical tool_call" from ~100k tokens of context, an OpenCode subagent issued **364 identical grep calls over ~50 minutes**, V4 Pro returned `content=""`, `reasoning_content=""`, `completion_tokens=0` after tool messages in 22 of 46 turns, GLM-5.2 through Claude Code dropped a planned `cd … &&` prefix from its emitted bash call ten times in a row, and local GLM-5.3-Flash returned `finish_reason: tool_calls` with `content: []` so that "agents loop indefinitely in clients that trust finish_reason=tool_calls" ([qwen-code #4695](https://github.com/QwenLM/qwen-code/issues/4695), [OpenCode #45442](https://github.com/anomalyco/opencode/issues/45442), [DeepSeek-V3 #1453](https://github.com/deepseek-ai/DeepSeek-V3/issues/1453), [zai-org/GLM-5 #116](https://github.com/zai-org/GLM-5/issues/116), [ds4 #1](https://github.com/IngeniousIdiocy/ds4/issues/1)). Moonshot's own guidance for repeated calls is to verify that the returned message was appended as-is and every call answered, then inject reminders at 3, 5 and 8 repetitions; community dsh plugins deny the second identical call outright ([Kimi tool-call repeat guide](https://platform.kimi.ai/docs/guide/tool-call-repeat.md), [dsh-repeat-tool-breaker](https://github.com/snailium/dsh-repeat-tool-breaker)). The `loop_guards` branch is a cumulative per-turn hash of tool name plus canonical arguments (remind at 3, deny at 5, end the turn at 8), an `empty_completion_retry` (`completion_tokens == 0` with tools present → retry once, then lower effort or switch provider), and a `tool_calls`-with-no-parseable-call guard that re-prompts instead of honouring `finish_reason`.

The seventh class is **host-level**: OpenRouter's `404 No endpoints found that support tool use` and `Invalid request: tokenization failed` on `moonshotai/kimi-k2.6` from one harness while curl succeeded, Z.ai's Coding Plan returning 429 code 1305 whenever the system prompt contained the phrase "Hermes Agent", Databricks 400s on unknown fields and 429s on over-budget `max_tokens` ([claude-code-router #409](https://github.com/musistudio/claude-code-router/issues/409), [pi #5159](https://github.com/earendil-works/pi/issues/5159), [hermes-agent #47685](https://github.com/NousResearch/hermes-agent/issues/47685)). These are handled by the `host_allowlist` branch (emit `provider`, `reasoning`, `plugins`, `models`, `usage` only when the base URL is `openrouter.ai`; strip everything outside Databricks' documented field set there; send `stream` explicitly) together with the `max_tokens_budget`/`overflow_classifier` pair from the previous section. Two findings temper the "tables fix everything" story. Aider's polyglot leaderboard is still the only public per-model edit-compliance data — DeepSeek V3.2-Exp Reasoner **97.3% well-formed**, DeepSeek V3 98.7%, Kimi K2 92.9%, Qwen3-235B 92.9%, Qwen3-32B 83.6%, Qwen2.5-Coder-32B 71.6% with `diff` versus 99.6% with `whole` — so a per-row `edit_format` switch (exact `Edit` with whitespace-tolerant matching above ~85%, `Write`-fallback below) remains worthwhile, and Aider ships no tuned rows at all for GLM, Qwen3, MiniMax, Kimi-thinking, Gemini 3 or gpt-oss ([Aider polyglot leaderboard](https://raw.githubusercontent.com/Aider-AI/aider/main/aider/website/_data/polyglot_leaderboard.yml), [Aider model-settings.yml](https://raw.githubusercontent.com/Aider-AI/aider/main/aider/resources/model-settings.yml)). And Qwen Code shows the cheapest prompt-level lever: one Claude-Code-style prompt whose few-shot tool-call *notation* is swapped per family (`<function=…>` for `qwen*-coder`, JSON for `qwen*-vl`, `<|tool_call>` for `gemma4`), selected by regex on the model id ([qwen-code prompts.ts](https://raw.githubusercontent.com/QwenLM/qwen-code/main/packages/core/src/core/prompts.ts)).

## The table carries parameters, eight branches carry behaviour

The mature tables only agree on booleans and limits: models.dev's `tool_call`/`reasoning`/`attachment`/`limit`, LiteLLM's `supports_*` flags, OpenRouter's `supported_parameters` and Cline's capability list all express *whether* a model can do something, and only three of them express anything a loop needs — models.dev's `reasoning_options` (`toggle` / `effort` / `budget_tokens`) and `interleaved.field` (`reasoning_content` vs `reasoning_details`), OpenRouter's `reasoning{mandatory,default_enabled,supported_efforts,default_effort}` and `default_parameters`, and Roo's `preserveReasoning`/`defaultTemperature` ([models.dev README](https://github.com/sst/models.dev/blob/dev/README.md), [models.dev api.json](https://models.dev/api.json), [OpenRouter models](https://openrouter.ai/api/v1/models), [Roo model.ts](https://github.com/RooCodeInc/Roo-Code/blob/main/packages/types/src/model.ts)). Every harness then resolves behaviour in the same order — exact-id row, then substring rules on the id, then provider defaults — and keeps hand-written branches for what tables cannot say: Aider's `apply_generic_model_settings` (`"deepseek" in model and "r1"` → `use_temperature=False; reasoning_tag="think"`, `"qwen3" and "235b"` → `system_prompt_prefix="/no_think"`), Roo's `convertToR1Format`, Gemini sentinel injection and Mistral id scrub, OpenCode's per-family `temperature()`/`topP()`/`topK()` regexes and `interleaved.field` re-emission "even when empty" ([aider/models.py](https://github.com/Aider-AI/aider/blob/main/aider/models.py), [Roo openrouter.ts](https://github.com/RooCodeInc/Roo-Code/blob/main/src/api/providers/openrouter.ts), [opencode transform.ts](https://github.com/anomalyco/opencode/blob/dev/packages/opencode/src/provider/transform.ts)). Kilo has gone furthest, replacing its static model table with per-model `defaults` and `compatibility` objects resolved by protocol code, and pi-ai's compat switches (`supportsDeveloperRole`, `requiresToolResultName`, `requiresAssistantAfterToolResult`, `requiresReasoningContentOnAssistantMessages`, `thinkingFormat`, `supportsStrictMode`, `maxTokensField`, `cacheControlFormat`) are the most complete public checklist of the same idea ([Kilo provider.ts](https://github.com/Kilo-Org/kilocode/blob/main/packages/llm/src/provider.ts), [dsh config catalog](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/config-catalog.md)).

The split for halo follows directly. **Data-drivable** (in `model_table.json`): ids and aliases per host; context, output cap and output default per alias; modalities; `tools`, `tool_choice_modes`, `max_tools`, `parallel_tools` and which hosts accept the `parallel_tool_calls` field; `tool_id_format` and tool-result shape; strict-mode kind; the names of leak patterns and serving parsers; the reasoning field name, replay mode, mandatory/default-on flags, toggle shape, effort vocabulary, default effort, per-host alias maps and the "off" strategy; sampling mode and per-thinking-state profiles plus `unsupported_params`; system placement; per-host overflow regexes; OpenRouter provider pins; Databricks rate limits; and the ordered list of hook names to run. **Code branches** (eight families of them): `reasoning_echo` (echo verbatim including `""`, opaque round-trip, sentinel injection, strip-prior-turns-except-tool-steps, harmony drop-after-final); `tool_id_normalize` (preserve, Kimi rename on import, Mistral scrub-and-pad applied symmetrically, MiniMax never synthesise); `system_normalize` (single leading system, scaffold→user, never trailing, `developer`→`system`, Gemma-3/R1 fold, Mistral `"Done."` bridge); `leak_parser` + `think_tag_strip` + `args_repair` (pattern set and coercions chosen by row); `stream_aggregate` (by `index`, null-safe, validate before dispatch, `stream:false` fallback); `max_tokens_budget` + `overflow_classifier` (compute per host, parse both numbers, one retry, then compaction); `loop_guards` (repeat breaker, empty-completion retry, `tool_calls`-with-no-call guard, `length`-vs-malformed); and `host_allowlist` (OpenRouter-only fields, Databricks strict field set, explicit `stream`, ≤32 tools frozen per session, per-host effort remap, GLM try-disabled-then-low). Runtime selection is `row = families[model.family] ⊕ model overrides ⊕ host profile`, then wire choice, then `hooks.pre_send` and `hooks.post_receive` in the listed order. The consolidated schema and merged rows follow; family objects hold shared rules, model rows override only what differs, values marked `"VERIFY:"` or listed under `unverified` are not vendor-confirmed, and conflicts between the notes are resolved in place with the losing value recorded in `quirks`.

### Corrections and additions to the earlier "DeepSeek and OpenRouter ori harnesses" report

## Conclusion

The picture that emerges is that "make every model work the same way" is mostly a data problem with a thin code core, and that the code core is smaller than the issue trackers suggest because the failures cluster. Three vendors enforce id formats, four demand reasoning echo, two forbid non-fixed sampling, one family forbids a second system message, and two return opaque blobs that must round-trip; every one of those facts fits in a row, and every mechanism that consumes them already exists in some harness as a hand-written branch keyed on a model-id substring. Moving the keys into `model_table.json` and leaving only the eight branches in code turns the per-model bug fixes of OpenCode, Roo, Cline, Kilo, Crush, Aider and dsh into a maintenance surface that halo can update from `/api/v1/models`, the endpoint tables and the vendor docs without touching the loop.

Two live tests decide the remaining shape of the Databricks profile — whether replayed `reasoning_content` is forwarded on the turn after a tool call, and whether GLM-5.2 rejects or coerces `thinking.type: disabled` — and both are already encoded as a try-then-fallback so the answer changes a row, not a branch. The larger implication is that a model's suitability for halo is now measurable from the table itself: a row with `tool_id_format: preserve`, `replay: echo_required*`, `sampling.mode: omit`, a first-party pin and a 1M window (Kimi K3, DeepSeek V4.1 Flash, GLM-5.3) is a first-class target, while a row that needs `prompt_emulated` tools, `fold_into_first_user` and third-party-only hosting (Gemma 3, V3.x DeepSeek, K2.x) is a fallback, and the harness should say so in `/model` before the user spends a session finding out.
